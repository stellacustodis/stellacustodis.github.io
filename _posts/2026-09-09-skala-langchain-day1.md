## LLM 호출을 서비스 흐름으로 바꾸기

첫날 교안은 LLM의 입력·출력 구조에서 출발해 LangChain의 기본 구성 요소와 Prompt Template을 다룬다. 프롬프트는 일회성 문자열보다 입력 변수, 지시, 필요한 문맥, 기대 출력 형식을 분리해 관리할 때 변경과 검증이 쉽다.

```text
사용자 입력 → 입력 검증 → 프롬프트 구성 → 모델 호출 → 출력 해석 → 응답
```

모델의 답이 문장으로 그럴듯해도 애플리케이션에 필요한 필드가 없거나 형식이 틀리면 다음 단계가 실패한다. 따라서 구조화 출력이나 파서를 두고, 필수 필드와 값의 범위를 코드에서 다시 검사한다. 템플릿을 쓴다고 근거 없는 사실이 자동으로 사라지는 것은 아니다.

## 상태와 외부 지식을 구분한다

대화 이력은 사용자가 이전에 무엇을 말했는지 유지하는 단기 상태다. 문서 검색은 모델이 답할 때 필요한 외부 근거를 가져오는 과정이다. 둘을 한 프롬프트에 계속 누적하면 비용과 혼선이 커지므로, 요청 목적에 맞는 이력과 검색 결과만 전달한다.

첫날 학습의 요지는 모델 호출을 감춘 래퍼를 외우는 것이 아니라, 입력·출력 계약과 실패 시 처리를 명확히 하는 데 있다.

## 템플릿에서 고정할 것과 바꿀 것

질문마다 바뀌는 사용자 입력은 변수로 두고, 역할·출력 필드·근거 사용 원칙은 템플릿의 계약으로 둔다. 예를 들어 답변에 `answer`와 `sources`가 필요하다면 모델 응답을 파싱한 뒤 두 필드의 존재와 자료 ID의 유효성을 검사한다. JSON처럼 보이는 문자열을 받았다는 사실만으로 유효한 결과가 아니다.

장기 대화에서는 지난 메시지를 모두 다시 보내는 방식이 간단하지만 토큰 비용과 오래된 지시의 충돌이 커진다. 어떤 상태가 다음 질문에 필요한지 먼저 정한 뒤 필요한 대화만 남긴다.
