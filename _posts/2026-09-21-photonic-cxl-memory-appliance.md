## 세 줄 요약

이 논문은 긴 컨텍스트 LLM 추론에서 GPU 밖으로 밀려난 KV 캐시를 다시 불러오는 비용과, 기존 전기적 CXL 메모리 풀의 스위치 지연·거리·전력 확장 문제를 함께 다룬다. 핵심은 16×16 패시브 광 섬유 셔플로 16개 호스트와 16개 메모리 모듈을 직접 연결해, 32 TB DDR5와 1.125 TB HBM3E를 하나의 공유 CXL 메모리 어플라이언스로 제공하는 것이다. 에뮬레이션과 서빙 시뮬레이션에서는 호스트당 128 GB/s, 평균 350 ns의 메모리 접근 특성을 적용했을 때 2 TB 호스트 DRAM에서 발생하는 KV 캐시 축출 절벽을 피하고 평균 TTFT와 접두사 캐시 히트율을 유지했다.

## 이 논문이 풀려는 문제

### KV 캐시는 연산 절약 장치인 동시에 새로운 메모리 병목이다

반복되는 접두사나 이전 대화 턴의 KV 캐시를 재사용하면 이미 처리한 토큰을 다시 Prefill할 필요가 없다. 문제는 컨텍스트가 길어질수록 캐시 자체가 매우 커진다는 점이다.

논문이 제시한 LLaMA 70B 예시에서는 BF16, 80개 레이어, 8개 KV 헤드, 128차원 헤드 크기일 때 토큰당 약 328 KB가 필요하다. 10~15회의 대화 뒤 전체 컨텍스트가 10,000토큰을 넘으면 사용자 한 명의 KV 캐시가 약 3.3 GB에 이른다. 논문은 Meta의 35억 일일 활성 사용자와 130만 GPU라는 조건을 대입하면 전체 사용자를 서빙하기 위해 GPU당 8.9 TB가 필요하다고 계산한다.

GPU HBM만으로 이 용량을 감당하기 어렵기 때문에 NVIDIA Dynamo, vLLM의 LMCache, SGLang의 HiCache 같은 시스템은 GPU HBM, 호스트 DRAM, 로컬 SSD, NAS를 계층적으로 사용한다. 그러나 계층을 하나 추가한다고 해서 병목이 사라지는 것은 아니다.

- 호스트 DRAM은 서버당 최대 2 TB라는 용량 제약 때문에 동시 사용자 수가 늘면 결국 캐시를 축출해야 한다.
- SSD는 CPU-to-GPU 경로보다 대역폭이 10~15배 낮다. 작은 컨텍스트에서는 저장된 KV를 읽는 것보다 GPU에서 다시 계산하는 편이 빠를 수도 있다.
- 외부 스토리지에 KV를 저장한 뒤 다른 워커가 다시 읽는 구조는 저장과 로드라는 두 번의 데이터 이동을 요구한다.

따라서 필요한 것은 단순히 더 큰 저장 공간이 아니다. GPU가 재연산을 피할 만큼 빠르면서, 여러 호스트가 공유할 수 있고, 용량을 늘려도 네트워크나 스위치가 새 병목이 되지 않는 메모리 계층이다.

### 분리형 추론에서는 KV 이동 경로가 TTFT를 지배한다

Prefill과 Decode를 서로 다른 워커에서 실행하는 분리형 추론(disaggregated inference)은 각 단계의 자원을 독립적으로 구성할 수 있다는 장점이 있다. 반면 Prefill 워커가 만든 KV 텐서를 Decode 워커로 넘겨야 한다. 컨텍스트가 길어지면 이 전송 지연이 Time-to-First-Token(TTFT)의 주요 구성 요소가 된다.

CPU 구동 RDMA에서는 데이터가 다음과 같이 이동한다.

```text
Prefill GPU HBM
  → 송신 호스트 DRAM 바운스 버퍼
  → 송신 NIC
  → 수신 NIC
  → 수신 호스트 DRAM 바운스 버퍼
  → Decode GPU HBM
```

이 경로에는 중간 DRAM 복사 2회, PCIe 교차 4회, CPU 직렬화 지점 3개가 포함된다. 논문이 제시한 추가 지연은 20~50 µs이며, 네트워크 경합이 생기면 지연 분산도 커진다.

GPUDirect RDMA는 PCIe BAR1 매핑을 이용해 NIC가 GPU 메모리를 직접 읽고 쓰므로 호스트 DRAM 바운스 버퍼를 제거한다. 지연은 2~15 µs로 줄어들지만, 여러 플랫폼에서 BAR 읽기 처리량이 3.4~7 GB/s로 제한되는 읽기·쓰기 비대칭이 있다. GPU와 NIC가 같은 PCIe 루트 복합체를 공유해야 한다는 배치 제약도 남는다.

두 RDMA 방식에는 더 근본적인 공통점이 있다. KV가 특정 워커에서 다른 워커로 전달되는 P2P 객체이므로, 제3의 워커가 같은 KV 블록을 재사용하려면 다시 전송해야 한다. 스케줄러도 어느 노드가 어떤 KV를 보유하는지 별도의 지역성 인덱스로 관리해야 한다.

계층형 스토리지 오프로드는 KV를 외부 저장소에 두어 이 결합을 완화하지만, 생산자의 저장과 소비자의 로드가 모두 필요하다. 결국 스토리지 대역폭과 네트워크 RPC 지연의 영향을 받는다.

### 전기적 CXL 풀도 규모가 커지면 스위치가 문제가 된다

CXL Type-3 장치를 이용한 공유 메모리 풀은 KV를 한 번 기록한 뒤 여러 호스트가 읽는 write-once-read-many 구조에 잘 맞는다. TraCT와 Beluga가 이 접근의 예로 제시된다. 하지만 전기적 CXL을 여러 호스트와 많은 메모리 모듈로 확장하면 세 가지 제약이 나타난다.

첫째, CXL 스위치는 홉마다 70~500 ns의 지연을 더한다. 포트 경합이 생기면 중재 지연도 변하며, 계층형 스위치 토폴로지에서는 이 비용이 누적된다.

둘째, 구리 케이블은 도달 거리가 수 미터, 구체적으로 2 m 이하로 제한된다. 더 멀리 연결하려면 리타이머가 필요하고 랙 단위 분리도 어렵다. 논문이 비교한 TraCT는 단일 섀시, Beluga는 같은 섀시 안의 CXL 2.0 스위치에 국한된다.

셋째, 스위치 전력은 포트 수와 신호 속도에 따라 초선형으로 증가한다. 32 TB 풀을 수백 개 모듈과 다단계 스위치 계층으로 구성하면 전력뿐 아니라 열 밀도도 문제가 된다.

이 논문은 메모리 프로토콜로서의 CXL을 버리지 않는다. 대신 CXL 트랜잭션을 운반하는 중간 패브릭을 전기적 스위치 계층에서 패시브 광 연결로 바꾼다.

## 핵심 아이디어

논문의 핵심은 능동 스위치가 수행하던 동적 경로 선택을 없애고, 필요한 모든 호스트-모듈 연결을 물리적인 전용 광학 경로로 미리 구성하는 것이다. 16개의 호스트 포트와 16개의 메모리 모듈 사이에 16×16 패시브 광 섬유 셔플을 두면 총 256개의 경로가 만들어진다. 중간 스위치의 버퍼링이나 중재 없이 각 호스트가 모든 메모리 모듈에 도달할 수 있는 풀-메시(full-mesh) 토폴로지다.

어플라이언스는 16개의 Photonic Fabric Memory Module로 구성되며, 전체적으로 32 TB DDR5와 1.125 TB HBM3E를 제공한다. HBM3E는 라이트스루(write-through) 캐시 또는 추가 풀링 메모리로 구성할 수 있다. 전체 광 스위칭 대역폭은 115 Tbps이고 각 포트의 양방향 광 대역폭은 7.2 Tbps다. 호스트가 실제로 사용할 수 있는 단방향 대역폭은 PCIe Gen6 경로의 제약 때문에 128 GB/s로 제한된다.

이 설계는 광 링크만 추가한 CXL 시스템이 아니다. 다음 세 층을 함께 맞춘 결과다.

1. 패시브 광 섬유 셔플이 스위치 지연과 경합을 제거한다.
2. 각 메모리 모듈의 HBM3E 캐시와 주소 인터리빙이 광 링크를 계속 채울 수 있게 한다.
3. DAX 매핑, 오프셋 기반 주소, 랑데부 프로토콜이 여러 호스트에서 KV 데이터를 안전하게 공유하게 한다.

_그림 2. 16×16 패시브 파이버 셔플이 256개의 전용 경로를 형성한다. 논문의 확장 전략은 능동 스위치를 더 쌓는 것이 아니라 중간 중재 요소 자체를 제거하는 데 있다._

## 하드웨어 구조

### PF Memory Module

각 PF Memory Module은 PCIe Gen6 인터페이스를 사용하는 CXL 3.1 Type-3 장치이며, 2.5D 전광(electro-optical) System-in-Package로 구성된다. 모듈 하나에는 다음 요소가 들어간다.

- 7.2 Tbps Photonic Fabric 광 연결
- 스택당 36 GB인 HBM3E 스택 2개
- 최대 2 TB DDR5를 지원하는 DDR5 인터페이스 8개
- 광학 PIC 인터포저와 FAU(Fiber Array Unit)
- CXL 및 광 패킷 처리를 위한 전자 ASIC

HBM3E는 광 링크의 최대 대역폭보다 높은 대역폭으로 프로비저닝된 직접 매핑(direct-mapped) 캐시로 동작한다. 이 헤드룸은 DDR5만으로 처리하기 어려운 무작위 접근에서도 광 링크가 메모리 측 병목 때문에 비지 않도록 하는 장치다.

광 변조기에는 GeSi EAM(Electro-Absorption Modulator)을 사용한다. 논문이 비교하는 MRR은 열 민감도가 높아 능동 파장 튜닝 전력이 필요하고, MZM은 길이가 밀리미터 단위다. GeSi EAM은 100 μm 미만의 풋프린트와 열적 안정성을 제공한다.

전자 회로와 광 회로는 같은 공정에 억지로 맞추지 않는다. 4nm/5nm CMOS 공정의 전자 ASIC과 광학에 최적화된 PIC를 따로 제작한 뒤 2.5D/3D 어셈블리로 결합한다. 이 구성은 Long-reach SerDes용 DSP 없이 광 연결을 구현하려는 선택이다. 광학 조명은 외부 레이저 소스(External Laser Source, ELS)가 제공한다.

### PF-NIC

호스트에는 PCIe Gen6/CXL 3.1 어댑터인 PF-NIC이 연결된다. PF-NIC은 외부 DDR5와 HBM을 제외하면 PF Memory Module과 유사하게 PF ASIC과 광 연결부를 포함한다.

PF-NIC은 호스트 쪽 CXL 링크를 종단하고, 들어온 flit에서 CXL.mem 트랜잭션 필드를 추출한다. 그 트랜잭션은 광 패킷으로 변환되어 목적지 PF Memory Module로 전달된다. 논문은 별도 카드 대신 PF Chiplet을 AI 가속기에 Co-packaging하는 대안도 제시한다.

여기서 CXL은 호스트가 보는 메모리 의미론을 담당하고, Photonic Fabric은 트랜잭션이 이동하는 물리적 경로를 담당한다. 소프트웨어가 광 경로 자체를 다루는 구조는 아니다.

### 주소 인터리빙과 HBM3E의 역할

높은 총 광 대역폭이 있어도 요청이 일부 DDR 채널이나 HBM 채널에 몰리면 실제 처리량은 낮아진다. PF Memory Module은 설정 가능한 PF 주소 비트를 이용해 다음 매핑을 제어한다.

- DDR 채널
- HBM 의사 채널 및 채널
- HBM 스택

논문은 모든 채널로 트래픽을 균등 분산하는 고정 인터리브 설정 파라미터를 찾아 적용했다. 그 결과 32 B부터 1 KB까지의 전송 크기, 순차 및 랜덤 접근 패턴 모두에서 16개 PF Memory Module 포트가 100% 대역폭 활용률을 기록했다. 프로토콜과 메타데이터 오버헤드를 제외한 지속 대역폭은 포트당 25.6 GB/s였다.

다만 이것은 최적화 전후를 비교한 결과는 아니다. 원문은 고정 설정을 적용한 상태의 측정만 제시하며, 적용 전의 채널 불균형이나 각 설정 후보의 성능 차이는 보고하지 않는다. 따라서 인터리빙이 중요하다는 것은 확인할 수 있지만, 제시된 결과만으로 탐색 절차나 민감도를 재구성할 수는 없다.

## KV 캐시 재사용의 수학적 조건

### 재연산보다 메모리 검색이 빨라야 한다

논문은 dense model에서 호스트 메모리 KV 검색의 이득을 Eq. (1)로 근사한다.

$$
S = \frac{T_{\text{compute}}}{T_{\text{memory}}}
\tag{1}
$$

$T_{\text{compute}}$는 캐시가 없을 때 GPU가 전체 KV를 다시 계산하는 시간이고, $T_{\text{memory}}$는 호스트 DRAM에 저장된 KV를 불러오는 시간이다.

- $S>1$이면 캐시를 읽는 편이 재연산보다 빠르다.
- $S=1$이면 두 경로의 시간이 같다.
- $S<1$이면 캐시 계층이 오히려 느리다.

SSD의 경우에는 분모를 $T_{\text{disk}}$로 바꾼다. 이 정의는 “캐시가 있는가”보다 “캐시를 가져오는 비용이 절약한 계산보다 작은가”가 중요하다는 것을 보여준다. 실제로 LLaMA-8B의 디스크 결과에는 1보다 작은 구간이 존재한다.

### Prefill 재연산 비용

Eq. (2)는 dense model의 Prefill 재연산 시간을 다음과 같이 근사한다.

$$
T_{\text{compute}}
=
\frac{
b\left(2sP + 2s^2 n_{\text{head}}h_{\text{head}}L\right)
}{
\text{MFU}
}
\tag{2}
$$

각 항의 역할은 다음과 같다.

- $b$는 배치 크기다. 배치가 늘면 처리해야 할 전체 작업량도 비례해 증가한다.
- $2sP$는 프롬프트 길이 $s$와 파라미터 수 $P$에 비례하는 항이다.
- $2s^2n_{\text{head}}h_{\text{head}}L$은 시퀀스 길이의 제곱에 비례하는 어텐션 항이다.
- $n_{\text{head}}$, $h_{\text{head}}$, $L$은 각각 어텐션 헤드 수, 헤드 차원, 트랜스포머 레이어 수다.
- MFU는 분모에 놓여 계산 자원 활용 특성을 반영하지만, 추출본과 원문의 수식 설명에는 이 기호의 추가 정의가 제시되지 않았다.

짧은 프롬프트에서는 $s$에 선형인 항이 상대적으로 중요하지만, $s$가 커지면 $s^2$인 어텐션 항이 빠르게 커진다. 논문은 405B 모델에서 약 20,000토큰일 때 어텐션 FLOPs와 피드포워드 FLOPs가 같아지고, 그 이후에는 어텐션이 지배한다고 설명한다.

이 지점부터는 KV를 읽는 비용보다 재연산 비용이 더 빠르게 증가할 수 있다. 긴 컨텍스트에서 캐시 검색 속도 향상비가 커지는 이유다.

### KV 로드 비용

호스트 메모리에서 KV를 읽는 시간은 Eq. (3)처럼 모델링된다.

$$
T_{\text{memory}} = K + bs\alpha
\tag{3}
$$

$K$는 캐시 룩업, 메모리 할당, PCIe 전송 초기화처럼 전송량과 직접 비례하지 않는 고정 오버헤드다. $\alpha$는 토큰당 로딩 비용이며, $bs\alpha$는 배치와 프롬프트 길이에 비례하는 데이터 이동 비용이다.

Eq. (2)와 Eq. (3)을 Eq. (1)에 대입하면 다음 구조를 얻는다.

$$
S
=
\frac{
b\left(2sP+2s^2n_{\text{head}}h_{\text{head}}L\right)
}{
\text{MFU}\left(K+bs\alpha\right)
}
$$

분자는 $s^2$ 항을 포함하지만 분모는 $s$에 선형이다. 따라서 다른 조건이 유지되고 어텐션 항이 지배하기 시작하면 $S$가 프롬프트 길이에 따라 초선형으로 증가할 수 있다.

여기서 각 항을 줄였을 때의 효과도 구분해야 한다.

- $K$를 줄이면 특히 작은 전송의 손해가 줄어든다.
- $\alpha$를 줄이면 긴 컨텍스트에서의 전송 시간이 개선된다.
- 메모리 용량을 늘리는 것은 한 번의 로드 시간을 직접 줄이지 않지만, 필요한 KV가 축출되어 $T_{\text{compute}}$ 경로로 돌아가는 상황을 막는다.
- 광 패브릭의 낮은 지연과 높은 대역폭은 $T_{\text{memory}}$를 낮추는 쪽에 작용한다.

### CXL 왕복 지연의 분해

하드웨어 경로의 왕복 지연은 Eq. (4)로 나눈다.

$$
T
=
T_{\text{CXL\_req}}
+
T_{\text{mem}}
+
T_{\text{CXL\_resp}}
\tag{4}
$$

- $T_{\text{CXL\_req}}$는 CXL 컨트롤러 안에서 요청을 처리하는 시간이다.
- $T_{\text{mem}}$은 CXL 프로토콜 인터페이스에서 메모리 서브시스템으로 전달되고 응답이 돌아올 때까지의 전파 시간이다.
- $T_{\text{CXL\_resp}}$는 CXL 컨트롤러가 응답을 처리하는 시간이다.

Idle 조건에서 컨트롤러 지연 추정치는 요청 24 ns, 응답 47 ns였다. 메모리 접근 전파 시간은 쓰기 153 ns, 읽기 212 ns였으므로 전체 왕복 시간은 다음과 같다.

$$
T_{\text{write}} = 24 + 153 + 47 = 224\ \text{ns}
$$

$$
T_{\text{read}} = 24 + 212 + 47 = 283\ \text{ns}
$$

읽기는 데이터를 반환해야 하므로 측정된 $T_{\text{mem}}$이 쓰기보다 크다. 반복 측정 변동은 1~2 ns 이하로 보고됐다.

QEMU 안에서 요청이 생성된 시점부터 Root Complex에 도착할 때까지의 지연은 관측할 수 없었기 때문에 Eq. (4)의 측정에 포함되지 않았다. 따라서 이 수치는 전체 애플리케이션 호출 지연이 아니라 관측 가능한 CXL 및 메모리 경로의 지연으로 읽어야 한다.

원문 p.7 본문에는 이 지연 구성 요소를 “Eq. (2)”로 지칭한 부분이 있지만, 식의 내용상 Eq. (4)를 가리키는 것으로 해석된다.

## 소프트웨어에서 공유 메모리를 안전하게 쓰는 방법

### DAX로 명시적인 배치 권한을 유지한다

부팅 과정에서는 PCIe DVSEC으로 CXL 지원을 확인하고 HDM 레지스터를 읽으며, ACPI CEDT의 CHBS와 CFMWS를 구성한다. Linux CXL 서브시스템의 `cxl_acpi`, `cxl_pci`, `cxl_mem`이 HDM 디코더를 설정하고 장치를 `/dev/daxN.M` 형태의 Device-DAX로 노출한다.

논문은 CXL 메모리를 시스템 RAM으로 편입하지 않고 DAX 모드로 유지한다. 운영체제의 일반 메모리 정책에 맡기는 대신, 추론 런타임이 KV 블록의 배치를 직접 관리하기 위해서다.

에뮬레이션 벤치마크에서도 같은 이유로 CXL 메모리를 NUMA 노드로 노출하지 않았다. NUMA 메모리로 사용하면 페이지 테이블 관리와 커널 메모리 작업에서 부수적인 트랜잭션이 발생해 애플리케이션이 만든 읽기·쓰기 패턴을 가릴 수 있다. 직접 `mmap()`한 가상 주소 범위를 사용함으로써 VirtuaLab 프로토콜 분석기에서 더 정제된 트랜잭션 추적을 얻었다.

### 공유 데이터 구조에는 포인터가 아니라 오프셋을 저장한다

각 호스트의 추론 프로세스는 DAX 장치를 `mmap()`으로 매핑하고, 그 영역을 `cudaHostRegister()`로 핀 고정해 GPU DMA가 접근할 수 있게 한다. 그러나 같은 물리적 공유 영역이라도 호스트마다 가상 주소가 다를 수 있다. 한 프로세스에서 유효한 포인터 값을 공유 메타데이터에 기록하면 다른 프로세스에서는 잘못된 주소가 된다.

논문은 모든 공유 데이터 구조에서 영역 베이스 기준 오프셋을 사용한다.

```python
# 각 프로세스의 로컬 가상 주소. 호스트마다 값이 다를 수 있다.
region_base = mmap_dax_region()                 # (shared_region_bytes,)
register_for_gpu_dma(region_base)

# 공유 인덱스에는 포인터 대신 정수 오프셋을 기록한다.
entry.offset = kv_block_offset                  # scalar
entry.length = kv_block_bytes                   # scalar

# 소비자는 자신의 로컬 base와 공유 offset으로 주소를 복원한다.
local_address = region_base + entry.offset
```

여기서 `region_base`는 각 프로세스에만 의미가 있고, `offset`과 `length`만 호스트 사이에서 공유된다. KV 텐서의 논리적 shape는 모델과 배치에 따라 달라질 수 있으므로 공유 인덱스에는 해당 블록을 복원할 메타데이터가 함께 필요하지만, 원문에서 그 구체적인 레이아웃은 제시되지 않는다.

### 랑데부가 데이터보다 먼저 보이면 안 된다

Prefill 워커와 Decode 워커의 데이터 흐름은 대칭이 아니다. Prefill은 KV 블록을 생산하고 공개하며, Decode는 준비 완료 신호를 확인한 뒤 읽는다.

```python
def prefill_publish(kv_gpu, shared_base, entry):
    # kv_gpu: Prefill이 생성한 KV 블록
    # 논리 shape 예: (layers, kv_heads, tokens, head_dim)
    dst = shared_base + entry.offset

    dma_copy_gpu_to_shared_async(
        dst, kv_gpu, entry.length
    )

    wait_for_producer_dma_completion()

    # 데이터 도착이 보장된 뒤에만 공개한다.
    rendezvous_publish(
        key=entry.key,
        offset=entry.offset,
        length=entry.length,
    )


def decode_consume(shared_base, key, kv_gpu):
    record = rendezvous_wait(key)

    src = shared_base + record.offset
    dma_copy_shared_to_gpu_async(
        kv_gpu, src, record.length
    )

    wait_for_consumer_dma_completion()
    return kv_gpu
```

핵심 순서는 `KV DMA 완료 → 랑데부 신호 발행`이다. 신호를 먼저 기록하면 Decode 워커가 아직 완전히 도착하지 않은 블록을 읽을 수 있다.

모든 메타데이터 쓰기마다 캐시 라인 플러시와 펜스를 수행하는 방식은 순서를 보장할 수 있지만 오버헤드가 크다. 이 설계는 메모리 안의 지정된 조정 구조에 랑데부 신호를 발행해 노드 간 공개 순서를 보장한다. 벌크 KV 데이터는 생산자 측 DMA 완료 이벤트를 통해 신호 발행 전에 어플라이언스에 도착했음이 보장되므로, 논문의 설계에서는 CPU가 KV 본문 전체에 대해 별도의 일관성 작업을 수행할 필요가 없다.

구현에서 특히 조심할 부분은 다음과 같다.

- 공유 구조에 프로세스 로컬 포인터를 기록하지 않는다.
- DMA 완료 확인과 랑데부 공개의 순서를 바꾸지 않는다.
- 소비자는 랑데부를 관측하기 전에 KV 데이터에 접근하지 않는다.
- DAX 영역의 크기와 `offset + length` 경계를 검사한다.
- KV 블록의 논리 shape와 실제 byte length를 혼동하지 않는다.
- 호스트 DRAM을 거치는 CPU 복사 경로를 추가하면 무복사 설계의 이점을 잃는다.

이 논문은 모델 학습 알고리즘을 제안하지 않으므로 학습 루프는 없다. 모델 실행 측면에서 구분해야 하는 루프는 Prefill 생산 경로와 Decode 소비 경로다. Prefill은 공유 풀에 KV를 저장하고, Decode는 재사용 가능한 블록을 찾아 GPU로 가져온다.

## 기존 추론 프레임워크와의 통합 경로

논문은 PF Memory Appliance를 별도의 추론 엔진으로 만들기보다 기존 프레임워크의 저장 계층이나 전송 백엔드로 연결하는 방식을 제시한다. 다만 각 통합 경로의 구현 상태를 구분해서 읽어야 한다.

- vLLM에는 GPU와 어플라이언스 사이에서 `cudaMemcpyAsync` DMA를 실행하고 공유 인덱스를 조회하는 `store()`와 `load()` 메서드를 갖는 CXL KV 커넥터를 향후 구현할 예정이다.
- SGLang에서는 어플라이언스 영역에 `get`, `exist`, `set` 인터페이스를 구현하고, GPU HBM과 호스트 DRAM 사이의 HiCache 스토리지 백엔드로 등록할 수 있다.
- NVIDIA Dynamo에는 NIXL South-Bound API의 `registerMem`, `connect`, `prepXfer`, `postXfer`, `checkXfer` 등을 구현하는 백엔드 플러그인으로 통합할 수 있다. NIXL의 자동 백엔드 선택을 통하면 vLLM, SGLang, TensorRT-LLM, LMCache 등 NIXL 통합 엔진으로 지원을 확장할 수 있다는 구상이다.
- PyTorch에서는 지연 시간에 덜 민감한 텐서를 `mbind(MPOL_BIND)` 기반 NUMA-aware CPU 할당자로 배치하거나, 직접 GPU DMA를 위한 CUDAHost 할당자로 접근할 수 있다.

현재 PyTorch의 메모리 모델은 온칩 DRAM 디바이스 메모리와 시스템 호스트 메모리로 제한되며, 이기종 메모리 계층을 직접 표현하지 못한다. 논문은 `torch.device`에 네이티브 메모리 유형을 추가해 PF Memory Appliance를 새 메모리 유형으로 표현하는 PyTorch RFC #153745가 진행 중이라고 설명한다.

## 실험 구성

### 반복 요청 벤치마크

동일한 요청을 반복해 100% 캐시 히트 조건을 만들고, GPU 재연산과 호스트 DRAM 및 로컬 SSD 검색을 비교했다. 배치 크기는 $\{1,2,8,16,32\}$이고 기본 프롬프트 길이는 1K~100K토큰이다. Maverick은 최대 1M, Scout은 최대 4M토큰까지 평가했다.

사용한 시스템은 다음과 같다.

- A100 환경: NVIDIA A100 80 GB HBM2e 1개, 듀얼 소켓 Intel Xeon, PCIe 4.0 ×16의 단방향 약 32 GB/s, 시스템 DRAM 512 GB, 로컬 디스크 7 TB
- H100/H200 환경: Runpod 인스턴스, PCIe 5.0 ×16의 단방향 약 64 GB/s, 최대 H100 또는 H200 8개, 호스트 DRAM 최대 2 TB
- 모델: LLaMA-8B, LLaMA-70B, LLaMA-405B, LLaMA Maverick, Scout
- 병렬 구성: 70B는 H200 2개와 TP=2, 405B·Maverick·Scout은 H200 8개와 TP=8, BF16
- 프레임워크: LMCache를 활성화한 vLLM

### 하드웨어 에뮬레이션

하드웨어 평가는 Siemens Veloce Strato-M 에뮬레이터에서 수행했다. 플랫폼은 Crystal 가속기 칩, 4개 용량 모듈, 64개 ABV로 구성된다. PF-NIC과 PF Memory Module 2개 SoC 인스턴스를 16개 광 링크로 연결했고, Siemens VirtuaLab 트랜잭터가 PCIe/CXL Root Complex를 모델링했다. 게스트 Linux는 QEMU에서 실행했으며 C/C++ 벤치마크가 매핑된 CXL 메모리에 읽기와 쓰기 요청을 생성했다.

프로토콜 분석에서는 쓰기가 CXL RwD(Read with Data) 뒤에 CXL NDR(No Data Response) 확인 응답을 받는 형태로 관찰됐다. 읽기는 CXL REQ(Request) 뒤에 CXL DRS(Data Response)가 돌아오는 형태였다.

Idle 조건은 단일 쓰기 뒤에 단일 읽기를 발행한다. Loaded 조건에서는 캐시 효과를 피하도록 주소를 64바이트씩 옮기며 읽기와 쓰기를 연속 발행한다. 이 요청열은 PF-NIC의 CXL 크레딧 교환 한도를 넘어 프로토콜 파이프라인에 부하와 경합을 만든다.

### 엔드투엔드 서빙 시뮬레이션

서빙 평가는 LLMServingSim을 사용했다. 8×H200에서 수집한 LLaMA 405B 프로파일링 데이터를 사용하며, 해당 프레임워크의 실제 서빙 배포 대비 평균 오차는 1.9%다. 여기에 에뮬레이션으로 얻은 호스트당 128 GB/s와 평균 350 ns를 PF Memory Appliance 파라미터로 입력했다.

워크로드는 50~300개의 멀티턴 대화다. 각 대화는 10턴이며, 턴마다 입력 5,120토큰과 출력 500토큰을 사용한다. 모든 대화는 512토큰 시스템 프롬프트 접두사를 공유한다. 비교 대상은 LRU 축출을 사용하는 2 TB 호스트 DRAM 기반 8×H200 DGX 시스템이다.

## 실험에서 확인한 것

### 모델과 컨텍스트에 따라 메모리 검색의 이득이 크게 달라진다

반복 요청 벤치마크의 전체 범위는 다음과 같다.

| Model | Platform | Host Memory | Disk Storage |
|---|---:|---:|---:|
| LLaMA-8B | 1×A100 | 3.3×–27.5× | 0.53×–1.72× |
| LLaMA-8B | 1×H100 | 1.9×–11.8× | 미측정 |
| LLaMA-8B | 1×H200 | 1.5×–17.2× | 0.38×–1.27× |
| LLaMA-70B | 2×H200 | 2.7×–51.4× | 미측정 |
| LLaMA-405B | 8×H200 | 2.7×–100.0× | 2.1×–9.7× |
| Maverick | 8×H200 | 2.7×–23.1× | 미측정 |
| Scout | 8×H200 | 2.6×–54.6× | 미측정 |

LLaMA-405B는 호스트 메모리에서 최대 100×의 속도 향상을 보였다. 100K토큰에서 KV 캐시 크기는 48 GB였고, 비교를 위해 제시된 8B 모델의 크기는 12 GB였다. 8개 GPU 전체의 집적 유효 대역폭은 165 GB/s였다. 디스크에서도 2.1×–9.7×로 재연산보다 빨랐다.

반면 LLaMA-8B의 디스크 결과는 캐시가 항상 유리하지 않다는 점을 보여준다. A100 디스크 검색은 50K토큰을 넘어야 속도 향상이 나타났고, 20K토큰 미만에서는 0.38×–0.53×로 재연산보다 느렸다. H200에서의 디스크 범위도 0.38×–1.27×다. 고정 오버헤드와 낮은 저장장치 대역폭을 감당할 만큼 절약되는 연산이 크지 않으면 $S<1$이 될 수 있다는 Eq. (1)의 사례다.

Maverick과 Scout의 최대 속도 향상은 각각 23.1×와 54.6×다. 405B dense 모델의 100×보다 낮은 이유로 논문은 희소 전문가 활성화가 기본 연산 요구량을 낮춘다는 점을 든다. 캐시가 줄이는 재연산 자체가 작아지면 같은 메모리 계층에서도 상대적 이득이 줄어든다.

### 광 링크만 빠른 것이 아니라 메모리 측에서도 링크를 채웠다

에뮬레이션에서는 32 B~1 KB의 모든 전송 크기와 순차·랜덤 패턴에 걸쳐 16개 포트가 100% 대역폭 활용률을 기록했다. 프로토콜 및 메타데이터 오버헤드를 뺀 지속 대역폭은 포트당 25.6 GB/s였다.

이 결과는 패시브 셔플의 총 광 대역폭만으로 설명되지 않는다. 고정 주소 인터리빙이 요청을 여러 채널에 분산하고, 광 링크보다 높은 대역폭으로 프로비저닝한 HBM3E 직접 매핑 캐시가 랜덤 접근에서도 메모리 측 처리량을 공급한다. 단일 호스트의 단방향 처리량은 PCIe Gen6에 의해 128 GB/s로 제한되므로, 어플라이언스의 총 115 Tbps 광 대역폭과 호스트가 관측하는 대역폭은 같은 수치가 아니다.

### 스위치 제거는 지연과 지연 분산을 함께 줄인다

Idle 조건의 왕복 지연은 쓰기 224 ns, 읽기 283 ns였다. Loaded 조건에서 쓰기는 주로 210~250 ns, 읽기는 275~290 ns에 모였다. 읽기의 꼬리 지연은 완료 경로 경합과 데이터 반환 종속성으로 인해 320 ns까지 늘어났다.

비교 대상인 Beluga의 CXL 2.0 스위치 기반 풀은 Intel MLC의 64 B 접근에서 800~900 ns였다. PF Memory Appliance는 평균 350 ns를 기록해 50% 이상 낮았다. 패시브 셔플은 중간 스위치의 홉 지연뿐 아니라 부하에 따라 변하는 중재 지연도 제거한다.

### 큰 풀의 효과는 평균 대역폭보다 축출 절벽에서 분명해진다

32 TB PF Memory Appliance에서는 동시 대화가 50개에서 300개로 증가해도 평균 TTFT가 2,690 ms로 유지됐다. 접두사 캐시 히트율도 82%였고, 캐시 축출은 발생하지 않았다.

2 TB 호스트 DRAM은 대화 100개에서 LRU 축출이 시작되며 평균 TTFT가 8,156 ms로 증가했다. 이는 PF 구성의 3배다. 대화 300개에서는 접두사 캐시 히트율이 82%에서 6.35%로 떨어졌고, PF 구성과의 TTFT 격차는 6.6배까지 벌어졌다.

이 결과에서 읽어야 할 것은 “32 TB가 2 TB보다 16배 크다”는 용량 차이만이 아니다. 캐시가 작업 집합을 담는 동안에는 성능이 안정적이지만, 용량 한계를 넘는 순간 LRU 축출이 재연산을 연쇄적으로 유발해 TTFT가 비선형적으로 악화된다. 논문은 이를 eviction cliff로 설명한다. 단일 8×H200 시스템 기준으로 PF 구성은 2 TB 호스트 DRAM보다 64배 많은 동시 멀티턴 대화 또는 롱컨텍스트 세션을 지원할 수 있다고 보고한다.

## 무엇이 성능을 만들었나

이 논문에는 구성 요소를 하나씩 제거한 전형적인 ablation 표가 없다. 대신 주소 배치, 메모리 계층, 패브릭, 총용량이 각각 어떤 병목을 해소하는지 별도의 측정으로 확인한다.

### 주소 인터리빙

고정 인터리브 설정을 적용한 결과, 32 B~1 KB 전송과 순차·랜덤 접근 모두에서 16개 포트가 100% 활용됐다. 이 결과는 주소 비트 매핑이 채널 병렬성을 실제 처리량으로 바꾸는 데 필요하다는 근거다.

다만 최적화 전후 수치가 없으므로 인터리빙을 제거했을 때 정확히 얼마나 나빠지는지는 알 수 없다. 보고된 결과는 선택한 고정 설정이 평가 범위에서 균형을 유지했다는 사실까지 뒷받침한다.

### HBM3E 대역폭 헤드룸

HBM3E를 광 링크보다 높은 대역폭으로 프로비저닝하고 직접 매핑 캐시로 사용함으로써 랜덤 접근에서도 링크 포화 상태를 유지했다. DDR5 용량은 큰 작업 집합을 담고, HBM3E는 접근 대역폭을 보완한다. 즉 32 TB라는 용량과 높은 랜덤 접근 처리량은 서로 다른 계층이 담당한다.

### 패시브 셔플

전기적 스위치를 제거한 PF 구성은 Beluga의 800~900 ns와 비교해 평균 350 ns를 기록했다. 이 비교는 패시브 광 섬유 셔플이 단순한 배선 방식이 아니라 메모리 접근 임계 경로에서 능동 중재 요소를 제거하는 설계임을 보여준다.

### 32 TB 용량

2 TB 베이스라인은 대화 100개에서 TTFT가 8,156 ms로 늘었고, 300개에서는 히트율이 6.35%까지 떨어지며 PF 대비 TTFT 격차가 6.6배가 됐다. 32 TB 구성은 같은 범위에서 히트율 82%와 평균 TTFT 2,690 ms를 유지했다.

여기서는 더 빠른 링크보다 “필요한 KV가 남아 있는가”가 먼저 성능을 결정한다. 캐시 미스가 발생하면 시스템은 단순히 느린 계층을 한 번 읽는 것이 아니라 Eq. (2)의 Prefill 재연산 비용을 다시 지불하기 때문이다.

## 비용과 트레이드오프

### 이 설계가 줄이는 비용

PF Memory Appliance는 세 종류의 비용을 줄인다.

- CPU 구동 RDMA의 호스트 DRAM 바운스 복사와 CPU 직렬화
- P2P KV 전달에서 같은 블록을 여러 워커로 반복 전송하는 비용
- 전기적 CXL 스위치의 홉 지연과 중재 지연

공유 풀에 KV를 한 번 기록하고 여러 Decode 워커가 읽게 하면 워커별 복제 전송을 줄일 수 있다. 오프셋 기반 인덱스는 공유 주소 공간을 프로세스마다 다른 가상 주소에 매핑할 수 있게 하고, 랑데부 프로토콜은 메타데이터 쓰기마다 캐시 라인 플러시와 펜스를 반복하는 비용을 피한다.

### 새로 지불하는 비용

스위치를 제거했다고 해서 하드웨어 복잡성이 사라지는 것은 아니다. 16×16 풀-메시에는 256개의 전용 광학 경로가 필요하며, 각 메모리 모듈에는 광학 PIC, FAU, 전자 ASIC, HBM3E와 DDR5 인터페이스가 들어간다. 외부 레이저 소스도 필요하다.

메모리 측에서는 32 TB DDR5뿐 아니라 총 1.125 TB HBM3E를 배치한다. HBM3E를 광 링크보다 높은 대역폭으로 프로비저닝한 것은 성능을 위한 의도적인 헤드룸이며, 그 비용 대비 편익은 논문에서 분석되지 않았다.

소프트웨어도 기존 NUMA 메모리처럼 투명하게 사용할 수 있는 단계는 아니다. DAX 매핑, GPU 등록, 공유 인덱스, 오프셋 주소, DMA 완료 순서, 랑데부 공개 규칙을 런타임이 구현해야 한다. vLLM 커넥터는 향후 구현 예정이고, SGLang과 Dynamo 통합도 가능한 경로로 제시된 상태다.

### 경량화와 효율 관점

이 논문은 모델 파라미터를 줄이거나 KV 표현을 압축하는 경량화 방법이 아니다. 동일한 KV를 더 큰 공유 계층에 보존하고 빠르게 재사용해 재연산과 복제 전송을 줄이는 시스템 효율화다.

그 차이는 중요하다. KV 자체의 크기가 줄어들지 않으므로 모델과 컨텍스트가 커질수록 총용량 요구량은 계속 증가한다. 이 아키텍처는 그 증가를 32 TB 풀로 수용하지만, 더 큰 규모에서는 현재의 16호스트·16모듈 풀-메시를 어떻게 확장할지 논문의 결과만으로는 알 수 없다.

추론 지연 측면에서도 모든 요청이 빨라지는 것은 아니다. 반복 요청 실험에서 작은 모델과 SSD 조합은 $S<1$이었다. 메모리 계층을 추가할 가치는 캐시 히트율, 컨텍스트 길이, 모델의 재연산 비용, 실제 전송 대역폭을 함께 고려해야 한다.

### 일반화 가능성

논문의 실험은 dense 모델과 MoE 모델 모두에서 호스트 메모리 검색의 이득을 측정했다. Maverick과 Scout에서도 이득은 있었지만 dense 405B보다 최대 속도 향상이 작았다. 이는 같은 메모리 시스템이라도 모델 구조에 따라 재사용의 경제성이 달라진다는 증거다.

소프트웨어 통합 구조는 vLLM, SGLang, Dynamo, PyTorch를 대상으로 제시되므로 특정 엔진 하나에만 묶이지 않을 가능성이 있다. 그러나 실제 구현 및 검증 상태가 서로 다르며, 다중 호스트 KV 공유의 엔드투엔드 이득은 아직 측정되지 않았다. KV 캐시 이외의 데이터에 적용할 수 있다는 가능성도 제시되지만 검증 범위 밖이다.

## 한계와 생각해볼 점

### 저자가 밝힌 한계

첫째, 디스크 저장소의 실증적 특성화는 LLaMA-8B와 LLaMA-405B에 집중되어 있다. DeepSeek와 Qwen을 포함한 최신 MoE 변종은 추가로 평가되지 않았다. Maverick과 Scout의 호스트 메모리 결과만으로 다른 MoE 모델의 디스크 검색 손익분기점을 판단할 수는 없다.

둘째, 엔드투엔드 서빙 결과는 실제 PF Memory Appliance에서 측정한 값이 아니다. 에뮬레이션으로 얻은 대역폭과 지연을 LLMServingSim에 입력한 시뮬레이션 결과이며, 실물 하드웨어에서의 추론 워크로드 검증은 보류 상태다.

셋째, 다중 GPU·다중 호스트 분리형 추론에서 공유 풀을 통한 노드 간 KV 재사용 이득은 아직 실측되지 않았다. 논문의 아키텍처가 제거하려는 핵심 비용 중 하나가 워커 간 KV 재전송이므로, 이 평가는 중요한 후속 과제다.

넷째, 전기적 CXL 스위치 계층, 능동형 광학 인터커넥트, 단순 서버 증설과 비교한 비용-편익 분석이 없다. 지연과 대역폭만으로 실제 배포의 경제성을 판단할 수 없다.

다섯째, 호스트 간 모델 가중치 공유나 내결함성 서빙을 위한 체크포인트 저장처럼 KV 캐시 이외의 워크로드는 검증하지 않았다.

### 결과를 해석할 때 남는 질문

평균 350 ns와 호스트당 128 GB/s는 에뮬레이션에서 얻은 하드웨어 특성이고, 2,690 ms TTFT와 82% 히트율은 그 값을 사용한 서빙 시뮬레이션 결과다. 두 결과를 하나의 실물 시스템에서 동시에 측정한 것으로 해석해서는 안 된다.

또한 32 TB와 2 TB 비교는 용량뿐 아니라 PF 어플라이언스와 호스트 DRAM이라는 시스템 구성이 함께 달라진다. 시뮬레이션은 큰 풀이 축출 절벽을 제거한다는 강한 근거를 제공하지만, 실제 환경에서 메모리 비용, 장애 처리, 공유 인덱스 경합, 여러 호스트의 동시 접근이 결과를 얼마나 바꾸는지는 논문에서 확인되지 않는다.

패시브 풀-메시는 중간 중재를 제거하는 대신 모든 호스트-모듈 경로를 물리적으로 구성한다. 16×16 범위에서는 256개 경로로 구현되지만, 호스트나 모듈 수가 더 커질 때 연결 수와 패키징 복잡성이 어떻게 변하는지는 제시된 평가 범위 밖이다.

마지막으로 부록, 보조정리, 별도의 증명은 제공되지 않는다. 이 논문의 주장은 수학적 정리보다 Eq. (1)~(4)의 비용 모델, 프로토콜 수준 에뮬레이션, 반복 요청 측정, 서빙 시뮬레이션의 연결을 통해 뒷받침된다. 따라서 구현 여부를 판단할 때는 각 결과가 실측인지 에뮬레이션인지 시뮬레이션인지 구분하는 것이 가장 중요하다.
