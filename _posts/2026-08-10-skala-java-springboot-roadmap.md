## 이 과정을 배우는 이유

REST API를 만드는 일은 컨트롤러에 URL과 메서드를 연결하는 것만으로 끝나지 않는다. 요청이 어느 프로세스의 어느 포트로 들어오는지, 여러 요청이 같은 데이터를 동시에 수정하면 어떤 문제가 생기는지, 객체의 생명주기와 데이터베이스 트랜잭션은 어디에서 시작하고 끝나는지를 함께 이해해야 한다. 프레임워크가 많은 부분을 자동화할수록 그 내부 경계를 모르면 문제가 발생했을 때 원인을 찾기 어렵다.

이 과정은 그래서 Spring Boot 사용법부터 시작하지 않는다. 먼저 IP와 Port, 프로세스와 스레드, 동기와 비동기 같은 시스템 기초를 확인하고, Java 코드가 바이트코드로 컴파일되어 JVM에서 실행되는 과정을 살펴본다. 그 위에 클래스와 객체, 다형성, 인터페이스, 컬렉션과 제네릭을 쌓은 뒤, 리플렉션(reflection)과 애노테이션(annotation)이 프레임워크의 자동화를 어떻게 가능하게 하는지 연결한다.

객체지향 문법을 배운 다음에는 SOLID와 디자인 패턴을 통해 변경에 견디는 구조를 고민한다. 이어서 소켓으로 HTTP 요청과 응답을 직접 다뤄 보고, REST의 자원·행위·표현을 Spring MVC의 Controller-Service-Repository 계층으로 옮긴다. 마지막에는 JPA 영속성, 트랜잭션, 동시성 제어, API 문서화와 운영 모니터링까지 확장한다. 전체 흐름은 다음 질문으로 요약할 수 있다.

> JVM에서 실행되는 객체를 어떻게 설계하고 조합하여, HTTP 요청을 안전하게 처리하고 데이터베이스에 일관된 상태로 저장할 것인가?
{: .prompt-info }

나는 Python을 기준점으로 Java와 JavaScript의 차이를 이해하는 방식을 택했다. 문법을 따로 외우기보다 “Python의 무엇에 해당하며, 왜 다르게 설계되었는가”를 계속 질문했다. Java의 정적 타입을 볼 때는 JavaScript가 타입 선언 없이 값을 다루기 위해 런타임에 어떤 처리를 더 맡는지 대조하고, Java 애노테이션을 볼 때는 Python 데코레이터와 기능적으로 비슷해 보이지만 왜 호출 가능한 함수가 아닌지 질문했다. 애노테이션에 대한 질문은 이후 리플렉션, 프록시(proxy), IoC와 AOP를 연결하는 기준점이 된다.

```text
1일차: 실행 환경과 객체의 기초
    ↓
2일차: 타입 안전한 데이터 처리와 추상화
    ↓
3일차: 변경 가능한 설계를 HTTP 서비스 구조로 확장
    ↓
4일차: Spring 컨테이너와 프록시가 객체를 조합
    ↓
5일차: 영속성·트랜잭션·운영 경계까지 완성
```

1일차의 Stack·Heap과 스레드 개념은 단순한 JVM 암기 항목이 아니다. 공유 Heap에 접근하는 여러 스레드가 경쟁 상태(race condition)를 만들 수 있다는 사실은 `synchronized`, 비동기 실행, 데이터베이스 락으로 이어진다. 기본형과 참조형의 차이 역시 컬렉션, 제네릭, 엔티티 상태 변경을 이해하기 위한 바탕이 된다.

2일차에는 “공통 구현을 물려받을 것인가, 규약만 공유할 것인가”를 상속·추상 클래스·인터페이스로 구분한다. 컬렉션과 제네릭은 데이터를 안전하게 담는 방법을 제공하고, 람다와 Stream API는 그 데이터를 선언형 파이프라인으로 처리하게 한다. 리플렉션과 애노테이션은 여기서 별도의 문법 기능으로 끝나지 않는다. 애노테이션은 메타데이터를 남기고, 런타임의 처리 주체가 리플렉션으로 이를 읽어 동작을 결정한다는 구조를 확인한다.

3일차는 Java 문법에서 웹 프레임워크로 넘어가는 연결 구간이다. Builder와 SOLID로 객체 생성 및 의존 관계를 정리한 뒤, `ServerSocket`과 `Socket` 수준에서 HTTP 요청의 시작 라인·헤더·본문을 살펴본다. 이 저수준 처리가 Spring Boot에서는 `DispatcherServlet`, 파라미터 바인딩, JSON 직렬화로 추상화된다. Controller-Service-Repository 분리는 요청 처리, 비즈니스 규칙, 데이터 접근의 변경 이유를 나누는 설계 문제로 다룬다.

4일차에는 Spring의 자동화가 작동하는 기준을 추적한다. IoC 컨테이너가 객체의 생성권을 갖고 생성자 주입으로 의존성을 연결하며, 프록시는 대상 객체를 감싸 로깅·트랜잭션·비동기 같은 횡단 관심사를 적용한다. 이때 동일 클래스의 내부 호출은 프록시를 통과하지 않으므로 AOP와 `@Async`가 적용되지 않을 수 있다는 경계를 함께 확인한다.

5일차에는 요청이 데이터베이스에 반영되고 운영 환경에서 관측되기까지를 다룬다. JPA의 1차 캐시와 변경 감지, `@ManyToOne`의 외래키 주인, 지연 로딩을 연결하고, `@Transactional`의 프록시 경계와 낙관적·비관적 락의 선택 기준을 비교한다. 이후 Swagger/OpenAPI로 구현과 명세의 차이를 줄이고, Actuator의 헬스·메트릭·로거 엔드포인트로 실행 중인 서비스를 관찰한다.

## 실습 환경

실습은 Java와 JVM을 기반으로 순수 Java 코드에서 시작해 Spring Boot 애플리케이션으로 확장한다. 초기에는 콘솔 프로그램, 컬렉션, 람다, Stream API, 리플렉션과 커스텀 애노테이션을 작은 코드 단위로 확인한다. 이어 `ServerSocket`과 `Socket`으로 Echo 통신 및 단순 HTTP 서버의 요청·응답 구조를 다룬다.

Spring Boot 구간에서는 내장 톰캣을 통해 REST API를 실행하고, H2 인메모리 데이터베이스로 Controller-Service-Repository 계층과 CRUD 흐름을 구성한다. 설정은 `application.yml`과 환경별 프로파일로 분리하며, Lombok은 Getter와 생성자, 로거 같은 반복 코드를 줄이는 범위에서 사용한다.

후반부에는 Spring Data JPA로 엔티티와 연관관계를 매핑하고, Bean Validation으로 잘못된 요청이 서비스 계층까지 들어오는 것을 막는다. `ThreadPoolTaskExecutor`를 통한 비동기 처리, Swagger UI를 통한 API 명세 확인, Actuator를 통한 헬스·메트릭 확인과 동적 로그 레벨 제어도 실습 범위에 포함된다.

## 글을 정리하는 기준

이 시리즈는 강의 목차를 순서대로 옮기기보다 각 기능이 해결하는 문제와 추상화의 경계를 중심으로 정리한다. Java 문법은 “어떻게 쓰는가”에 더해 JVM 메모리와 타입 시스템에서 왜 그런 제약이 생기는지 살펴본다. Spring 애노테이션은 이름을 나열하지 않고, 누가 언제 메타데이터를 읽으며 실제 호출이 원본 객체와 프록시 중 어디를 통과하는지 추적한다.

한 가지 미리 밝혀 둘 것이 있다. **3일차(8월 12일)는 정보처리기사 시험 응시로 교육에 참석하지 못했다.** 그날 글은 강의를 들은 기록이 아니라 배포된 강의자료를 따로 읽고 정리한 것이며, 해당 글 서두에도 같은 내용을 적어 두었다.

실습 글에서는 수행하지 않은 결과를 완성된 성과처럼 쓰지 않는다. 제공된 요구사항, 평가 기준, 구현 방향을 분리하고 코드가 필요한 경우에도 동작 하나를 드러내는 최소 예제를 사용한다. 특히 다음과 같은 함정을 남기는 데 초점을 맞춘다.

- `String` 반복 연결과 불필요한 객체 생성
- `equals()`와 `hashCode()` 불일치로 인한 `Set`·`Map` 오동작
- Stream의 지연 평가와 재사용 불가
- 런타임 애노테이션의 `Retention` 누락
- Controller에 비즈니스 로직을 넣어 생기는 책임 혼합
- AOP, `@Async`, `@Transactional`의 자기 호출(self-invocation) 문제
- JPA의 즉시 로딩과 N+1 문제, Enum의 순서 저장 위험
- Actuator와 Swagger 엔드포인트의 운영 환경 노출 위험

각 일차의 글은 앞선 개념이 다음 추상화에서 어떻게 사용되는지를 명시한다. 최종 목표는 Spring Boot 기능을 많이 아는 것이 아니라, 자동화된 동작의 근거와 실패 경계를 설명할 수 있는 백엔드 구조를 만드는 것이다.
