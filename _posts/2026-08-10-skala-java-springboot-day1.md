## 문법보다 실행 환경을 먼저 보는 이유

Java 문법을 배우기 전에 시스템과 네트워크 구조부터 살펴본 이유는 백엔드 코드가 혼자 실행되지 않기 때문이다. 서버 프로그램은 운영체제 위의 프로세스로 실행되고, 특정 IP 주소와 포트를 통해 요청을 받는다. 요청을 처리하는 동안에는 여러 스레드가 같은 객체를 공유할 수 있으며, 잘못된 입력이나 네트워크 실패는 예외로 이어진다. 클래스와 메서드 문법만 따로 외우면 이런 실행 조건이 코드와 어떻게 연결되는지 놓치기 쉽다.

1일차의 흐름은 다음과 같이 정리할 수 있다.

```text
클라이언트 요청
  → IP와 Port로 서버 프로세스 식별
  → 프로세스 안의 스레드가 요청 처리
  → JVM이 Java 바이트코드 실행
  → Stack과 Heap에 값과 객체 배치
  → 제어문으로 업무 규칙 분기
  → 예외 처리로 실패 경로 제어
  → 캡슐화된 객체가 자신의 상태 보호
```

Python을 기준점으로 삼아 Java를 따라가면서, JavaScript에서는 변수 선언 시 자료형을 지정하지 않는데 기계가 그 값을 메모리에서 어떻게 처리하는지 질문했다. 또 Java 같은 정적 타입 언어와 비교했을 때 런타임에 무엇이 더 필요해지는지도 궁금했다. 이 질문에 대한 Java 쪽 비교축은 분명했다. Java는 소스 코드를 바이트코드로 컴파일하는 단계에서 타입을 검사하고, JVM은 기본형과 참조형을 구분하여 각 값을 정해진 런타임 영역에 배치한다. 따라서 Java 문법의 타입 선언은 단순한 표기법이 아니라 컴파일과 메모리 모델에 연결된 규칙이다.

## 서버를 찾는 두 좌표: IP와 Port

네트워크에서 서버에 접근하려면 먼저 어느 호스트인지, 그 호스트 안의 어느 프로그램인지 구분해야 한다. IP 주소는 네트워크 인터페이스를 식별하고, 포트는 해당 호스트에서 실행 중인 애플리케이션의 접점을 식별한다. 같은 서버에서 여러 프로그램이 동시에 동작할 수 있는 것은 각 프로그램이 서로 다른 포트에 바인딩될 수 있기 때문이다.

예를 들어 `127.0.0.1`과 `localhost`는 현재 컴퓨터 내부로 되돌아오는 루프백 통신을 가리킨다. 로컬에서 서버를 실행하고 테스트할 때 유용하지만, 외부 클라이언트가 이 주소로 내 서버에 접근할 수 있는 것은 아니다. 외부 통신에서는 NAT 내부의 사설 IP와 인터넷에서 라우팅되는 공인 IP의 경계를 구분해야 한다.

요청이 서버까지 전달되는 과정에는 목적이 다른 네트워크 장비가 개입한다.

- 라우터는 L3 계층에서 목적지까지의 경로를 탐색한다.
- 로드밸런서는 L4 또는 L7 계층에서 여러 서버로 트래픽을 분배한다.
- 게이트웨이는 서로 다른 프로토콜이나 보안 정책 사이의 관문 역할을 한다.

백엔드 애플리케이션 관점에서 이를 단순화하면 다음과 같다.

```text
클라이언트
  → 공인 IP 또는 도메인
  → 라우터·게이트웨이·로드밸런서
  → 서버의 IP
  → 애플리케이션이 바인딩한 Port
  → 요청을 처리하는 프로세스와 스레드
```

프론트엔드와 백엔드가 분리된 구조에서는 정적 자원과 동적 처리를 담당하는 계층도 나뉜다. Web Server는 정적 자원을 제공하거나 리버스 프록시 역할을 맡고, WAS는 비즈니스 로직 실행과 데이터베이스 연동을 담당한다. 클라이언트와 서버 사이의 데이터는 주로 키-값과 배열 구조를 가진 JSON으로 교환한다. YAML은 들여쓰기 기반의 계층 구조와 주석을 지원하므로 통신 데이터보다 설정 파일에 적합하다.

> JSON은 주석을 허용하지 않고 문법이 엄격하다. YAML은 읽기 편하지만 공백과 들여쓰기 오류에 취약하므로, 두 형식을 같은 용도로 취급하면 안 된다.

## 프로세스와 스레드, 그리고 공유 상태

프로세스는 운영체제로부터 자원을 할당받아 실행되는 프로그램 인스턴스다. 각 프로세스는 Code, Data, Stack, Heap으로 구성된 독립적인 가상 메모리 공간을 가지며, 다른 프로세스와 데이터를 주고받으려면 IPC가 필요하다.

스레드는 프로세스 내부의 CPU 작업 흐름이다. 같은 프로세스에 속한 스레드들은 Code, Data, Heap을 공유하지만 Stack은 개별적으로 가진다. 프로세스를 여러 개 만드는 것보다 생성과 전환 비용이 작기 때문에 하나의 서버가 여러 작업을 처리할 때 중요한 실행 단위가 된다.

공유는 효율을 높이지만 동시에 문제를 만든다. 여러 스레드가 Heap에 있는 동일한 계좌 객체를 읽고 수정하면, 두 스레드가 변경 전 잔액을 동시에 확인한 뒤 각각 출금을 반영하는 경쟁 상태(race condition)가 발생할 수 있다. 이때 `synchronized`를 사용하면 모니터 락을 얻은 한 스레드만 임계 영역에 진입하게 할 수 있다.

```java
public synchronized void withdraw(int amount) {
    if (balance >= amount) {
        balance -= amount;
    }
}
```

여기서 중요한 것은 `synchronized`를 많이 붙이는 것이 아니라 공유 상태를 실제로 변경하는 범위를 식별하는 것이다. 잠금 범위가 지나치게 넓으면 다른 스레드가 오래 기다리면서 병목이 생긴다.

동기와 비동기도 대기 방식의 차이로 연결된다. 동기 처리는 요청한 결과가 돌아올 때까지 기다리므로 실행 흐름을 따라가기 쉽고 트랜잭션 경계를 관리하기 유리하다. 비동기 처리는 제어권을 먼저 반환한 뒤 콜백이나 이벤트로 결과를 받기 때문에 외부 I/O처럼 대기 시간이 긴 작업에서 자원을 더 효율적으로 사용할 수 있다. 다만 처리 순서와 공유 상태를 별도로 관리해야 하므로 무조건 더 단순한 방식은 아니다.

## 좋은 경계는 높은 응집도와 낮은 결합도에서 시작한다

시스템 기초에서 응집도(cohesion)와 결합도(coupling)를 함께 본 것은 이후의 객체 설계를 평가할 기준을 마련하기 위해서다. 응집도는 한 모듈이 하나의 책임에 집중하는 정도이고, 결합도는 모듈들이 서로 의존하는 정도다. 유지보수하기 좋은 구조는 관련된 기능을 한곳에 모으되 다른 모듈의 내부 구현에는 가능한 한 적게 의존한다.

이 기준은 배포 구조에도 적용된다. 모놀리스(monolith)는 하나의 배포 단위 안에 기능을 모으므로 시작하기 단순하지만 내부 결합도가 높아질 수 있다. 마이크로서비스 아키텍처(MSA)는 서비스를 독립적으로 배포하고 확장할 수 있지만, 서비스 사이의 통신이 네트워크를 거치면서 복잡도가 증가한다.

같은 원리가 1일차 후반의 캡슐화에도 이어진다. 필드를 외부에 그대로 공개하면 여러 코드가 객체의 상태 표현에 직접 의존한다. 반대로 객체가 상태와 변경 규칙을 함께 관리하면 관련 책임의 응집도는 높아지고 외부 코드와의 결합도는 낮아진다.

## Java 소스가 JVM에서 실행되기까지

Java의 WORA(Write Once, Run Anywhere)는 운영체제가 Java 소스를 직접 실행해서 가능한 것이 아니다. Java 컴파일러와 JVM 사이에 바이트코드라는 중간 표현이 있기 때문에 가능하다.

```text
.java 소스 코드
  → javac 컴파일
  → .class 바이트코드
  → JVM ClassLoader
  → Execution Engine
      ├─ Interpreter
      └─ JIT Compiler
  → 실행 환경의 기계어
```

`javac`는 `.java` 파일을 JVM이 이해할 수 있는 `.class` 바이트코드로 변환한다. 실행 시 클래스로더가 필요한 클래스를 JVM에 적재하고, 실행 엔진은 인터프리터와 JIT 컴파일러를 통해 바이트코드를 실제 기계어로 처리한다. 운영체제마다 JVM 구현은 달라도 동일한 바이트코드를 실행할 수 있으므로 소스 코드가 특정 OS에 직접 묶이지 않는다.

JVM은 실행 중인 데이터를 역할별 영역에 나누어 관리한다.

| 런타임 영역 | 공유 범위 | 주요 저장 대상 |
|---|---|---|
| Stack | 스레드별 독립 | 메서드 호출 프레임, 지역 변수, 기본형 데이터 |
| Heap | 모든 스레드 공유 | `new`로 생성한 객체와 배열 |
| Method Area·Metaspace | JVM 수준 | 클래스 메타데이터, 상수 풀, 정적 변수 |

메서드를 호출하면 해당 스레드의 Stack에 호출 프레임이 생성되고, 메서드가 종료되면 프레임도 제거된다. 반면 Heap의 객체는 메서드 종료만으로 바로 사라지지 않는다. Garbage Collector가 더는 참조되지 않는 객체를 추적하여 회수한다.

자동 메모리 관리가 모든 메모리 문제를 없애는 것은 아니다. 사용하지 않는 객체라도 다른 객체가 계속 참조하고 있으면 도달 가능한 상태로 남기 때문에 GC가 회수할 수 없다. 따라서 불필요한 장기 참조를 유지하지 않는 것도 Java 프로그램의 메모리 관리에 포함된다.

## 기본형과 참조형을 메모리 구조로 이해하기

Java의 기본형(primitive type)은 값을 직접 저장하고, 참조형(reference type)은 Heap에 있는 객체를 가리키는 참조값을 저장한다.

```java
int primitiveVal = 100;
String refVal = "Hello";
Integer wrapperVal = Integer.valueOf(100);
```

`primitiveVal`은 기본형 값 자체가 Stack에 놓인다. `refVal` 변수에는 참조값이 있고, 문자열 객체는 Heap 내부의 문자열 상수 풀에서 관리된다. `wrapperVal`은 기본형 `int`를 객체로 다룰 수 있게 감싼 `Integer` 참조형이다. 이 변환을 박싱(boxing)이라고 하며 반대 방향은 언박싱(unboxing)이다.

이 구분이 필요한 이유는 메모리 효율성과 객체 기반 기능의 요구가 다르기 때문이다. 단순한 수치 계산에서는 기본형이 직접적이지만, 객체를 다루는 구조에서는 래퍼 타입이 필요할 수 있다. 변수 선언부만 보고도 값인지 객체에 대한 참조인지 구분할 수 있다는 점이 Java의 정적 타입 체계를 이해하는 기준이 된다.

`String`은 참조형이면서 불변(immutable) 객체다. 문자열을 수정하는 것처럼 보이는 연산도 기존 객체를 바꾸는 대신 새로운 문자열 객체를 만든다. 따라서 반복문에서 `+`를 이용해 문자열을 계속 연결하면 중간 객체가 많이 생성될 수 있다. 변경 가능한 버퍼가 필요한 경우에는 `StringBuilder`가 적합하다.

```java
StringBuilder builder = new StringBuilder();

builder.append("Java");
builder.append(" ");
builder.append("Backend");

String result = builder.toString();
```

`StringBuilder`는 동기화 락을 사용하지 않아 단일 스레드 작업에 적합하다. 여러 스레드가 하나의 문자열 버퍼를 공유해야 한다면 메서드 수준 동기화를 제공하는 `StringBuffer`를 고려할 수 있다. 선택 기준은 단순한 기능 차이가 아니라 해당 객체가 어느 스레드에서 공유되는지다.

`static` 멤버도 인스턴스 멤버와 생명주기가 다르다. 인스턴스 필드는 객체마다 생성되지만 `static` 필드와 메서드는 클래스 단위로 적재되어 모든 인스턴스가 공유한다. 그래서 `static` 메서드는 인스턴스 없이 클래스명으로 호출할 수 있지만, 특정 인스턴스를 가리키는 `this`나 인스턴스 필드를 직접 사용할 수 없다.

## 연산자와 제어문으로 업무 규칙 표현하기

연산자는 값을 계산하거나 조건을 만들고, 제어문은 그 결과에 따라 실행 경로를 선택한다. 백엔드 코드에서는 사용자 입력 검증, 상태 전환, 연산 종류 선택처럼 업무 규칙을 코드로 옮길 때 두 요소가 함께 사용된다.

조건이 소수라면 `if-else`가 자연스럽다. 하나의 값에 따라 여러 경우를 나눌 때는 `switch`가 분기 의도를 더 분명하게 보여줄 수 있다. 향상된 `switch` 표현식은 화살표 구문으로 값을 반환하므로 전통적인 `switch-case`보다 분기 결과를 하나의 표현식으로 구성하기 쉽다.

```java
String grade = switch (score / 10) {
    case 10, 9 -> "A";
    case 8 -> "B";
    default -> "F";
};
```

전통적인 `switch-case`에서는 `break`를 빠뜨리면 다음 `case`까지 실행되는 fall-through가 발생한다. 의도적으로 사용하는 경우가 아니라면 오류의 원인이 되기 쉽기 때문에 화살표 표현식이 안전한 선택이 될 수 있다.

반복문은 반복 조건과 순회 대상에 따라 구분할 수 있다.

- `while`은 종료 조건을 중심으로 반복할 때 적합하다.
- `do-while`은 본문을 최소 한 번 실행해야 할 때 사용한다.
- `for`는 인덱스나 반복 횟수를 명시적으로 다루기 좋다.
- 향상된 `for-each`는 순회 가능한 객체의 각 요소를 차례로 처리할 때 적합하다.

콘솔 계산기를 예로 들면 `while`은 입력을 반복해서 받는 바깥 흐름을 담당하고, `switch`는 연산 종류를 선택하며, `for-each`는 이전 연산 이력을 출력하는 역할을 맡을 수 있다. `break`, `continue`, `return`은 각각 반복 종료, 현재 반복 건너뛰기, 메서드 반환처럼 현재 제어 흐름을 변경한다.

```text
입력 반복(while)
  → 연산자 선택(switch)
  → 입력값 검증(if)
  → 계산 실행
  → 이력 저장
  → 이력 순회(for-each)
  → 종료 조건이면 break
```

이렇게 제어문의 책임을 분리하면 중첩이 깊어지는 것을 막을 수 있다. 조건을 모두 하나의 거대한 `if-else` 블록에 넣는 것보다 반복, 분기, 검증의 역할을 구분하는 편이 변경 범위를 좁힌다.

## 예외는 실패를 숨기는 문법이 아니다

예외 처리는 문제가 생기지 않게 만드는 기능이 아니라, 정상 흐름과 실패 흐름을 분리하여 실패를 복구하거나 상위 계층으로 전달하는 구조다. 예외를 처리하지 않으면 프로그램이 비정상 종료될 수 있지만, 모든 예외를 `catch`해서 무시하는 것도 올바른 대응은 아니다.

Java 예외는 처리 강제 여부에 따라 크게 나뉜다.

| 구분 | 기준 | 대표적인 발생 상황 | 처리 방향 |
|---|---|---|---|
| Checked Exception | `RuntimeException`을 제외한 `Exception` 하위 | 파일 I/O, 네트워크 실패 | 컴파일 시 처리 또는 전파 강제 |
| Unchecked Exception | `RuntimeException` 하위 | NPE, 잘못된 인자 등 논리 오류 | 입력 검증과 코드 수정, 필요 시 전파 |

파일이나 네트워크 연결처럼 사용 후 반드시 닫아야 하는 리소스는 `try-with-resources`로 관리할 수 있다. `AutoCloseable`을 구현한 객체를 `try` 괄호 안에 선언하면 블록이 끝날 때 `close()`가 자동 호출된다.

```java
try (BufferedReader br =
         new BufferedReader(new FileReader("file.txt"))) {
    String line = br.readLine();
} catch (IOException e) {
    throw new CustomBusinessException("파일 읽기 실패", e);
}
```

새로운 예외로 변환할 때 원래 예외 `e`를 함께 전달하는 이유는 실패 원인을 추적할 수 있게 하기 위해서다. `catch` 블록을 비워두거나 아무 처리 없이 넘어가면 당장은 프로그램이 계속 실행되더라도 원인 분석에 필요한 정보가 사라진다.

첫 번째 환영 메시지를 출력한 뒤 `Thread.sleep(1000)`으로 대기하고 두 번째 메시지를 출력하는 실습도 같은 맥락이다. 구현의 핵심은 두 번의 출력보다 `Thread.sleep` 호출에서 요구되는 `InterruptedException`을 어떻게 처리할지 결정하는 데 있다. 예외 처리는 문법을 맞추기 위한 부속 코드가 아니라 정상적인 대기 흐름이 중단되었을 때의 정책이다.

계산기에서는 0으로 나누기처럼 예상할 수 있는 실패 상황을 `try-catch`와 사용자 정의 예외로 분리할 수 있다. 이때 사용자에게 보여줄 메시지와 원인 추적을 위한 예외 정보는 목적이 다르므로, 오류를 무조건 문자열 하나로 바꾸기보다 필요한 지점까지 전파하는 구조를 고려해야 한다.

> 예외를 잡았다는 사실만으로 처리된 것은 아니다. 복구할 수 있으면 복구하고, 그렇지 않으면 원인을 보존한 채 적절한 계층으로 전달해야 한다.
{: .prompt-warning }

## 클래스와 객체: 데이터 옆에 변경 규칙 두기

클래스는 객체가 가질 데이터와 행동을 정의하고, 객체는 그 클래스를 바탕으로 생성된 인스턴스다. 객체지향 프로그래밍의 핵심은 관련된 값을 한곳에 모으는 데서 끝나지 않는다. 해당 값을 어떤 조건에서 변경할 수 있는지까지 객체가 책임져야 한다.

잔액 필드가 공개되어 있다면 외부 코드는 음수를 대입하거나 검증 절차를 건너뛸 수 있다.

```java
public class Account {
    private long balance;

    public void deposit(long amount) {
        if (amount > 0) {
            this.balance += amount;
        }
    }
}
```

`balance`를 `private`으로 숨기고 `deposit()`을 통해서만 변경하면, 잔액과 입금 규칙이 한 클래스 안에 모인다. `this.balance`의 `this`는 현재 메서드를 실행하는 인스턴스 자신을 가리킨다. 매개변수나 지역 변수와 필드의 이름을 구분할 때도 사용할 수 있다.

캡슐화(encapsulation)는 필드에 Getter와 Setter를 기계적으로 추가하는 것이 아니다. 모든 필드에 공개 Setter를 제공한다면 외부 코드가 객체 상태를 임의로 바꿀 수 있어 필드를 공개한 것과 큰 차이가 없다. 객체가 허용하는 행위를 메서드로 표현하고, 그 안에서 유효성을 검사해야 상태의 무결성을 지킬 수 있다.

패키지는 관련 클래스를 묶는 네임스페이스이자 접근 범위를 정하는 경계다. 같은 이름의 클래스가 충돌하는 것을 막고, 외부에 보여줄 기능과 내부 구현을 구분한다.

| 접근 제어자 | 접근 가능한 범위 |
|---|---|
| `private` | 선언된 클래스 내부 |
| `default` | 같은 패키지 내부 |
| `protected` | 같은 패키지와 다른 패키지의 자식 클래스 |
| `public` | 모든 패키지 |

필드는 기본적으로 `private`으로 두고, 외부에 꼭 필요한 행동만 제한적으로 공개하는 것이 캡슐화의 출발점이다. 패키지와 접근 제어자는 단순한 가시성 문법이 아니라 다른 코드가 객체 내부 표현에 의존하지 못하게 하는 설계 수단이다.

## 실습

1일차 실습은 개별 문법을 따로 확인하는 단계에서 시작해, 제어문과 예외 처리, 캡슐화를 조합하는 방향으로 이어진다. 제출 코드가 제공된 것은 아니므로 여기서는 요구사항과 구현 방향을 중심으로 정리한다.

### 실행 흐름과 자료형 확인

`App.java`에서는 첫 번째 환영 메시지를 출력하고 1초 동안 대기한 다음 두 번째 메시지를 출력해야 한다. 기본 클래스와 `main` 메서드 구조를 유지하면서 `Thread.sleep(1000)`을 호출하고, `InterruptedException`을 처리하는 것이 평가 기준이다.

`NumberBox.java`에서는 기본형과 래퍼 클래스를 함께 선언하여 박싱과 언박싱을 구분한다. 각 변수가 기본값 자체를 보관하는지, Heap 객체에 대한 참조를 보관하는지를 JVM의 Stack·Heap 구조와 연결하는 것이 핵심이다.

정적 멤버 실습에서는 다음 항목을 분리해 비교할 수 있다.

```text
인스턴스 변수 → 객체마다 별도 상태
static 변수  → 클래스 수준에서 공유
인스턴스 메서드 → 특정 객체를 통해 호출
static 메서드  → 클래스명으로 직접 호출
```

평가의 초점은 문법적인 호출 성공 여부보다 인스턴스를 추가로 생성했을 때 어떤 값이 공유되는지 설명하는 데 있다.

### 문자열과 공유 자원 확인

문자열 포맷터 실습에서는 `String.format()`과 `printf()`를 사용해 값을 형식에 맞춰 출력한다. 반복적인 문자열 조합은 `String`의 `+` 연산과 `StringBuilder.append()`의 차이를 기준으로 구현 방향을 세울 수 있다. 전자는 불변 문자열 객체를 새로 만들고, 후자는 가변 버퍼에 내용을 누적한다.

멀티스레드 계좌 실습에서는 여러 스레드가 같은 `Account` 객체의 `withdraw()`를 호출하는 상황을 구성한다. 구현 시 확인할 기준은 다음과 같다.

- 여러 스레드가 동일한 Heap 객체를 공유하는가
- 잔액 확인과 차감이 하나의 임계 영역으로 보호되는가
- `synchronized`의 범위가 필요한 코드보다 지나치게 넓지 않은가
- 모든 작업이 끝난 뒤 잔액의 데이터 정합성이 유지되는가

### 제어문 기반 콘솔 계산기

계산기 실습은 1일차 문법을 하나의 작은 프로그램으로 결합한다.

```text
사용자 입력
  → while로 반복
  → Enum과 switch로 연산 선택
  → if로 입력값과 연산 조건 검사
  → 결과 및 이력 저장
  → for-each로 이력 출력
  → 종료 조건 처리
```

0으로 나누기와 잘못된 연산 요청은 정상 계산 흐름과 분리한다. `try-catch`로 비정상 종료를 막되 예외를 무시하지 않고, 필요하면 사용자 정의 예외로 실패 원인을 표현한다. 평가 기준은 제어문을 많이 사용하는 것이 아니라 반복, 분기, 종료, 예외 처리의 책임이 구분되어 있는지다.

### 패키지와 캡슐화 확인

Stock 관련 실습에서는 클래스를 서로 다른 패키지에 배치하고 `public`, `protected`, `default`, `private` 멤버에 대한 접근 가능 여부를 비교한다. 컴파일 가능 여부를 확인하는 데서 끝내지 않고, 외부 패키지에 공개해야 하는 기능과 내부 구현으로 숨겨야 하는 상태를 구분해야 한다.

기본 클래스 구현에서는 필드를 `private`으로 두고, 상태 변경 메서드 안에 유효성 검증을 배치한다. 잔액이나 수량처럼 유효 범위가 있는 데이터를 공개 Setter로 변경하게 하기보다 `deposit()`, `withdraw()`처럼 의도를 드러내는 메서드로 표현하는 편이 캡슐화 원칙에 맞는다.

## 정리

1일차에는 서버 프로그램이 IP와 Port를 통해 식별되고, 프로세스와 스레드 위에서 실행된다는 시스템 관점에서 출발했다. 이어 Java 소스가 바이트코드로 컴파일되어 JVM에서 실행되는 과정과 Stack, Heap, Metaspace의 역할을 연결했다. 이 구조를 기준으로 기본형과 참조형, 불변 문자열, 정적 멤버를 구분하고, 제어문과 예외 처리로 정상·실패 흐름을 표현했다. 마지막에는 상태와 변경 규칙을 클래스 안에 묶는 캡슐화를 통해 문법이 설계 경계로 확장되는 과정을 정리했다.
