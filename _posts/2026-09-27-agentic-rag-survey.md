## 세 줄 요약

에이전틱 RAG(Agentic Retrieval-Augmented Generation)는 검색 결과를 받아 답하는 흐름에 **다음에 무엇을 검색하고 언제 멈출지 결정하는 제어 과정**을 더한다. 이 서베이는 RAG의 발전 경로와 에이전트 설계 패턴을 정리하고, 에이전트 수·제어 구조·자율성·지식 표현을 기준으로 아키텍처를 비교한다. 핵심은 복잡한 질문에 맞춰 검색 경로를 바꿀 수 있는 만큼 검색 품질과 실행 비용, 중단 조건, 결정 과정의 검증을 함께 설계해야 한다는 것이다.

## 이 논문이 풀려는 문제

언어 모델의 사전 학습 지식은 계속 바뀌는 외부 정보를 그대로 반영하지 못한다. 검색 증강 생성(Retrieval-Augmented Generation, RAG)은 추론 시점에 문서, 데이터베이스, API, 웹에서 정보를 가져와 답변에 넣는다. 기본 구성은 **검색(retrieval) → 검색 결과의 가공·선별(augmentation) → 생성(generation)**이다. 검색은 후보 근거를 찾고, 보강은 그중 질문에 필요한 내용을 생성기가 사용할 수 있도록 구성하며, 생성은 그 근거를 바탕으로 답을 만든다.

외부 근거를 가져올 수 있다는 점은 유용하지만, 검색을 한 번 수행한 뒤 생성하는 고정된 흐름만으로는 모든 질문을 처리하기 어렵다. 첫 검색에서 관련 문서를 찾더라도 답에 필요한 연결 고리가 빠질 수 있다. 서로 다른 자료원에 사실이 흩어져 있다면 첫 결과를 보고 다음 검색어를 바꾸거나 다른 자료원으로 옮겨야 한다. 논문은 전통적 RAG의 어려움을 **문맥 통합, 여러 단계의 추론, 데이터 규모에 따른 확장성과 지연**으로 나누어 설명한다.

이 세 문제는 서로 이어진다. 문서 여러 개를 가져왔어도 각각의 내용을 질문의 맥락에 맞게 연결하지 못하면 답은 단편적으로 남는다. 연결에 필요한 정보가 빠졌다면 추가 검색이 필요하다. 그러나 매 질문마다 모든 자료원을 다시 검색하고 결과를 평가하면 지연이 커진다. 따라서 중요한 설계 질문은 검색 기능을 추가하는 데서 끝나지 않는다. **어느 질문에 어느 자료원을 사용하고, 중간 결과에 따라 언제 경로를 바꾸며, 어느 시점에 검색을 마칠 것인가**까지 정해야 한다.

서베이가 제시하는 RAG의 발전 경로를 구분하면 에이전트의 역할이 더 분명해진다.

| 패러다임 | 검색과 처리의 중심 | 해결하려는 문제와 남는 비용 |
|---|---|---|
| 나이브 RAG(Naïve RAG) | TF-IDF, BM25 같은 어휘 기반 검색 뒤 생성 | 단순한 사실 질문에 적용하기 쉽지만 표현이 다른 관련 문서를 놓치거나 문맥 결합이 약할 수 있다. |
| 어드밴스드 RAG(Advanced RAG) | 밀집 검색, 재순위화, 반복·다중 홉 검색 | 의미적 관련성과 복잡한 질의 처리를 개선하려 하지만 검색·순위화의 계산 비용이 늘어난다. |
| 모듈러 RAG(Modular RAG) | 희소·밀집 검색의 조합, 교체 가능한 구성 요소, 도구 연동 | 도메인에 맞춰 구성할 수 있다. 어떤 구성 요소를 언제 실행할지는 별도의 설계 문제로 남는다. |
| 그래프 RAG(Graph RAG) | 개체와 관계를 그래프로 표현하고 연결을 따라 검색 | 관계를 건너가는 질문에 유리하지만 그래프의 품질과 구축·통합 비용에 의존한다. |
| 에이전틱 RAG(Agentic RAG) | 에이전트가 검색 경로, 도구, 반복 여부를 결정 | 질문과 중간 결과에 맞춰 흐름을 바꿀 수 있지만 제어·조정·지연·자원 사용량이 복잡해진다. |

이 표는 논문 Table 1의 특징과 강점을 구현 관점에서 읽은 것이다. 각 패러다임이 앞의 방식을 완전히 대체한다는 뜻은 아니다. 모듈러 RAG에 충분한 검색기와 재순위화가 갖춰져 있다면 범위가 좁은 질문에는 추가 에이전트가 필요하지 않을 수 있다. 논문도 실무 교훈에서 **에이전틱 RAG를 모든 작업의 기본 선택지로 삼지 말라**고 조언한다.

## 핵심 아이디어 — 검색 위에 제어 계층을 둔다

전통적인 검색 파이프라인은 대체로 배포 전에 정해 둔 순서대로 움직인다. 에이전틱 RAG에서는 현재 질문과 확보한 근거를 바탕으로 다음 동작을 선택한다. 검색 결과가 부족하면 질문을 다시 쓰고, 다른 자료원을 호출하거나, 결과를 평가한 뒤 다시 검색한다. 근거가 충분하다고 판단하면 답을 합성한다.

따라서 핵심은 에이전트의 개수 자체보다 **검색 과정의 어떤 결정을 고정해 두고, 어떤 결정을 실행 중에 내리게 할 것인가**에 있다. 논문 초록은 분류 기준으로 에이전트 수(agent cardinality), 제어 구조(control structure), 자율성(autonomy), 지식 표현(knowledge representation)을 제시한다. 다만 본문의 Table 3에는 자율성이 독립된 행으로 제시되지 않는다. 초록에서 밝힌 분류의 취지와 비교표에서 실제로 대조하는 항목을 구분해 읽을 필요가 있다.

### 에이전트의 구성, 행동 패턴, 실행 구조

논문은 에이전트의 구성 요소로 역할과 작업을 부여받은 언어 모델, 단기·장기 기억(memory), 계획(planning), 외부 도구(tools)를 든다. 이 요소들은 서로 다른 문제를 맡는다. 모델은 질문과 중간 결과를 해석하고, 기억은 앞선 상호작용과 현재 작업 상태를 유지한다. 계획은 큰 질문을 작은 작업으로 나누며, 도구는 모델 내부 지식만으로 얻을 수 없는 문서·데이터·계산 결과를 가져온다.

여기서 기억과 검색 결과를 혼동하면 안 된다. 검색 결과는 이번 질문에 사용하려고 외부에서 가져온 근거다. 기억은 대화나 이전 작업을 이어 가기 위한 상태까지 포함한다. 오래 보존된 기억이 현재 근거보다 앞서면 오래되거나 잘못된 정보가 답에 영향을 줄 수 있다. 논문이 장기 기억 관리와 최신 외부 지식의 조정을 별도의 연구 과제로 다루는 이유다.

논문은 에이전트가 보이는 대표적인 행동을 **반성(reflection), 계획(planning), 도구 사용(tool use), 다중 에이전트 협업(multi-agent collaboration)**으로 설명한다.

- **반성**은 초안이나 검색 결과를 평가하고, 발견한 결함을 다음 시도에 반영한다. 평가를 했다는 사실만으로 교정이 이루어지지는 않는다. 평가 결과가 재검색, 재작성, 중단 같은 다음 동작을 바꾸어야 한다.
- **계획**은 복잡한 질문을 작은 과제로 나누고 순서를 정한다. 고정된 절차로 처리하기 어려운 질문에 도움이 되지만, 실행 경로를 예측하기도 어려워진다.
- **도구 사용**은 벡터 검색, 웹 검색, 데이터베이스, API처럼 모델 밖의 자원에 접근하는 방법이다. 도구가 많아지면 질문에 맞는 도구를 고르는 일도 설계 대상이 된다.
- **협업**은 서로 다른 역할을 맡은 에이전트가 중간 결과를 주고받는 방식이다. 독립 작업의 병렬 실행과 역할 분담이 가능해지는 만큼 위임과 결과 통합이 필요하다.

한편 워크플로 패턴은 그 행동들을 **어떤 실행 구조에 놓을지** 설명한다.

| 워크플로 | 실행 구조 | 선택할 때 볼 점 |
|---|---|---|
| 프롬프트 체이닝(prompt chaining) | 앞 단계의 출력을 다음 단계로 넘김 | 하위 작업이 미리 정해져 있으면 흐름이 명료하지만 단계별 지연이 누적된다. |
| 라우팅(routing) | 입력을 분류해 알맞은 경로로 보냄 | 자료원이나 처리 방식이 질문 유형에 따라 달라질 때 쓴다. |
| 병렬화(parallelization) | 독립 작업을 동시에 실행하거나 여러 결과를 비교함 | 대기 시간을 줄이거나 결과를 교차 검토할 수 있으나 통합이 필요하다. |
| 오케스트레이터–워커(orchestrator–workers) | 중앙 제어자가 실행 중 작업을 나누어 위임함 | 필요한 하위 작업을 미리 확정할 수 없을 때 적합하다. |
| 평가자–개선자(evaluator–optimizer) | 결과를 평가하고 다시 개선함 | 평가 기준이 분명할 때 반복의 이득과 비용을 판단하기 쉽다. |

예를 들어 ‘반성’은 에이전트의 행동이고, ‘평가자–개선자’는 평가와 개선을 반복 실행하도록 배치한 구조다. ‘도구 사용’도 단일 에이전트의 라우팅 안에 들어갈 수 있고, 여러 워커의 역할로 나뉠 수도 있다. 두 분류를 같은 목록으로 취급하면 어떤 능력이 필요한지와 그 능력을 어떻게 실행할지가 섞인다.

워크플로 선택은 앞에서 본 문제와 대응된다. 검색 결과의 적합성이 불확실하면 평가자–개선자 구조로 재검토할 수 있다. 질문 유형에 따라 자료원이 분명히 갈리면 라우팅이 적합하다. 서로 다른 자료원에서 독립적으로 근거를 모아야 한다면 병렬화나 워커 위임을 고려한다. 이때 후속 검색이 앞선 결과에 의존한다면 모든 단계를 병렬로 실행할 수 없다. **의존 관계가 있는 작업은 순서대로, 독립적인 작업은 동시에** 처리할 수 있는지를 먼저 판단해야 한다.

## 방법 — 선택, 검증, 중단을 어떻게 표현할까

이 논문은 **서베이**다. 새로운 학습 손실, 확률 모델, 정리의 증명이나 특정 모델의 학습 알고리즘을 제안하지 않는다. 원문에 유도할 논문 고유의 수식도 없다. 아래 표기는 여러 아키텍처의 결정을 비교하기 위한 **이 글의 설명용 표현**이다. 원문의 식이나 저자가 증명한 성질은 아니다.

질문을 $q$, 현재까지 확보한 근거를 $E_t$, 남은 실행 예산을 $B_t$라고 쓰면 다음 동작을 아래처럼 표현할 수 있다.

$$
a_t=\pi(q,E_t,B_t)
$$

$a_t$는 검색, 검색어 재작성, 다른 자료원 호출, 근거 평가, 답변 생성 가운데 선택한 동작이다. $\pi$는 그 동작을 고르는 정책을 뜻한다. 각 입력을 따로 적은 이유는 역할이 다르기 때문이다.

- **$q$**는 사용자가 실제로 요구한 정보다. 검색어가 여러 번 바뀌더라도 평가와 최종 답변은 이 요구를 기준으로 해야 한다.
- **$E_t$**는 이미 확보한 근거다. 무엇이 확인되었고 무엇이 빠졌는지 알아야 다음 검색을 정할 수 있다. 이전 결과를 무시하면 같은 검색을 반복할 수도 있다.
- **$B_t$**는 남은 호출·시간·자원 같은 운영상 한도다. 논문은 구체적인 예산 수치를 정하지 않지만, 제한된 계획 범위와 명시적 중단 기준을 권한다.

검색 결과 $D_t$가 들어왔을 때 관련성 평가를 통과한 부분을 $V(q,D_t)$라고 두면, 근거 상태의 갱신은 개념적으로 다음과 같이 쓸 수 있다.

$$
E_{t+1}=\operatorname{merge}\bigl(E_t,V(q,D_t)\bigr)
$$

이 식도 설명용이다. `merge`에는 단순 추가 이상의 판단이 들어간다. 같은 문서가 여러 경로로 검색되었는지, 새 문서가 이전 근거와 충돌하는지, 검색 결과가 원래 질문의 어느 부분을 뒷받침하는지를 확인해야 한다. 검색된 문서 전체를 검증 없이 $E_{t+1}$로 취급하면 교정 단계의 의미가 사라진다.

중단 역시 하나의 결정이다. 답을 만들 만한 근거가 모였는지, 예산이 끝났는지, 새 검색으로 얻는 정보가 부족한지를 구분해야 한다. 예산이 소진된 상태는 **충분한 근거를 찾은 상태와 다르다**. 둘 다 검색을 멈출 수는 있지만, 앞의 경우에는 답변 대신 근거 부족을 드러내는 처리가 필요할 수 있다. 논문의 자율성 제약과 과정 중심 평가를 구현 관점에서 읽으면 이 구분이 중요하다.

### 교정형 RAG: 검색 결과가 부적절하면 경로를 바꾼다

교정형 RAG(Corrective RAG)는 처음 검색한 문서를 그대로 생성기에 넘기지 않는다. 논문이 설명하는 구성은 초기 문서를 찾는 에이전트, 관련성을 평가하는 에이전트, 질의를 다시 쓰는 에이전트, 외부 자료를 찾는 에이전트, 답을 합성하는 에이전트로 나뉜다. 평가에서 부적절하거나 애매하다고 판단된 결과는 질의 재작성 또는 다른 출처 검색의 계기가 된다.

이 방식이 다루는 실패는 분명하다. **생성기가 아무리 정교해도 필요한 근거가 검색되지 않았다면 그 근거를 사용해 답할 수 없다.** 교정 단계는 답변 전에 검색의 결함을 발견하고 검색 경로를 바꾸려는 장치다. 다만 관련성 평가자가 필요한 문서를 잘못 제외할 수도 있고, 재검색에도 호출과 대기 비용이 든다. 서베이는 모든 작업에 적용할 공통 임계값이나 반복 횟수를 제공하지 않는다.

평가 대상도 둘로 나누어 볼 필요가 있다. 문서가 질문 주제와 관련 있는지와 **답에 필요한 사실을 실제로 담고 있는지**는 다르다. 관련성이 높은 문서라도 핵심 관계나 최신 정보가 빠져 있을 수 있다. 따라서 교정형 흐름을 구현한다면 주제 관련성만으로 종료하지 않고, 원래 질문의 요구를 충족할 근거가 있는지 확인해야 한다. 이는 논문의 검색 결과 평가와 응답 합성 구조에서 도출한 구현상의 해석이다.

### 적응형 RAG: 모든 질문에 같은 검색 비용을 쓰지 않는다

적응형 RAG(Adaptive RAG)는 질문의 복잡도를 분류해 경로를 고른다. 원문은 **검색 없이 생성, 한 단계 검색, 여러 단계 검색**의 세 경로를 설명한다. 단순 질문에는 불필요한 검색을 생략하고, 복합 질문에는 더 깊은 탐색을 배정하는 구성이다. 복잡도 판단에 작은 언어 모델을 쓰며, 과거 모델 결과와 질문 패턴에서 자동으로 라벨링한 데이터로 분류기를 학습하는 방식도 서술한다.

여기에는 교환 관계가 있다. 검색을 생략하면 해당 질문의 검색 비용은 줄지만, 잘못 분류된 질문은 필요한 외부 근거를 얻지 못한다. 여러 단계 검색으로 보낸 질문은 더 많은 정보를 모을 수 있으나 지연이 늘어난다. 따라서 분류기의 정확도만 볼 것이 아니라 **경로를 잘못 골랐을 때 답변 품질과 비용이 어떻게 바뀌는지** 함께 봐야 한다. 이는 논문이 제시한 구조에서 도출한 구현상의 해석이다.

특히 질문이 짧다는 이유만으로 검색이 불필요하다고 볼 수 없다. 현재 상태나 개인별 정보를 묻는 짧은 질문은 외부 자료가 필요할 수 있다. 반대로 문장이 길어도 이미 주어진 내용의 형식을 바꾸는 작업이라면 검색의 이득이 작을 수 있다. 원문이 든 경로 구분을 실제 서비스에 적용할 때는 표면적인 문장 길이보다 **어떤 종류의 근거가 필요한지**를 확인해야 한다.

![문서 관련성과 생성 답변을 점검하는 반복 흐름](/assets/img/posts/agentic-rag-survey/figure20.png){: w="800" }
_그림 20. 문서 관련성, 환각 여부, 답변 가능성을 점검해 재검색 또는 재생성을 반복하는 적응형 흐름_

교정형과 적응형은 서로 배타적인 분류가 아니다. 적응형 경로는 **처음에 검색을 얼마나 할지** 결정하고, 교정형 경로는 **검색해 얻은 결과를 받아들일지** 결정한다. 적응형 분류가 한 단계 검색을 골랐어도 결과가 부적절하면 교정이 필요할 수 있다. 반대로 모든 질문에 교정 루프를 실행하면 단순 질문의 비용 절감 효과가 줄어든다. 두 구조를 결합할 때는 초기 경로와 재검색 조건을 따로 명시해야 한다.

## 아키텍처 분류 — 무엇을 중앙에서 결정하는가

### 단일 에이전트와 다중 에이전트

**단일 에이전트 RAG**에서는 하나의 조정자가 질문을 보고 자료원을 고른다. 원문은 구조화 데이터에 대한 Text-to-SQL, 비정형 문서의 벡터 검색, 실시간 정보의 웹 검색, 추천 시스템을 선택지로 든다. 조정과 통합 지점이 적어 구현·운영이 비교적 단순하다. 논문은 도구와 자료원이 제한된 환경에 적합하다고 본다. 단일 에이전트라고 해서 항상 한 자료원만 쓰는 것은 아니다. 질문에 맞는 경로를 선택하고 결과를 통합할 수 있다.

**다중 에이전트 RAG**에서는 조정자가 역할별 검색 에이전트에 일을 배정한다. 예를 들어 SQL, 문서 검색, 웹·API, 추천을 나누어 맡을 수 있고 독립적인 검색은 병렬로 실행할 수 있다. 질문에 서로 다른 종류의 자료가 필요하면 역할 분담이 자연스럽다. 반면 결과 형식과 신뢰도가 다를 때 이를 합성하는 일, 에이전트 간 통신, 중복 검색을 통제하는 일이 추가된다. 각 에이전트가 관련 있는 답을 냈다는 사실만으로 전체 답의 일관성이 보장되지는 않는다.

**계층형 RAG**는 여러 에이전트를 나열하는 데서 더 나아가 상위 에이전트가 자료원의 우선순위와 위임 대상을 정한다. 하위 에이전트가 검색한 결과를 상위 단계에서 모아 답을 만든다. 원문은 신뢰도가 다른 금융 자료원을 우선순위에 따라 다루는 예를 든다. 감독과 우선순위 조정이 필요한 대신 계층을 거치는 지연과 자원 배분 문제가 생긴다. 상위 단계가 모든 결과를 다시 검토한다면, 하위 작업을 병렬로 실행해 줄인 시간 중 일부가 통합 단계에서 다시 쓰일 수 있다.

![다중 에이전트의 역할 분담](/assets/img/posts/agentic-rag-survey/figure17.png){: w="800" }
_그림 17. 자료원별 검색을 나누어 실행하고 결과를 합성하는 다중 에이전트 구조_

에이전트 수만으로 복잡한 추론 능력을 판단하기는 어렵다. 하나의 에이전트가 여러 도구를 차례로 사용하며 검색을 교정할 수 있고, 여러 에이전트를 두어도 위임과 결과 결합이 고정되어 있다면 실행의 자율성은 제한적일 수 있다. 따라서 설계할 때는 **몇 명이 일하는가**, **누가 다음 단계를 결정하는가**, **중간 결과가 경로를 바꿀 수 있는가**를 각각 확인해야 한다.

### 그래프 기반 검색과 문서 작업 흐름

그래프 기반 에이전틱 RAG는 **연결 관계 자체가 질문의 일부**일 때 중요하다. 논문이 소개하는 Agent-G는 그래프 지식 기반과 비정형 문서를 함께 검색한다. 검색기 묶음에서 필요한 출처를 고르고, 비평 모듈(critic module)이 결과의 관련성과 품질을 평가하며, 부족한 결과는 다시 검색한다. 그래프는 개체 간 관계를, 문서는 그 관계를 설명하는 문맥을 제공한다.

GeAR는 기본 검색기의 결과를 그래프의 연결 개체로 확장해 여러 홉이 필요한 질문을 다루고, 에이전트가 확장 경로를 사용할지 결정한다. 단일 문서 안에 답이 없는 질문에서는 첫 개체에서 다음 개체로 이어지는 경로가 검색의 단서가 된다. 그러나 확장 경로가 길어질수록 처음 질문과 거리가 먼 결과도 들어올 수 있다. 그래프의 개체·관계가 부실하면 그 위에서 확장한 검색 경로도 신뢰하기 어렵다. 이는 원문이 그래프 RAG의 데이터 의존성과 통합 복잡성을 한계로 드는 이유와 이어진다.

![그래프와 문서 검색을 함께 쓰는 Agent-G](/assets/img/posts/agentic-rag-survey/figure21.png){: w="700" }

에이전틱 문서 워크플로(Agentic Document Workflows, ADW)는 답변 생성보다 긴 **문서 처리 과정 전체**를 다룬다. 원문이 든 송장 예에서는 필드 파싱, 계약 검색, 처리 단계의 상태 유지, 업무 규칙 적용, 구조화된 권고문 생성이 이어진다. 단순 문서 질의응답과 달리 현재 어떤 문서를 처리하는지, 어떤 단계가 끝났는지, 어느 규칙을 확인했는지가 다음 단계에 영향을 준다. 이 때문에 ADW는 RAG에 파싱, 상태 관리, 업무 처리를 결합한 형태로 읽는 편이 정확하다.

이 구조에서는 검색 근거뿐 아니라 **작업 상태**도 결과의 일부다. 파싱한 송장 필드가 잘못되면 계약 검색 대상부터 달라질 수 있고, 계약을 제대로 찾아도 적용할 업무 규칙을 누락하면 최종 권고가 달라진다. 검색 품질만 재는 평가로는 이런 단계별 실패를 구분하기 어렵다. 논문의 과정 중심 평가 요구가 문서 작업 흐름에서 특히 구체적인 이유다.

## 구현 관점에서 — 검색기보다 제어 흐름을 명시하기

이 서베이에는 그대로 옮길 단일 Algorithm 블록이나 모델 학습 루프가 없다. 아래는 원문의 **적응형 라우팅과 교정형 검색**을 합쳐 그린 설명용 의사코드다. 특정 프레임워크의 API나 논문이 지정한 유일한 구현 절차는 아니다.

```python
def answer(query, sources, max_rounds):
    # query: Text 1개
    # sources: 사용 가능한 자료원 목록, (S,)
    # max_rounds: 검색 회차의 상한을 나타내는 설정값
    route = classify_query(query)  # {"direct", "single", "multi"}

    if route == "direct":
        return generate(query, evidence=[])

    evidence = []                   # 근거 레코드 목록, (K,); 처음에는 K=0
    current_query = query

    for round_index in range(max_rounds):
        selected = choose_sources(current_query, sources, route)
        # selected: 이번 회차의 자료원 목록, (A,), A <= S

        candidates = retrieve(current_query, selected)
        # candidates: 출처·본문·검색 경로를 담은 레코드, (K_round,)

        accepted, uncertain = evaluate_relevance(query, candidates)
        # accepted, uncertain: 길이가 달라질 수 있는 레코드 목록

        evidence = merge_evidence(evidence, accepted)
        # evidence: 중복과 충돌을 검토한 누적 근거, (K,)

        if sufficient_for_answer(query, evidence):
            return generate(query, evidence)

        if round_index + 1 == max_rounds:
            break

        current_query = rewrite_query(query, evidence, uncertain)
        route = "multi"             # 추가 검색이 필요하다고 판정된 경로

    return report_insufficient_evidence(query, evidence)
```

`(S,)`, `(K,)`, `(A,)`는 신경망 텐서의 고정 차원이라기보다 **리스트에 담긴 자료원·문서·활성 경로의 개수**를 나타낸다. 서베이는 임베딩 차원이나 배치 텐서의 shape을 지정하지 않으므로 그 값을 만들어 넣을 수 없다. 실제 구현에서 중요한 자료 구조는 문서 본문만이 아니라 출처와 검색 경로를 함께 보존하는 **근거 레코드**다. 그렇지 않으면 답변을 만든 뒤 어떤 출처가 어느 주장에 기여했는지 추적하기 어렵다. 이는 논문의 추적 가능성과 감사 가능성 요구를 코드 구조로 옮긴 해석이다.

코드에서 특히 확인할 지점은 다음과 같다.

1. **직접 생성 경로의 조건**: 적응형 RAG에서는 검색을 건너뛸 수 있다. 그러나 최신 정보나 개인별 상태가 필요한 질문을 이 경로로 보내면 외부 근거가 빠진다. 복잡도 분류 결과와 질문에 필요한 정보의 유형을 함께 점검해야 한다.
2. **원래 질문과 재작성 질문의 구분**: `current_query`는 검색을 위한 표현이며, 사용자의 요구인 `query`를 대체하지 않는다. 평가와 최종 답변을 원래 질문에 맞추어야 검색어 재작성 중 목표가 바뀌는 일을 발견하기 쉽다.
3. **반복의 종료 조건**: 관련성이 낮다는 평가만으로 재검색을 계속하면 호출이 끝나지 않을 수 있다. `max_rounds`는 제한된 계획 범위를 표현한 설정값이며, 논문이 권장 수치를 제시한 것은 아니다. 상한에 도달했을 때는 근거가 충분해서 멈춘 것인지 별도로 구분한다.
4. **근거의 병합**: 여러 자료원과 회차의 결과는 중복되거나 충돌할 수 있다. 단순히 문자열을 이어 붙이는 것으로는 어느 주장을 뒷받침하는지 알기 어렵다. 관련성 판단과 출처 정보를 보존해야 한다.
5. **근거 부족 시 응답**: 여러 번 검색했다는 사실이 답의 충분성을 보장하지 않는다. 원문의 과정 평가·거버넌스 논의를 따른다면, 근거 부족을 생성 성공과 구분해 기록하는 편이 합리적이다.
6. **검색과 평가의 순서**: 새로운 문서가 들어올 때마다 평가를 실행한다면 재검색의 근거를 얻을 수 있지만 호출 비용도 증가한다. 평가를 생략할 때는 부적절한 문서가 바로 답변으로 넘어갈 가능성을 감수해야 한다.

경계 조건에도 주의해야 한다. `max_rounds`가 검색을 허용하지 않는 설정이라면 코드의 직접 생성 경로와 근거 부족 처리를 먼저 정의해야 한다. 자료원 목록이 비어 있거나 선택된 자료원에서 결과가 없을 때도 재작성만 반복해서는 새 근거가 생기지 않는다. 이런 처리는 서베이의 고정된 구현 규격이 아니라, 자율적 반복에 명시적 경계를 두라는 지침을 의사코드에 적용한 것이다.

일반적인 생성모델 논문의 **학습 루프와 샘플링 루프**에 해당하는 절차는 여기서 중심이 아니다. 대응해서 구분할 흐름은 **사전에 구성하는 검색기·분류기·도구 접근 정책**과 **질문을 받을 때 실행되는 라우팅·검색·평가 반복**이다. 원문은 적응형 RAG의 분류기 학습을 설명하지만, 이 서베이 자체의 학습 데이터 구성, 손실 함수, 학습 절차 또는 하이퍼파라미터를 실험으로 제시하지 않는다. 서베이에 없는 학습 루프를 코드로 채우는 대신, 실제 실행 중 어떤 결정이 바뀌는지 드러내는 편이 이 논문을 구현 관점에서 읽는 데 도움이 된다.

## 표에서 읽어야 할 설계상의 교환 관계

원문 Table 2는 전통적 RAG, 에이전틱 RAG, ADW를 기능별로 비교한다. 전통적 RAG는 개별 검색·생성 작업과 빠른 구축에, 에이전틱 RAG는 동적인 다중 단계 추론에, ADW는 상태를 유지하는 문서 중심 업무에 초점을 둔다. 기억 모듈, 외부 도구, 워크플로 조정, 복잡한 추론의 비중이 달라지면서 조정 복잡성과 자원 비용도 달라진다는 것이 이 표에서 읽을 지점이다. 표의 ‘높은 정확도’ 같은 표현은 이 서베이가 자체 실험으로 측정한 수치가 아니라 비교 범주의 정성적 설명으로 다뤄야 한다.

Table 3은 아키텍처를 에이전트 수, 제어 구조, 지식 표현, 지식 의존성, 추론 방식과 깊이, 검색 적응성, 확장성, 지연, 엔지니어링 복잡도 등에 배치한다. 중요한 항목을 설계 결정에 맞춰 다시 묶으면 다음과 같다.

| 선택 | 제어와 지식의 형태 | Table 3이 제시하는 적합한 상황 | 지불하는 비용 |
|---|---|---|---|
| 단일 에이전트 | 중앙 제어, 주로 비정형 지식 | 단순 QA와 라우팅 | 복합 도메인 추론의 폭이 제한될 수 있다. |
| 다중 에이전트 | 여러 역할이 나뉜 제어, 비정형 또는 혼합 지식 | 여러 도메인의 정보 합성 | 에이전트 간 조정과 결과 통합이 필요하다. |
| 계층형·교정형 | 감독 또는 평가 기반 제어 | 신뢰성이 중요한 작업 | 반복 평가와 계층 이동으로 지연·구현 복잡성이 늘어난다. |
| 그래프·문서 중심 | 관계 그래프 또는 단계별 문서 상태 | 관계를 따라가는 질문과 문서 처리 | 그래프·문서 구조의 품질에 민감하고 구성도 복잡하다. |

이 표를 읽을 때 두 가지 혼동을 피해야 한다. 첫째, Table 3은 단일 에이전트의 검색 적응성을 ‘제한적’으로, 다중 에이전트나 교정형을 ‘높음’으로 표시한다. 이를 **단일 에이전트는 동적 라우팅을 못 한다**는 뜻으로 읽으면 앞의 단일 에이전트 설명과 충돌한다. 단일 에이전트도 질문에 따라 SQL, 벡터 검색, 웹 중에서 선택할 수 있다. 표는 여러 경로의 협업이나 반복 교정까지 포함한 **상대적 설계 범위**로 읽는 편이 자연스럽다.

둘째, Table 1과 Table 2의 확장성 항목은 장점 중심으로 적혀 있지만 본문은 에이전트가 늘면 계산 자원과 조정 부담이 커진다고 명시한다. **독립 작업을 병렬로 처리할 수 있다는 성질**과 **높은 질의량에서 낮은 비용을 유지한다는 성질**은 같지 않다. 표의 정성적 강점을 실제 처리량이나 지연 보장으로 바꾸어 쓸 수는 없다. 아키텍처를 고른 뒤에는 대상 질문과 자료원에서 직접 측정해야 한다.

## 적용 사례를 읽는 방법

서베이는 고객 지원, 의료, 법률, 금융, 교육, 멀티모달 작업을 사례로 제시한다. 이 사례들은 어떤 자료원과 제어 흐름을 조합할 수 있는지 보여준다.

- **고객 지원**에서는 주문 데이터베이스의 상태와 배송 API의 최신 정보를 결합한다. 단일 에이전트 라우팅이나 복잡도에 따른 적응형 검색의 예다.
- **의료**에서는 환자 기록과 의료 문헌·지침을 함께 사용하거나, 그래프의 질병·증상 관계를 문서 설명과 연결한다. 출처의 적합성과 검증 과정이 중요해지는 이유를 보여준다.
- **법률·계약 분석**에서는 조항 추출, 관련 규칙 검색, 표준 조건과의 차이 확인처럼 문서의 여러 단계가 연결된다.
- **금융·보험**에서는 실시간 수치와 과거 자료, 정책 또는 계약 조건을 함께 다룬다. 여러 자료원의 시점과 신뢰도를 조정해야 한다.
- **교육**에서는 학습자별 설명이나 여러 자료를 종합한 연구 보고서를 예로 든다.
- **멀티모달 시장 조사**에서는 연결된 자료원에서 텍스트와 이미지·영상 정보를 함께 모으는 상황을 설명한다.

같은 ‘여러 자료원을 쓴다’는 사례라도 필요한 제어는 다르다. 배송 현황은 정해진 데이터베이스와 API를 순서대로 조회하는 경로로 충분할 수 있다. 여러 연구 문헌의 관계를 따라가야 하는 질문은 첫 검색 결과를 바탕으로 다음 검색 대상을 정해야 할 수 있다. 송장 처리에서는 근거 검색 외에 파싱 결과와 업무 단계의 상태를 유지해야 한다. 사례를 읽을 때는 도메인 이름보다 **어떤 중간 결정이 필요한지**에 주목하는 편이 아키텍처 선택에 유용하다.

원문의 개별 “Integrated Response”에는 배송 예정 시각, 고용 규모, 성장률, 의료 상관관계, 송장 금액 같은 구체적인 문장이 들어 있다. 이들은 **워크플로를 설명하기 위한 응답 예시**이지, 이 서베이가 해당 수치를 측정하거나 사실 검증한 결과가 아니다. 따라서 방법의 성능 근거로 쓰지 않는다.

논문이 나열하는 개발 도구도 같은 관점에서 볼 수 있다. LangChain·LangGraph는 구성 요소와 루프·상태 관리, LlamaIndex는 문서 작업 흐름, Hugging Face Transformers와 Qdrant는 모델·검색 구성, CrewAI·AG2는 다중 에이전트 조정, Neo4j와 벡터 데이터베이스는 관계·유사도 검색에 놓인다. Semantic Kernel, Amazon Bedrock, Vertex AI, IBM watsonx.ai, OpenAI Swarm도 구현 수단으로 언급된다. 이 목록은 **서베이에 실린 도구의 역할 지도**이며, 같은 조건에서 성능을 비교한 실험 표는 아니다.

도구 이름보다 먼저 정할 것은 제어의 책임이다. 예를 들어 상태를 저장할 수 있는 도구를 선택해도 어떤 상태를 언제 갱신하고 폐기할지 정하지 않으면 문서 작업의 일관성이 저절로 생기지 않는다. 여러 에이전트를 실행할 수 있는 도구를 선택해도 결과의 충돌을 해결하고 종료를 판단하는 기준은 설계자가 명시해야 한다. 이는 논문의 아키텍처 비교와 자율성 제약을 도구 선택에 연결한 해석이다.

## 평가하려면 무엇을 재야 할까

이 서베이에는 저자가 새 에이전틱 RAG 시스템을 구현해 측정한 실험 설정, 점수표, 제거 실험(ablation)이 없다. 그래서 특정 구성 요소를 빼면 성능이 얼마나 달라진다는 결론을 만들 수 없다. 대신 Section 11은 검색, 여러 홉의 추론, 답변 생성에 사용할 수 있는 기존 벤치마크와 데이터셋을 모아 둔다.

| 평가 대상 | 원문에 제시된 예 | 확인할 수 있는 실패 |
|---|---|---|
| 검색·순위화 | BEIR, MS MARCO, TREC | 필요한 문서가 검색 후보나 상위 결과에 들어오는가 |
| 여러 문서를 잇는 질문 | MuSiQue, 2WikiMultihopQA, HotpotQA | 첫 근거를 찾은 뒤 다음 근거까지 이어지는가 |
| 답변과 근거의 관계 | RAGBench | 검색 결과를 이용한 답의 품질을 어떻게 설명할 수 있는가 |
| 표준화된 실험 구성 | BERGEN, FlashRAG | 서로 다른 RAG 방법을 어떤 실험 조건에서 비교하는가 |
| 그래프 기반 질문 | GraphQA, GNN-RAG 관련 평가 | 개체와 관계를 통한 검색·추론이 작동하는가 |
| 검색 견고성 | NoMIRACL | 검색의 관련성 판단이 흔들리는 상황을 다룰 수 있는가 |

이 표에서 BERGEN과 FlashRAG는 데이터셋 이름과 같은 방식으로 읽으면 안 된다. 원문은 BERGEN을 **RAG 벤치마킹 라이브러리**, FlashRAG를 **방법과 데이터셋을 지원하는 툴킷**으로 소개한다. 평가 대상 데이터와 실험을 구성하는 도구의 역할을 구분해야 한다.

원문은 BEIR을 **17개 데이터셋**에 걸친 검색 평가로, RAGBench를 **100,000개 예시**를 가진 평가 자료로 소개한다. 이 수치는 벤치마크의 설명이지 에이전틱 RAG의 성능 향상 수치가 아니다. Table 4와 Table 5는 QA, 대화, 추천, 추론, 요약, 코드 검색, 견고성, 수학, 번역 등 하위 작업과 데이터셋을 유사한 범주로 반복해 싣는다. Section 11이 “Table 5”를 가리키는 한편 유사한 목록이 두 표에 모두 나타나므로, 여기서는 이들을 독립적인 실험 결과처럼 세지 않았다.

출력의 정답 여부만으로는 에이전트가 **어떤 경로로 그 답을 얻었는지** 평가할 수 없다. 논문은 추론 경로, 계획 깊이, 변화하는 문맥에 대한 적응, 잡음이 섞인 검색에서의 견고성, 도구 사용과 비용 효율을 함께 보아야 한다고 주장한다. 구현한다면 질문별로 선택한 경로, 호출한 자료원, 재검색 여부, 각 단계의 평가 결과, 최종 근거를 기록해야 이런 평가가 가능하다. 이는 논문의 과정 중심 평가 요구를 운영 항목으로 풀어 쓴 것이다.

과정 기록은 실패를 분리하는 데도 쓰인다. 필요한 문서가 검색 후보에 없었다면 검색 또는 색인의 문제다. 문서는 있었지만 평가 단계에서 제외되었다면 관련성 판단의 문제다. 적절한 근거가 남아 있는데도 답이 틀렸다면 생성과 근거 통합을 살펴봐야 한다. 최종 답의 점수 하나만 보면 이 세 실패가 섞인다. 특히 에이전트와 도구가 많아질수록 어느 단계가 답을 바꾸었는지 추적할 수 있어야 수정 방향을 정할 수 있다.

## 비용과 트레이드오프 — 언제 에이전트를 늘릴까

이 서베이에는 에이전트별 GPU 시간, 파라미터 수, 토큰 사용량, 지연 수치가 없다. 그래도 비용이 생기는 위치는 실행 구조에서 알 수 있다. 다음 식은 **논문의 측정 결과가 아니라 워크플로를 비교하기 위한 단순한 비용 계산**이다.

$$
T_{\text{순차}} \approx \sum_i T_i,\qquad
T_{\text{병렬}} \gtrsim \max_i T_i + T_{\text{통합}}
$$

순차 체이닝에서는 앞 단계가 끝나야 다음 단계가 시작되므로 각 단계의 시간이 쌓인다. 독립 검색을 병렬로 돌리면 가장 늦은 검색을 기다린 뒤 결과를 통합한다. 실제 시스템에서는 라우팅·통신·대기 시간도 더해지고, 같은 자원을 두고 작업이 경쟁할 수 있다. 따라서 병렬 에이전트를 추가하면 **대기 시간의 일부**를 줄일 가능성은 있지만 **총 호출량과 메모리 사용량**까지 자동으로 줄어드는 것은 아니다. 검색 결과가 많아지면 통합 단계에서 읽고 비교할 문맥도 늘어난다.

적응형 경로의 기대 호출 비용은 다음처럼 생각할 수 있다. 이것 역시 논문의 공식이 아니라 비용이 어디서 나오는지 보여 주는 설명용 표기다.

$$
\mathbb{E}[C]
=
C_{\text{분류}}
+
\sum_{r\in\{\text{직접},\,\text{한 단계},\,\text{여러 단계}\}}
P(r)\,C_r
$$

$C_{\text{분류}}$는 질문의 경로를 고르는 비용이고, $P(r)$는 실제 질문들에서 경로 $r$이 선택되는 비율, $C_r$는 그 경로의 비용이다. 분류기 비용을 치르더라도 많은 질문을 저렴한 경로로 보낼 수 있다면 평균 비용이 낮아질 수 있다. 그러나 이 식만 최소화하면 모든 질문을 직접 생성 경로로 보내는 선택이 유리해 보일 수 있다. 어려운 질문을 그 경로로 잘못 보내면 호출비는 낮아져도 필요한 근거가 사라진다. **비용은 근거 충족과 답변 품질을 함께 확인하면서** 비교해야 한다.

재검색도 같은 관점에서 판단할 수 있다. 관련성 평가와 질의 재작성에 드는 비용을 추가했을 때, 처음 검색에서 놓친 근거를 얼마나 회복하는지가 중요하다. 그 이득이 거의 없는 질문에까지 반복을 적용하면 지연만 늘어난다. 반대로 근거가 여러 자료원에 흩어진 질문에 단일 검색만 허용하면 비용은 낮아도 답이 불완전할 수 있다. 이 교환 관계가 논문이 제안하는 비용 인식형 계획, 선택적 도구 호출, 검색 깊이 조절이라는 연구 방향으로 이어진다.

논문이 정리한 운영상 판단은 다음 순서로 이해할 수 있다.

1. **검색 품질을 먼저 확보한다.** 색인 범위나 검색 결과가 계속 부실하면 에이전트의 추가 추론도 필요한 근거를 만들어 내지 못한다.
2. **범위가 좁은 질문에는 간단한 경로를 쓴다.** 사실 검색이라면 모듈러 RAG로 충분할 수 있다.
3. **여러 자료원이 필요한 질문에 위임·병렬화를 검토한다.** 역할 분담의 이득과 추가 조정 비용을 함께 평가한다.
4. **교정과 반복에 상한을 둔다.** 검증 이득이 추가 지연과 호출 비용을 정당화하는지 관찰한다.
5. **도메인의 규칙과 자료 구조를 활용한다.** 논문은 의료·금융·법률처럼 구조화된 지식과 명시적 제약이 있는 분야에서 에이전트 설계의 이점이 클 수 있다고 본다.

결국 경량화의 목표는 에이전트나 검색 단계를 무조건 줄이는 데 있지 않다. **질문의 요구를 충족하는 데 필요한 경로만 활성화하고, 그 경로가 실제로 근거를 확보했는지 확인하는 것**이다. 원문이 계산 효율과 지속 가능성을 열린 연구 문제로 남긴 만큼, 아키텍처의 정성적 장점을 비용 절감의 실측 결과로 받아들여서는 안 된다.

## 한계와 남은 연구 문제

저자들이 명시한 미해결 문제는 여섯 갈래다.

**첫째, 에이전트의 조정과 제어다.** 여러 에이전트가 부분적인 정보만 보고 움직이거나 목표가 충돌하면 전체 행동을 예측하기 어렵다. 현재의 휴리스틱 규칙과 프롬프트 중심 조정에는 수렴 보장이 제한적이라고 논문은 설명한다. 한 에이전트의 잘못된 결과가 다른 단계로 전파되는 문제도 남는다.

**둘째, 결과뿐 아니라 과정을 평가해야 한다.** 최종 답이 맞더라도 불필요한 도구를 반복 호출했거나 우연히 맞는 출처를 골랐을 수 있다. 반대로 검색에 잡음이 들어왔을 때 경로를 적절히 수정했는지도 출력 점수 하나로는 알기 어렵다. 저자들은 계획 깊이, 적응성, 견고성, 비용까지 보는 표준화된 평가를 요구한다.

**셋째, 장기 기억의 관리다.** 기억을 오래 보존하면 오래된 정보나 편향이 축적될 수 있고, 잦은 갱신은 잘못된 내용을 다시 강화할 수 있다. 무엇을 남기고 외부 최신 지식과 어떻게 조정할지 열려 있다.

**넷째, 계산 비용과 지속 가능성이다.** 협업과 반복 검색은 지연과 자원 사용량을 늘린다. 저자들은 활성 에이전트 수, 도구 호출, 검색 깊이를 질문에 맞게 조절하는 비용 인식형 계획과 가벼운 조정 방식을 연구 과제로 둔다.

**다섯째, 안전·신뢰·거버넌스다.** 자율적 도구 사용은 허가되지 않은 동작이나 편향된 결정을 일으킬 수 있고, 다중 에이전트 환경에서는 책임을 특정하기도 어렵다. 결정 경로의 기록, 사람의 감독, 권한 범위 설정이 필요하다.

**여섯째, 다른 도메인으로의 일반화다.** 원문은 많은 시스템이 특정 분야나 잘 정리된 벤치마크에서 평가되어, 데이터 특성과 규제가 다른 환경에도 잘 옮겨지는지 불분명하다고 밝힌다. 도메인별 조정에 덜 의존하는 계획·검색 정책이 연구 방향이다.

구현 관점에서 덧붙일 점은 **서베이의 아키텍처 표를 배포 성능의 순위표처럼 사용하기 어렵다**는 것이다. 이 글은 여러 방식을 비교하는 분류와 설계 지침을 제공하지만, 같은 검색 색인·모델·질문·예산 아래에서 각 방식을 실행한 통제 실험은 제시하지 않는다. 어떤 방식이 실제 서비스에서 더 빠르거나 정확한지는 대상 질문과 자료원에 맞춘 측정이 필요하다. 특히 사례 속 응답 문장과 Table 2·3의 정성적 강점은 그 측정을 대신하지 않는다.

이 서베이에서 도출할 수 있는 설계 기준은 **질문의 복잡도에 맞는 제어 범위를 고르고, 검색 근거와 결정 경로를 함께 검증하는 것**이다. 에이전트가 유용한 순간은 여러 번 검색했다는 사실 자체보다, 이전 결과를 보고 다음 검색과 중단 여부를 더 적절하게 결정할 수 있을 때다.
