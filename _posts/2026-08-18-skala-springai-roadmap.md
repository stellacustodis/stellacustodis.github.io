## 이 과정을 어떤 상태에서 들었는가

Spring AI 과정은 8월 18일(화)부터 20일(목)까지 3일간 진행됐다. 바로 앞 과정이 Java와 Spring Boot 5일이었지만, 그것으로 Java와 Spring이 손에 익었다고 말하기는 어렵다. 나는 Python으로 모델을 다뤄 왔고 백엔드 프레임워크의 관례에는 아직 익숙하지 않다.

그래서 이 시리즈는 Spring AI의 기능을 소개하는 글이 아니라, **Java와 Spring의 관례가 아직 몸에 붙지 않은 상태에서 LLM 애플리케이션 구조를 어떻게 읽어 냈는가**를 기록한 글이다. 애노테이션 하나가 무엇을 하는지, 왜 이 클래스는 `@Configuration`이고 저 클래스는 `@Service`인지를 매번 다시 확인해야 했다. 그 확인 과정을 생략하지 않고 적었다.

역설적이지만 이 조건이 과정을 이해하는 데 불리하기만 하지는 않았다. LLM 쪽 개념(토큰, 임베딩, 컨텍스트 윈도우, 환각)은 이미 익숙했기 때문에, 내가 새로 배워야 할 것은 **그 개념들이 Spring이라는 컨테이너 안에서 어떤 자리를 차지하는가** 하나로 좁혀졌다. 과정의 첫 장이 Spring AI가 아니라 Spring Boot 계층 구조로 시작하는 것도 같은 이유였다고 본다.

## 이 과정의 전제

교재가 반복해서 강조하는 문장이 하나 있다.

> AI는 새로운 계층이 아니라 기존 계층에 얹히는 하나의 관심사다.
{: .prompt-info }

이 문장은 과정 전체의 설계 원칙이다. LLM을 붙인다고 해서 Controller-Service-Repository 구조를 버리는 것이 아니라, 그 구조 위에 `config`(빈 구성) · `rag`(근거) · `tools`(행동) · `advisor`(공통 관심사)라는 축이 추가된다. 그래서 3일 내내 반복되는 판단 기준도 결국 Spring의 오래된 질문들과 같다. 이 코드는 어느 계층에 있어야 하는가, 이 관심사는 어디서 가로채야 하는가, 이 실패는 누가 처리해야 하는가.

`ChatClient`를 컨트롤러에서 직접 부르지 않는다는 규칙이 첫날 실습의 합격 기준으로 나오는 것도 이 때문이다. AI 호출을 서비스 계층에 두면 프롬프트를 고쳐도 웹 계층은 그대로이고, 모델 공급자를 바꿔도 업무 코드는 손대지 않는다.

## 전체 흐름

| 일차 | 날짜 | 핵심 주제 | 도달 목표 |
|---|---|---|---|
| 1일차 | 08/18(화) | Spring Boot 계층 구조, Spring AI 아키텍처, 3대 추상화, 개발환경, ChatClient | AI 호출이 계층 어디에 놓이는지 설명하고, 용도별 `ChatClient` 빈을 구성해 첫 응답을 받는다. |
| 2일차 | 08/19(수) | 프롬프트·옵션·스트리밍, 구조화 출력·멀티모달, 워크플로 패턴, RAG와 RAG 심화 | 같은 모델로 답 품질을 끌어올리고, 응답을 자바 객체로 받으며, 사내 문서를 근거로 답하게 만든다. |
| 3일차 | 08/20(목) | Tool Calling·Agent·MCP, 도구 안전 설계, Advisor·메모리·운영, 종합 실습 | 모델이 우리 함수를 부르게 하되 실행 권한은 코드가 쥐고, 공통 관심사를 Advisor 체인으로 모은다. |

```text
1일차: 추상화와 계층 — 모델을 "부르는" 법
    ↓
2일차: 입력과 출력 — 잘 묻고, 객체로 받고, 근거를 붙인다
    ↓
3일차: 행동과 운영 — 도구를 쥐여 주고, 통제 장치를 두른다
```

1일차는 Spring AI가 무엇을 추상화했는지 확인하는 날이다. `ChatModel`·`EmbeddingModel`·`VectorStore` 세 인터페이스가 뼈대이고, 그 위에 `ChatClient`라는 Fluent API가 얹힌다. 공급자 교체가 의존성 한 줄과 `application.yml`만으로 끝난다는 주장을 실제 `build.gradle`에서 확인하는 것이 첫날의 실질적 목표다.

2일차는 모델을 바꾸지 않고 답을 좋게 만드는 날이다. 프롬프트를 4요소(역할·맥락·지시·형식)로 다시 쓰고, `.entity(Class)`로 문자열 파싱 코드를 지우고, `QuestionAnswerAdvisor`로 검색과 근거 주입을 한 줄에 맡긴다. 이날 배우는 것 중 실무에서 가장 먼저 필요해지는 것은 화려한 기법이 아니라 **실패 복구**다. 구조화 출력은 대부분 성공하지만 그 "대부분"이 운영에서는 장애 알람이 된다.

3일차는 말하는 AI를 일하는 AI로 바꾸는 날이다. `@Tool`을 붙인 평범한 메서드가 도구가 되고, 모델은 그 함수를 실행하는 것이 아니라 어떤 인자로 부를지만 결정한다. 실행은 우리 코드가 하므로 권한 검증도 우리 책임이다. 이 비대칭이 3일차 내용 전체를 관통한다.

## 3일을 관통하는 다섯 문장

교재 곳곳에 [체크]·[주의] 상자로 흩어져 있지만, 정리해 보면 반복되는 원칙은 다섯 개였다.

1. **판단은 모델, 실행은 우리 코드다.** 도구·에이전트·보안 이야기가 전부 이 한 줄에서 갈라져 나온다.
2. **권한은 프롬프트가 아니라 코드로 강제한다.** 프롬프트에 적은 지시는 지켜지지 않을 수 있고, 모델은 사용자 ID를 지어낼 수 있다.
3. **RAG 답이 틀렸으면 검색 결과를 먼저 눈으로 본다.** 근거에 답이 없으면 프롬프트를 아무리 고쳐도 좋아지지 않는다.
4. **Advisor의 순서가 곧 정책이다.** 차단은 언제나 저장보다 앞에 있어야 한다.
5. **상한 없는 반복은 비용 사고다.** 에이전트 루프에도, 교정 루프에도 횟수 제한을 건다.

이 다섯 문장은 각 일차의 글에서 코드로 다시 나온다.

## 실습 환경과 샘플 코드

실습은 폴더 하나가 실습 하나인 구조로 배포됐다. `01_간식추천_3계층`부터 `14_SSE와추적ID`까지 번호가 붙은 독립 Gradle 프로젝트와, 교재 장 번호를 그대로 딴 `ch03_chatclient`~`ch12_ops` 참조 예제가 함께 제공됐다. 각 프로젝트는 다른 장을 참조하지 않고 혼자 돌아간다.

공통 스택은 Java 21 toolchain, Spring Boot, Spring AI, springdoc-openapi(Swagger UI)다. 모델 공급자는 OpenAI이고 채팅은 `gpt-4o-mini`, 임베딩은 `text-embedding-3-small`을 기본값으로 쓴다. 키는 `application.yml`에 자리표시자만 두고 환경변수로 주입한다.

```yaml
spring:
  ai:
    openai:
      # 키는 소스에 넣지 않는다.  export OPENAI_API_KEY="sk-..."
      api-key: ${OPENAI_API_KEY}
      chat:
        options:
          model: gpt-4o-mini
          temperature: 0.7
      embedding:
        options:
          model: text-embedding-3-small
```

한 가지 미리 적어 둘 것이 있다. **교재 슬라이드와 배포된 샘플 코드의 버전이 일치하지 않는다.** 슬라이드의 `build.gradle` 예시는 Spring Boot `4.1.0`과 `spring-ai-bom:2.0.0`을 쓰는데, 실제 샘플 프로젝트는 대부분 Spring Boot `3.5.16`과 `spring-ai-bom:1.1.8` 조합이다(`01_간식추천_3계층`만 슬라이드와 같은 조합이다). 문서를 보고 따라 치다가 의존성이 해결되지 않으면 이 차이를 먼저 확인하는 편이 빠르다. 이 시리즈의 코드는 실제로 배포된 샘플을 기준으로 인용한다.

벡터 저장소는 8장 전까지는 필요 없다. RAG 구간에서도 기본값은 인메모리 `SimpleVectorStore`이고, `docker-compose.yml`로 pgvector를 띄워 볼 수 있게 되어 있다.

## 글을 나눈 기준

하루치를 한 편으로 쓰면 글이 지나치게 길어지고, 개념 사이의 연결이 오히려 안 보인다. 그래서 이번 시리즈는 **하루를 여러 편으로 나눠** 각 편이 하나의 질문에 답하도록 구성했다.

| 편 | 다루는 질문 |
|---|---|
| 1일차 ① 계층 | AI 호출은 어느 계층에 두어야 하는가 |
| 1일차 ② 아키텍처 | Spring AI는 무엇을 추상화했고, 공급자 교체는 정말 설정만으로 되는가 |
| 1일차 ③ ChatClient | 모델을 부르는 창구를 어떻게 만들고 나누는가 |
| 2일차 ① 프롬프트 | 모델을 바꾸지 않고 답을 좋게 만들 수 있는가 |
| 2일차 ② 구조화 출력 | 문자열 파싱 코드를 지울 수 있는가, 그리고 형식이 깨지면 어떻게 되는가 |
| 2일차 ③ 워크플로 | 한 번의 큰 호출을 언제 여러 번의 작은 호출로 쪼개는가 |
| 2일차 ④ RAG | 우리 문서를 근거로 답하게 하려면 무엇이 필요한가 |
| 2일차 ⑤ RAG 심화 | 검색이 못 찾을 때 어디를 손보는가 |
| 3일차 ① Tool Calling | 모델이 우리 코드를 부르게 하려면 무엇을 알려 줘야 하는가 |
| 3일차 ② 도구 안전 | 되돌릴 수 없는 행동을 어떻게 통제하는가 |
| 3일차 ③ Advisor·운영 | 공통 관심사를 어디에 모으고, 순서는 왜 중요한가 |
| 3일차 ④ 종합 실습 | 배운 조각들이 하나의 서비스에서 어떻게 협력하는가 |

각 편에서 코드를 인용할 때는 배포된 샘플 코드를 그대로 쓰되, 그 코드가 어떤 실패를 막기 위한 것인지를 함께 적는다. 동작하는 코드보다 **왜 그 자리에 그 줄이 있는지**가 3일 과정에서 실제로 배운 내용이기 때문이다.
