## 검색을 붙이기 전에 실패 유형을 나눈다

첫 단원은 검색 증강 생성(RAG)을 외부 근거를 찾아 모델 입력에 제공하는 방법으로 설명한다. 모델이 답을 모르는 이유는 자료 자체가 없는 경우, 자료는 있지만 검색에 실패한 경우, 검색은 됐지만 답을 잘못 읽은 경우로 다를 수 있다. 모든 실패를 프롬프트 한 줄로 해결하려 하면 원인을 놓친다.

```text
질문 → 검색 질의 → 문서 검색 → 근거 선택 → 답변 생성 → 근거 확인
```

PDF의 표·그림·다단 레이아웃이 깨진 채 색인되면 검색기가 관련 문서를 찾아도 핵심 수치가 빠질 수 있다. 따라서 추출 품질, 문서 버전, 출처와 페이지 정보는 생성 모델 선택만큼 중요하다. 근거가 없을 때는 답변을 유보하는 경로도 설계해야 한다.

## 7반 2조 프로젝트의 문제 정의

7반 2조 논문 리뷰 Agent 프로젝트의 README는 PDF·텍스트·arXiv에서 기술 개요, 적용 범위, 한계를 근거와 함께 추출하는 목표를 명시한다. 단일 논문 분석과 다중 논문 비교는 서로 다른 작업이며, 조건이 다른 수치를 직접 비교하지 않도록 계약을 둔다. 이 글에서는 프로젝트의 설계와 코드 구조가 존재한다는 사실만 다루고, 모든 논문에서 정답을 보장한다고 주장하지 않는다.

## ‘모른다’를 한 가지 오류로 묶지 않기

질문에 필요한 문서가 인덱스에 없다면 검색 설정을 조정해도 답은 나오지 않는다. 문서가 있는데 검색 결과에 들지 않았다면 쿼리·청킹·검색기를 점검한다. 검색 결과에 근거가 있는데도 모델이 다른 내용을 썼다면 프롬프트, 근거 선택, 답변 검증을 봐야 한다. 이 구분은 개선 작업의 순서를 바꾼다.

논문 PDF에서는 수치가 있는 표의 열 제목과 실험 조건이 떨어져 나오기 쉽다. “값 93.2”만 남은 청크는 검색에 잡혀도 비교 근거로 쓰기 어렵다. 파싱 품질을 페이지 단위로 점검하는 이유다.
