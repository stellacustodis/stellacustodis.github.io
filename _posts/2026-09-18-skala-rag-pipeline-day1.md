## RAG는 모델 밖의 지식을 연결한다

LLM이 학습할 때 보지 못한 사내 문서나 최근 자료를 답변에 쓰려면 외부 지식을 가져오는 단계가 필요하다. 모델을 다시 학습하는 방법도 있지만, 문서가 자주 바뀌거나 답의 출처를 확인해야 하는 서비스에는 비용과 운영 부담이 크다. RAG는 질문과 관련된 문서를 먼저 찾고 그 내용을 프롬프트에 넣어, 모델이 답변할 근거를 제공한다.

```text
질문
  → 검색 질의 구성
  → 관련 문서 검색
  → 필요한 근거 선택
  → 답변 생성
  → 근거와 답변 확인
```

여기서 검색 결과를 붙였다는 사실만으로 환각이 사라지지는 않는다. 자료가 인덱스에 없거나, 청크가 잘못 나뉘었거나, 검색한 근거를 모델이 잘못 해석하면 여전히 틀린 답이 나온다. 실패 지점을 나눠 보는 것이 RAG 설계의 출발점이다.

## RAG는 어떻게 확장됐나

가장 단순한 Naive RAG는 색인한 문서를 한 번 검색하고 답을 만든다. 이후에는 검색 전후 처리와 여러 검색기를 조합하는 Advanced RAG, 모델이 검색 필요성과 근거 품질을 스스로 점검하는 Self-RAG, 기능을 모듈로 나눠 조합하는 Modular RAG로 발전했다. Agentic RAG는 여기에 계획, 도구 사용, 반성, 여러 에이전트의 역할 분담을 더한다.

각 방식은 앞 단계의 한계를 보완하지만 호출 횟수와 상태 관리도 늘어난다. 기본 검색 경로에서 무엇이 실패하는지 측정한 뒤 필요한 기능을 추가해야 한다.

## 전처리 단계에서 검색 품질이 정해진다

문서를 벡터 DB에 넣기 전에는 로더, 파서, 텍스트 분할기를 거친다. PDF는 단순 텍스트 파일과 달리 다단 편집, 머리말, 표, 그림, 캡션이 섞여 있다. 읽기 순서가 어긋나면 한 문장이 다른 단의 문장과 합쳐지고, 표의 값이 열 제목과 떨어질 수 있다.

전처리에서 남겨야 할 정보는 본문만이 아니다.

- 문서 ID와 버전
- 물리 페이지와 인쇄 페이지
- 섹션 제목
- 표·그림·캡션의 관계
- 문장이나 표 셀의 위치
- 청킹과 임베딩에 사용한 설정

이 정보가 있어야 검색 결과가 어느 원문에서 왔는지 되짚을 수 있다.

## 청크 크기는 문맥과 검색 정밀도의 절충이다

청크가 너무 짧으면 질문과 정확히 맞는 문장을 찾기 쉽지만, 그 문장을 해석할 조건이 빠질 수 있다. 너무 길면 조건은 보존되지만 관련 없는 문장이 많아져 임베딩이 흐려지고 입력 토큰도 늘어난다.

강의에서는 단순 고정 길이 분할뿐 아니라 문단과 제목을 따르는 계층형 청킹, 의미 변화에 맞춰 경계를 잡는 semantic chunking도 다뤘다. 실제 문서에서는 하나의 규칙만 고집하기보다 문서 형식과 질문 유형에 맞춰 선택해야 한다. 표를 다룰 때는 값과 행·열 제목을 함께 보존하고, 캡션과 본문에서 표를 설명한 문장을 연결하는 편이 유리하다.

## 임베딩과 벡터 색인

임베딩은 텍스트를 의미 공간의 벡터로 바꾼다. 모델을 고를 때는 벤치마크 순위만 볼 수 없다. 한국어와 전문 용어를 얼마나 잘 다루는지, 벡터 차원과 최대 입력 길이가 운영 환경에 맞는지, 라이선스와 실행 비용은 어떤지 함께 확인해야 한다.

벡터를 저장한 뒤에는 검색 규모와 지연 시간에 맞는 색인이 필요하다.

| 방식 | 특징 | 살펴볼 점 |
|---|---|---|
| Flat | 모든 벡터와 직접 비교 | 정확하지만 데이터가 커질수록 느리다 |
| HNSW | 그래프를 따라 가까운 후보 탐색 | 빠른 검색과 높은 재현율을 노릴 수 있지만 메모리를 더 쓴다 |
| IVF | 벡터 공간을 여러 군집으로 나눠 일부만 탐색 | 탐색 군집 수에 따라 속도와 재현율이 달라진다 |
| PQ | 벡터를 압축해 저장 공간을 줄임 | 압축으로 인한 정확도 손실을 확인해야 한다 |

벡터 DB를 선택할 때도 제품 이름보다 데이터 규모, 갱신 주기, 메타데이터 필터, 백업과 복구, 운영 비용을 먼저 적어 보는 편이 낫다.

## 프로젝트에 연결해 본 전처리 원칙

팀 프로젝트의 기술 조사 에이전트는 논문 PDF를 PyMuPDF로 페이지와 블록 단위로 읽고, pdfplumber로 표를 복원한다. 표를 이미지처럼 통째로 넘기지 않고 Markdown 형태와 셀 위치를 함께 보존한다. 그림과 캡션은 별도 요소로 기록하고 필요하면 시각 분석 결과를 보강한다.

이 단계의 목적은 읽기 좋은 텍스트를 만드는 데서 끝나지 않는다. 이후 생성한 기술 주장과 수치를 페이지·문장·표 셀로 다시 연결할 수 있어야 한다. 스캔 PDF처럼 유효 텍스트가 부족하면 조용히 넘어가지 않고 OCR이 필요하다는 오류로 중단한다.
