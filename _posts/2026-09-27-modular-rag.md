## 세 줄 요약

이 논문은 ‘검색한 뒤 생성한다’는 고정된 절차만으로 복잡해진 검색 증강 생성(retrieval-augmented generation, RAG) 시스템을 설명하기 어렵다고 본다. 인덱싱부터 생성까지의 기능을 모듈·하위 모듈·연산자로 나누고, 라우팅·스케줄링·융합으로 실행 흐름을 제어하는 **Modular RAG**를 제안한다. 핵심 기여는 새 모델의 성능 수치가 아니라, 기존 방법을 공통 부품과 흐름 패턴으로 읽고 조합하는 설계 틀이다.

## 이 논문이 풀려는 문제

기본적인 RAG는 문서를 조각으로 나누어 색인하고, 질문과 가까운 조각을 찾아, 질문과 함께 언어 모델에 넣는다. 논문이 *Naive RAG*라고 부르는 형태다. 이 절차는 단순하지만, 질문과 문서 조각의 벡터 유사도가 답변에 필요한 근거를 충분히 나타낸다고 가정한다. 복잡한 질문에서는 그 가정이 약해진다. 답에 필요한 정보가 여러 문서에 흩어져 있거나, 질문과 비슷하지만 답에는 불필요한 조각이 검색될 수 있다. 검색 결과를 모두 생성 모델에 넘기면 중복과 잡음도 함께 들어간다.

*Advanced RAG*는 검색 전 질문 재작성, 검색 후 재정렬, 계층적 색인 같은 단계를 추가한다. 검색 결과를 개선할 수 있지만, 전체 시스템을 여전히 일렬의 ‘검색 후 생성’ 절차로 보면 설명하기 어려운 사례가 생긴다. 질문에 따라 다른 자료원으로 보내거나, 여러 경로를 동시에 실행하거나, 잠정 답을 점검한 뒤 다시 검색하는 시스템이 그렇다. 표와 지식 그래프까지 함께 다룬다면 하나의 텍스트 검색기만 놓고 설계하기도 어렵다.

![Naive RAG, Advanced RAG, Modular RAG의 구성 비교](/assets/img/posts/modular-rag/fig3.jpg){: w="800" }
_그림 3. 논문이 구분하는 세 패러다임의 관계다. 뒤의 패러다임은 앞선 절차를 포함하면서 표현할 수 있는 기능과 제어 흐름을 넓힌다._

저자는 이 변화를 **네 가지 도전 과제**와 연결한다.

1. **이질적인 데이터 소스의 통합:** 일반 문서뿐 아니라 표와 지식 그래프처럼 구조가 다른 자료를 함께 다뤄야 한다.
2. **해석 가능성·제어 가능성·유지보수성:** 문제가 생겼을 때 어느 구성 요소의 입력, 출력, 판단을 고쳐야 하는지 추적할 수 있어야 한다.
3. **컴포넌트 선택과 최적화:** 작업과 자원 조건에 맞는 검색기·모델·처리 기능을 고르고, 함께 작동하도록 조정해야 한다.
4. **워크플로 오케스트레이션과 스케줄링:** 구성 요소를 어떤 순서로 실행할지, 언제 병렬로 처리하거나 다시 검색할지 결정해야 한다.

앞의 두 과제는 **무엇을 다루고 어떻게 관찰할 것인가**에, 뒤의 두 과제는 **어떤 부품을 골라 어떻게 실행할 것인가**에 가깝다. 특히 컴포넌트 선택과 워크플로 스케줄링은 다른 문제다. 적합한 검색기를 골랐더라도 모든 질문에 무조건 실행할지, 먼저 다른 자료원을 확인할지는 별도의 흐름 결정이다. 기존 연구를 검색·생성 단계별 기술로만 정리하면 이 결정을 충분히 드러내기 어렵다는 것이 논문의 출발점이다.

관련 연구의 계보도 이 문제를 설명한다. 초기 검색 증강은 언어 모델의 지식 집약적 작업을 돕는 데 초점을 두었다. 이후 외부 지식과 근거를 제공하고, 질문 재작성·문맥 압축·그래프 활용·검색 시점의 동적 결정처럼 기능이 분화했다. Modular RAG는 그 기능을 모두 새로 발명하는 방법이라기보다, 분화한 기능들이 한 시스템에서 **어떤 관계로 연결되는지** 기술하려는 틀이다.

## 핵심 아이디어: 기능뿐 아니라 연결 방식까지 표현한다

논문은 RAG 시스템을 세 수준으로 나눈다.

| 수준 | 역할 | 예 |
|---|---|---|
| 모듈(module) | 큰 처리 단계 | 검색, 생성, 오케스트레이션 |
| 하위 모듈(sub-module) | 모듈 안에서 맡는 기능 | 검색 전 질문 처리, 검색 후 결과 처리 |
| 연산자(operator) | 선택해 실행할 구체적인 처리 | 질문 확장, 재정렬, 압축, 라우팅 |

주요 모듈은 **인덱싱, 검색 전 처리, 검색, 검색 후 처리, 생성, 오케스트레이션**의 여섯 가지다. 앞의 다섯 가지는 자료나 답을 만들고 바꾸는 처리 단계다. 오케스트레이션은 어떤 경로를 택할지, 언제 처리를 반복할지, 여러 경로의 결과를 어떻게 합칠지 결정한다. 그러므로 같은 검색기와 생성기를 쓰더라도 연결 방식이 다르면 다른 RAG 흐름이 된다.

이를 계산 그래프(computational graph)로 읽으면 노드는 구체적인 연산이고 간선은 데이터 또는 제어의 흐름이다. 일렬로 연결하면 전통적인 RAG가 된다. 조건에 따라 다음 노드를 고르면 라우팅, 여러 노드를 실행하면 분기, 앞선 노드로 돌아가면 루프다. 논문은 Naive RAG가 Advanced RAG의 특수한 경우이고, Advanced RAG가 Modular RAG의 특수한 경우라고 설명한다. 이 포함 관계는 **표현할 수 있는 시스템의 범위**에 관한 주장이다. 모듈을 더 많이 넣을수록 정확도가 높아진다는 성능 주장은 아니다.

![데이터와 제어 구성 요소가 늘어난 Modular RAG 사례](/assets/img/posts/modular-rag/fig2.png){: w="500" }
_그림 2. 데이터 종류와 중간 판단에 따라 검색·생성의 경로가 달라지는 구성을 보여준다. 그림의 제어 요소는 단순한 처리 단계를 넘어 흐름 자체를 설계 대상으로 만든다._

앞서 본 네 과제와도 대응된다. 인덱싱·질의 구성은 이질적 자료를 연결하고, 모듈·연산자 단위의 구분은 어느 부분을 점검할지 드러낸다. 검색기와 생성기의 선택·학습은 컴포넌트 최적화에 해당한다. 라우팅·스케줄링·융합은 실행 순서와 분기 문제를 다룬다. 이 대응을 기억하면 아래의 긴 기능 목록을 독립된 기술 나열이 아니라 하나의 설계 문제에 대한 답으로 읽을 수 있다.

## 방법 — 기본 RAG를 모듈의 언어로 옮기기

### 색인·검색·생성: 식 (1)~(4)

논문은 먼저 기본 RAG의 기호를 고정한다. 문서 조각 집합 $D=\{d_1,\ldots,d_n\}$에 임베딩 함수 $f_e$를 적용해 벡터를 저장한다.

$$
I=\{e_1,\ldots,e_n\},\qquad e_i=f_e(d_i)\in\mathbb{R}^{d}
\tag{1}
$$

$I$는 색인이고 $e_i$는 조각 $d_i$의 벡터 표현이다. 색인을 만들 때는 조각만 저장해서는 충분하지 않다. 검색된 벡터에서 원래 조각과 출처로 돌아갈 수 있어야 생성과 근거 확인에 쓸 수 있다. 문서가 많아질수록 조각 수와 벡터 차원은 저장 비용에도 연결된다.

검색기는 질문과 가까운 상위 $k$개 조각을 골라 $D_q$를 만든다.

$$
R(q,D)=\operatorname{topk}_{d_i\in D}\operatorname{Sim}(q,d_i)
\longrightarrow D_q
\tag{2}
$$

유사도에는 내적 또는 코사인 유사도를 사용할 수 있다.

$$
\operatorname{Sim}(q,d_i)
=
e_q\cdot e_{d_i}
\quad\text{또는}\quad
\frac{e_q\cdot e_{d_i}}{\lVert e_q\rVert\lVert e_{d_i}\rVert}
\tag{3}
$$

내적에는 벡터 길이의 영향이 들어가고, 코사인 유사도는 길이로 나누어 방향을 비교한다. 어느 방식을 택하든 질문과 문서의 벡터는 서로 비교할 수 있는 표현 공간에서 만들어야 한다. 검색기를 바꾸었는데 이전 문서 벡터를 그대로 둔다면 식 (3)의 점수가 의도한 의미를 유지하는지 확인해야 한다.

마지막으로 검색된 조각과 질문을 합쳐 답을 만든다.

$$
y=\operatorname{LLM}([D_q,q])
\tag{4}
$$

여기서 기본 RAG의 빈틈이 드러난다. 식 (2)는 유사한 조각을 선택하지만, 식 (4)의 모델이 그 조각을 올바르게 사용한다는 보장은 하지 않는다. 검색 전 질문 처리, 검색 후 근거 선택, 생성 뒤 검증을 별도 기능으로 두는 이유가 여기에 있다.

### 시스템의 구성과 실행 흐름: 식 (5)~(6)

논문은 모듈 $M$, 하위 모듈 $M_s$, 연산자 $Op$를 이용해 전체 시스템을 다음과 같이 적는다.

$$
G=\{q,D,M,\{M_s\},\{Op\}\}
\tag{5}
$$

식 (5)는 시스템이 **어떤 구성 요소를 보유하는지** 나타낸다. 반면 RAG 흐름 $F=(M_{\phi_1},\ldots,M_{\phi_n})$는 선택한 구성 요소를 어떤 순서와 설정으로 실행하는지 나타낸다. 이 둘을 구분하면 하나의 검색 연산자를 다른 흐름에 재사용할 수 있고, 같은 선형 흐름에서 검색기만 교체하는 경우도 기술할 수 있다.

식 (6)은 가장 단순한 Naive RAG를 $q\rightarrow D_q\rightarrow y$로 나타낸다. 논문의 예시에는 구체적인 임베딩·생성 모델 이름도 들어가지만, 식에서 읽어야 할 핵심은 특정 제품이 아니다. **검색 연산의 출력이 생성 연산의 입력이 되는 연결 관계**다.

논문의 Table I도 이 기호를 읽기 위한 표다. $q$는 원래 질문, $D$는 문서 조각 저장소, $R(q,D)$는 검색기, $F$는 실행 흐름, $P$는 흐름 패턴이다. $f_{qe}$·$f_{qc}$·$f_{\mathrm{comp}}$·$f_{\mathrm{sel}}$·$f_r$은 각각 질문 확장·질의 구성·압축·선택·라우팅 같은 기능을 가리킨다. 표가 제시하는 것은 실험 점수가 아니라, 뒤의 여러 설계를 같은 언어로 설명하기 위한 **인터페이스의 이름**이다.

## 여섯 모듈을 구현 관점에서 읽기

### 인덱싱: 무엇을 검색 단위로 만들 것인가

조각 $d_i$의 크기는 $L_i=\lvert d_i\rvert$, 다음 조각과 겹치는 부분은 $L_i^o=\lvert d_i\cap d_{i+1}\rvert$로 표현한다. 큰 조각은 문맥을 보존하지만 불필요한 내용과 처리 비용이 늘 수 있다. 작은 조각은 검색 단위를 세밀하게 만들지만 답에 필요한 앞뒤 문맥을 잃기 쉽다. 겹치는 슬라이딩 윈도는 경계의 문맥을 살리지만, 의미 단위를 고려하지 않으면 문장이나 단어가 어색하게 잘릴 수 있다.

논문은 이 문제에 몇 가지 보완책을 연결한다. **메타데이터 부착**은 페이지·파일명·작성자·시각·요약 등을 조각과 연결한다. 검색 범위를 좁히는 조건으로 쓸 수 있고, 답의 근거를 원래 자료로 추적하는 데도 필요하다. **Small-to-Big**은 작은 조각으로 찾되 생성 단계에는 부모 조각이나 주변 문장을 제공한다. 검색의 세밀함과 생성 문맥의 충분함을 별도 크기로 다루는 셈이다.

**계층 색인**은 문단·문장 구조, PDF·HTML의 문서 구조, 의미적 구분 등을 이용해 부모와 자식 관계를 만든다. 상위 노드의 요약을 통해 탐색 범위를 좁힌 뒤 관련된 하위 조각을 찾을 수 있다. **지식 그래프 색인**은 노드 $V$, 관계 $E$, 내용 특성 $X$로 자료를 조직한다. 논문의 예처럼 페이지·표·문단을 노드로 두고 소속이나 의미 관계를 간선으로 표현할 수 있다. 이러한 방법은 검색 결과가 어느 문서의 어느 구조에서 왔는지를 유지하려는 시도이기도 하다.

구현상의 핵심은 **검색 단위와 생성 단위가 같을 필요는 없다는 점**이다. 작은 자식 조각이 검색되었을 때 부모 문맥을 가져오려면 자식에서 부모로 가는 식별자가 있어야 한다. 출처와 계층 관계를 색인할 때 잃어버리면 나중에 후처리 모듈을 추가해도 복원하기 어렵다.

### 검색 전 처리: 원래 질문을 그대로 검색할 것인가

질문 확장(query expansion)은 하나의 질문에서 여러 검색 질문을 만든다.

$$
f_{qe}(q)=\{q_1,\ldots,q_n\}
\tag{7}
$$

여러 표현을 병렬로 검색하는 Multi-Query는 회수 범위를 넓힐 수 있지만 원래 의도를 흐릴 위험이 있다. 논문은 원래 질문에 더 큰 비중을 주는 방식을 완화책으로 든다. 복잡한 질문을 하위 질문으로 나누는 Sub-Query에서는 각 질문의 의존 관계가 중요하다. 서로 독립된 질문이라면 병렬로 실행할 수 있지만, 앞선 답을 알아야 뒤의 질문을 만들 수 있다면 순서가 필요하다. 확장된 질문을 다시 검증하는 접근으로 Chain-of-Verification도 소개한다.

질문 변환(query transformation)은 검색에 사용할 표현을 바꾼다.

$$
f_{qt}(q)=q'
\tag{8}
$$

Rewrite는 모호한 질문을 검색하기 쉬운 형태로 다시 쓴다. HyDE는 가상의 답변 문서를 만들고 그 표현으로 실제 답변 문서를 찾으려 한다. 이는 질문 문장과 답변 문서가 임베딩 공간에서 바로 가까울 것이라는 가정을 완화한다. 반대 방향의 접근에서는 각 문서 조각에 가상의 질문을 연결해 질문끼리 비교한다. Step-back Prompting은 원래 질문보다 추상적인 질문도 함께 검색한 뒤 결과를 결합한다.

자료가 텍스트 문서만이 아니라면 질문을 실행 가능한 다른 질의 언어로 구성해야 할 수도 있다.

$$
f_{qc}(q)=q^*,\qquad
q^*\in\{\mathrm{SQL},\mathrm{Cypher},\ldots\}
\tag{9}
$$

SQL이나 Cypher로의 변환은 문장 다듬기와 다르다. 검색 대상, 질의 실행기, 반환되는 자료의 구조가 함께 바뀐다. 따라서 질의 구성 결과를 어느 자료원에 보낼지도 명확히 해야 한다. 이 지점에서 검색 전 처리와 오케스트레이션이 만난다.

### 검색: 검색기를 고르고 작업에 맞추기

검색기는 희소(sparse), 밀집(dense), 혼합(hybrid) 방식으로 나뉜다. 희소 검색은 TF-IDF나 BM25처럼 단어 통계에 기반한다. 논문은 큰 자료에서의 효율을 장점으로 들지만 복잡한 의미 관계는 놓칠 수 있다고 설명한다. 밀집 검색은 학습된 벡터로 의미를 표현하는 대신 모델 추론과 벡터 저장 비용이 든다. 혼합 검색은 두 신호를 함께 사용하며, 드문 개체명이 포함된 질문처럼 한쪽 신호만으로 부족한 경우를 고려한다.

도메인의 용어와 문서가 검색기의 사전 학습 자료에서 멀다면 검색기를 조정할 수 있다. 식 (10)의 감독 미세조정은 질문 $q_i$에 대해 양성 문서 $d_i^+$의 점수를 음성 문서보다 높이는 대조 목적이다.

$$
\mathcal L(D_R)=
-\frac{1}{T}\sum_{i=1}^{T}
\log
\frac{\exp(\operatorname{sim}(q_i,d_i^+))}
{\exp(\operatorname{sim}(q_i,d_i^+))+
\sum_{j=1}^{N}\exp(\operatorname{sim}(q_i,d_{ij}^-))}
\tag{10}
$$

분모에는 양성 후보와 음성 후보의 점수가 함께 들어간다. 분수는 **주어진 후보들 사이에서 양성 문서에 배정한 몫**으로 읽을 수 있다. 양성 점수를 올리는 것만이 아니라 경쟁 후보와의 상대적인 위치를 학습하는 구조다. 위 식의 $d_{ij}^-$는 질문 $i$에 대한 음성 후보 $j$를 구별하는 표기이며, $j=1,\ldots,N$에 걸쳐 합산한다.

LM-supervised Retriever(LSR)는 사람이 부여한 관련성 표시 대신, 문서 $d$를 주었을 때 생성 모델이 정답 $y$를 얼마나 잘 설명하는지를 감독 신호로 사용한다. 식 (11)은 그 값을 $\beta$로 조정해 문서 후보 간 분포로 만드는 형태다. 구현에서는 분모의 합산 변수와 문서 후보가 일치하도록 정의해야 한다. 핵심 역할은 **생성 모델의 문서 선호를 검색기의 학습 신호로 쓰는 것**이다. 큰 검색기를 전부 미세조정하는 부담을 줄이기 위한 선택으로는 어댑터(adapter)도 소개한다.

### 검색 후 처리: 무엇을 생성 모델에 넘길 것인가

검색 결과를 그대로 이어 붙이면 긴 문맥의 중간에 있는 정보를 덜 활용하거나, 잡음과 상충하는 내용 때문에 답이 흔들릴 수 있다. 생성 모델에 넣을 수 있는 문맥 길이에도 한계가 있다. 논문은 결과를 다루는 세 연산을 구별한다.

- **재정렬(rerank):** 조각의 내용과 길이는 두고 순서를 바꾼다. 식 (12)의 $D_q^r=f_{\mathrm{rerank}}(q,D_q)$가 이에 해당한다. 관련성이나 다양성에 관한 규칙 또는 모델의 점수로 중요한 조각의 위치를 조정한다.
- **압축(compression):** 남길 조각의 내용을 줄인다. 식 (13)의 $D_q^c=f_{\mathrm{comp}}(q,D_q)$는 조각별 길이 감소를 나타낸다. 논문은 중요도가 낮은 토큰을 제거하는 LongLLMLingua를 사례로 든다.
- **선택(selection):** 조각 전체를 버리거나 유지한다. 식 (14)은 조건 $P(d_i)$에 해당하는 문서를 삭제하고 그렇지 않은 문서를 남기는 방식이다. LLM-Critique처럼 모델이 근거의 관련성을 먼저 판단할 수도 있다.

세 연산은 이름만 다른 동일한 축소 방법이 아니다. 재정렬은 조각의 총량을 줄이지 않는다. 압축은 짧은 입력을 만들 수 있지만 답에 필요한 구절을 지울 위험이 있다. 선택은 무관한 조각을 통째로 제거하지만, 그 안의 일부 유용한 내용도 함께 잃을 수 있다. 따라서 어떤 문제를 해결하려는지에 따라 순서와 조합을 정해야 한다. 예를 들어 문맥 길이가 병목이라면 재정렬만으로는 부족하다.

선택기의 인터페이스에서는 **이미 검색된 후보 $D_q$에서 무엇을 남길 것인지** 분명히 해야 한다. 선택기가 전체 저장소 $D$에서 검색하지 않은 새 문서를 추가하는 동작까지 맡는다면, 그것은 다른 역할이다.

### 생성과 검증: 답을 만든 뒤에도 흐름이 끝나는가

생성 모듈에서는 작업의 형식, 추론 효율, 개인정보 요구를 고려해 모델을 고른다. 논문은 생성기의 지시 미세조정, 사람 또는 검색기 선호를 이용한 강화학습, 검색기와 생성기를 함께 조정하는 방식을 다룬다.

공동 조정에서는 검색 점수로 만든 문서 분포와, 정답 생성에 대한 언어 모델의 문서 선호 분포를 맞춘다. 식 (15)은 검색 점수에 온도 역할의 $\gamma$를 적용하고 후보 문서 $D_q$ 전체로 **정규화한** 분포다. 분모의 $d'$는 합산에만 쓰는 변수로, 분자의 대상 문서 $d$와 구별했다.

$$
P_R(d\mid q)=
\frac{
\exp\!\left(\operatorname{sim}(d,q)/\gamma\right)
}{
\displaystyle\sum_{d'\in D_q}
\exp\!\left(\operatorname{sim}(d',q)/\gamma\right)
}
\tag{15}
$$

이 정규화 덕분에 같은 후보 집합 $D_q$에 대한 $P_R(d\mid q)$의 합은 $1$이 된다. 식 (16)은 검색기 분포 $P_R$와 생성 모델이 정답 $y$를 바탕으로 선호하는 문서 분포 $P_{\mathrm{LSR}}$ 사이의 KL 발산을 사용한다. 질문이 $T$개일 때 합산 인덱스는 $i=1$부터 $T$까지다.

$$
\mathcal L=
\frac{1}{T}\sum_{i=1}^{T}
\operatorname{KL}\!\left(
P_R(\,\cdot\mid q_i)
\,\middle\|\,
P_{\mathrm{LSR}}(\,\cdot\mid q_i,y_i)
\right)
\tag{16}
$$

원문의 식 (16)은 앞의 계수를 $1/\lvert T\rvert$로 표기하지만, 본문에서 $T$를 **질의 총수**로 정의한다. 위 식의 $1/T$는 질의별 손실의 평균을 뜻한다. KL 발산을 계산하려면 두 분포가 동일한 후보 문서 축을 공유해야 한다. 검색기가 어떤 문서에 높은 점수를 주는 것과, 생성 모델이 어떤 문서로 정답을 더 잘 설명하는 것이 어긋난다면 손실이 그 차이를 드러낸다. 구현에서는 식 (11)의 생성 모델 선호 분포를 만드는 절차도 별도로 정해야 한다.

검증은 생성한 답 $y$를 질문과 근거에 다시 대조하며, 논문은 $y_k=f_{\mathrm{verify}}(q,D_q,y)$로 표현한다(식 (17)). 지식 기반 방식은 답의 주장이나 관계를 추출해 확인된 자료와 비교하고, 지지·반박·근거 부족을 판단한다. 모델 기반 방식은 질문·검색 근거·답을 입력받는 작은 모델이 답의 근거 반영 여부를 판단한다. 검증에 실패해 재생성한다면 검증 결과는 단순한 품질 표시가 아니다. **다음 실행 경로를 바꾸는 제어 신호**가 된다.

### 오케스트레이션: 라우팅·스케줄링·융합

**라우팅(routing)**은 질문 $q$를 적절한 흐름 $F$에 보낸다. 논문의 식 (18)은 이를 $f_r:Q\rightarrow F$로 쓴다. 메타데이터 기반 방식은 질문에서 찾은 키워드와 각 흐름에 연결된 키워드의 겹침을 점수로 삼는다(식 (19)~(20)). 의미 기반 방식은 질문의 의도를 추정해 해당 흐름에 연결한다(식 (21)). 혼합 방식은 키워드와 의미 점수를 결합한다(식 (22)).

라우팅을 구현할 때는 집합 첨자와 `score`의 정의, 혼합 가중치 $a$와 $\alpha$의 역할을 일관되게 정해야 한다. 키워드가 없을 때의 처리, 각 점수의 범위와 정규화, 의도에서 흐름으로 가는 대응표도 필요하다. 서로 다른 범위의 점수를 그대로 더하면 가중치의 의미도 흐려진다.

**스케줄링(scheduling)**은 현재 정보나 답이 충분한지 판단하고 다음 검색·생성 여부를 결정한다. 논문은 토큰 확률이 임계값 $\tau$를 만족하는지 보는 규칙, 프롬프트에 따른 LLM 판단, 행동 토큰을 출력하도록 미세조정한 모델, 지식 그래프의 추론 경로를 따르는 방식을 소개한다. 규칙 기반 방식은 판정 조건을 명시하기 쉽지만 토큰 확률이 답의 사실성을 직접 보증하지는 않는다. 프롬프트 방식은 별도 미세조정이 필요 없지만 정해진 출력 형식을 모델이 지키는지 확인해야 한다. 행동 토큰 방식에는 그 행동을 학습할 자료가 필요하다.

**융합(fusion)**은 여러 가지에서 나온 문서나 답을 합친다. 완성된 답을 언어 모델에 넣어 통합할 수 있지만, 긴 가지별 출력을 한 번에 넣으면 문맥 한계가 문제가 된다. 논문은 가지별 답을 먼저 요약하는 방법도 설명한다. 다른 방식인 식 (23)~(24)는 문서마다 얻은 생성 확률을 검색 유사도에 따른 가중치 $\lambda(d,q)$로 결합한다.

$$
p(y\mid q,D_q)
=
\sum_{d\in D_q}p(y\mid d,q)\lambda(d,q)
\tag{23}
$$

$$
\lambda(d,q)=
\frac{\exp(s(d,q))}
{\displaystyle\sum_{d'\in D_q}\exp(s(d',q))}
\tag{24}
$$

여기서 분모의 $d'$는 분자의 $d$와 충돌하지 않도록 구별한 합산 변수다. 가중치 합이 $1$이므로 문서별 확률을 하나의 가중 결합으로 읽을 수 있다. 다만 **토큰 확률의 결합**과 **완성된 답의 요약·통합**은 서로 다른 입력과 출력을 요구한다. 하나의 `merge` 함수라고 이름 붙이더라도 실제 구현에서 같은 연산으로 취급할 수 없다. 논문은 서로 다른 검색 순위를 합치는 Reciprocal Rank Fusion(RRF)도 소개한다.

## RAG 흐름의 여섯 패턴

모듈을 정의하는 것과 실행 흐름을 설계하는 것은 별개의 일이다. 논문이 설명하는 실행 흐름은 다음처럼 읽을 수 있다.

| 흐름 형태 | 결정해야 할 것 | 논문에서 든 사례 |
|---|---|---|
| 선형(linear) | 고정된 처리 순서 | RRR |
| 조건부(conditional) | 실행할 경로 하나 | 질문에 따른 서로 다른 검색·생성 경로 |
| 분기(branching) | 실행할 여러 가지와 합치는 방법 | REPLUG |
| 반복(iterative) | 이전 출력을 다음 검색에 반영하는 방법 | ITER-RETGEN |
| 재귀(recursive) | 새 하위 질문을 확장하는 방법 | ToC |
| 적응형(adaptive/active) | 검색 시점과 종료 여부 | FLARE, Self-RAG |

논문은 반복·재귀·적응형을 **루프 패턴**의 하위 형태로 묶는다. 별도의 **튜닝 패턴**도 다루는데, 이는 실행 간선의 모양보다는 어느 부품을 학습시키는지에 관한 축이다. 따라서 표는 루프의 세 하위형을 풀어 쓴 것이며, 튜닝을 빠뜨린 전체 목차로 읽으면 안 된다. 표에서 특히 봐야 할 것은 각 패턴이 추가하는 **제어 결정**이다. 검색기나 생성기의 종류가 같아도 그 결정이 다르면 호출 수와 실패 지점이 달라진다.

### 선형과 조건부: 순서를 고정하거나 경로 하나를 고른다

선형 패턴은 $P_{\mathrm{linear}}=\{M_1\rightarrow\cdots\rightarrow M_n\}$이다(식 (25)). Algorithm 1은 원래 질문을 검색용으로 전처리하고, 검색·후처리를 거친 뒤 **생성에는 원래 질문 $q$와 후처리된 문서**를 넣는다. 검색하기 좋게 바꾼 질문 $q'$와 사용자에게 답해야 할 질문 $q$를 구별하는 지점이다. RRR은 학습 가능한 질문 재작성 모듈을 앞에 두고 BM25로 검색하는 선형 사례다.

조건부 패턴은 라우터 $f_r$의 판단에 따라 $M_j$ 또는 $M_k$로 간다(식 (26), Algorithm 2). 질문 종류에 따라 검색 자료원, 모델, 프롬프트, 처리 기준이 다를 때 필요한 구조다. 여기서는 여러 후보 중 **한 경로를 선택**한다. 어떤 경로를 고르느냐가 답의 근거 범위를 결정할 수 있으므로, 경로 선택의 입력과 판단 이유를 기록할 필요가 있다. 이는 논문의 유지보수성 문제를 구현으로 옮겼을 때의 점검 사항이다.

### 분기: 여러 경로를 실제로 실행하고 합친다

분기 패턴은 $M_{\mathrm{split}}$이 만든 여러 입력 $b_i$를 처리하고 $M_{\mathrm{merge}}$로 합친다. 융합 뒤에 검증 같은 모듈을 더 연결할 수도 있다(식 (27)). 검색 **전**에 분기하면 질문을 확장해 각 질문에서 검색·생성을 수행한다(식 (28), Algorithm 3). 검색 **후**에 분기하면 한 번 검색한 문서 각각을 별도의 생성 입력으로 쓰고 합친다(식 (29), Algorithm 4).

![검색 전에 질문을 나누어 각 가지에서 검색과 생성을 수행하는 흐름](/assets/img/posts/modular-rag/fig7.png){: w="800" }
_그림 7. 검색 전 분기는 확장된 질문마다 검색부터 수행한다. 여러 질문 표현으로 찾는 범위를 넓히지만 가지 수에 따라 검색도 늘어난다._

![한 번 검색한 뒤 문서별로 생성하는 흐름](/assets/img/posts/modular-rag/fig8.png){: w="800" }
_그림 8. 검색 후 분기는 검색 결과를 공유한다. 각 문서에서 별도로 생성한 뒤 결과를 합치므로, 생성과 융합의 입력 단위가 문서별로 나뉜다._

REPLUG는 검색 후 분기의 사례다. 문서별 가지에서 다음 토큰 확률을 얻고 가중 결합하며, 그 결과를 검색기 조정의 피드백으로도 사용한다. 조건부 패턴과의 차이는 **여러 경로를 실제로 실행한다**는 점이다. 다양성을 얻는 대신 가지별 생성 비용을 지불한다. 검색 전 분기에서 질문마다 검색 결과를 하나로 합친 뒤 한 번 생성하는 설계도 생각할 수 있지만, 논문의 Algorithm 3은 문서별 생성까지 포함한다. 호출 수를 비교할 때 어느 변형을 말하는지 구별해야 한다.

### 루프: 다시 검색할 이유와 멈출 조건을 둔다

루프는 모듈을 정점, 데이터·제어 연결을 간선으로 보았을 때 앞선 정점으로 되돌아가는 경로가 있는 구조다. ‘여러 번 실행한다’고만 쓰면 설계가 끝나지 않는다. **이전 결과 중 무엇을 다음 입력에 반영하는지, 어느 판단이 되돌리는지, 언제 멈추는지**가 흐름에 포함돼야 한다.

![반복·재귀·적응형 검색의 루프 구조](/assets/img/posts/modular-rag/fig10.png){: w="700" }
_그림 10. 세 루프 모두 검색과 생성을 다시 연결한다. 이전 답을 갱신에 쓰는지, 새 하위 질문을 확장하는지, 검색 필요성 자체를 판단하는지가 구분점이다._

반복 검색(iterative retrieval)은 이전 출력을 다음 검색의 문맥으로 사용한다. Algorithm 5는 최대 반복 횟수 $T$ 안에서 질문 변환, 검색, 생성, 계속 여부 판정을 수행한다. ITER-RETGEN은 이전 생성 결과를 뒤의 검색에 활용하는 사례다. 최대 횟수는 종료 안전장치이자 호출 비용의 상한을 정하는 장치다. 다만 논문 알고리즘의 처음 단계에서는 ‘이전 출력’이 비어 있으므로, 구현 시 첫 질문 변환과 첫 검색이 빈 값을 어떻게 다룰지 정해야 한다.

재귀 검색(recursive retrieval)은 앞선 단계에서 **새 하위 질문**을 만들어 탐색을 깊게 한다. Algorithm 6은 질문 집합을 단계별로 확장하며 최대 깊이 $K_{\max}$에 이르거나 새 질문이 없으면 종료한다. ToC는 모호한 질문의 해석을 clarification tree의 노드로 확장한 뒤 유효한 노드를 모아 답하는 사례다. 같은 질문에 이전 답을 보태며 갱신하는 반복과, 질문 자체를 새 가지로 뻗게 하는 재귀가 다르다. 재귀에서는 이미 다룬 질문이 다시 생성되지 않도록 확인하는 단계도 중요하다.

적응형 검색(adaptive retrieval)은 **검색할 필요가 있는 시점**을 판단한다. FLARE는 다음 문장을 잠정 생성하고 낮은 확률의 토큰이 발견되면 문서를 검색해 해당 문장을 다시 생성하는 사례다. Self-RAG는 검색 필요성, 근거의 관련성, 답의 근거 지지 여부, 답의 유용성에 관한 특수 토큰을 생성하도록 모델을 조정한다. 두 방법은 모두 흐름을 제어하지만 판단을 얻는 방식이 다르다.

적응형 흐름을 구현한다면 질문과 답의 상태 변수, 종료 조건을 명시해야 한다. ‘검색이 필요하지 않음’, ‘현재 답이 충분함’, ‘더 진행해도 답을 얻지 못함’을 각각 어떤 결과로 처리할지 구분해야 한다.

### 튜닝: 흐름 안에서 무엇을 학습시키는가

튜닝 패턴은 세 갈래다. **검색기만 조정**할 때는 감독 미세조정, 어댑터, 언어 모델 출력을 감독 신호로 쓰는 방법, 언어 모델 보상을 이용한 강화학습이 제시된다. **생성기만 조정**할 때는 지도 학습, 강한 모델의 출력을 이용한 증류, 사람이나 모델의 피드백을 이용한 강화학습이 정리된다. **둘을 함께 조정**하는 RA-DIT 사례에서는 생성기가 정답을 더 잘 만들도록 학습하는 동시에 검색기의 문서 점수 분포를 생성 모델의 문서 선호와 맞춘다.

이 구분을 운영 관점에서 읽으면 변경의 범위를 파악하기 쉽다. 검색기를 바꾸면 질문 표현과 저장된 문서 벡터가 호환되는지 확인해야 한다. 생성기를 바꾸면 같은 근거를 쓰더라도 답의 형식과 근거 활용 방식이 달라질 수 있다. 둘을 함께 바꾸면 각 모델의 단독 지표뿐 아니라 동일한 후보 문서에 대한 선호가 어떻게 맞물리는지도 살펴야 한다. 이는 논문의 튜닝 분류에서 이어지는 구현상의 점검 사항이다.

## 구현 관점에서: 오프라인 색인과 온라인 실행을 분리하기

이 논문은 하나의 고정된 학습 알고리즘을 제시하지 않는다. 아래 코드는 식 (1)~(4)와 Algorithm 1~4의 공통 흐름을 인터페이스 수준에서 옮긴 **의사코드**다. `embed`, `retrieve`, `generate`는 특정 라이브러리의 API가 아니라 각 모듈의 역할이다.

```python
def build_index(chunks, embed, store):
    # chunks: 길이 N의 조각 목록; 각 조각에 출처 정보가 연결됨
    vectors = embed(chunks)          # (N, d): 조각별 d차원 벡터
    store(chunks, vectors)           # N개의 조각·벡터·출처를 함께 저장


def answer_linear(q, store, pre, retrieve, post, generate):
    # q: 질문 하나; 배치라면 B개 질문에 각각 적용
    q_search = pre(q)                # 검색용 질문 q'
    docs = retrieve(q_search, store) # 최대 k개 조각
    context = post(q_search, docs)   # 재정렬·압축·선택한 근거
    return generate(q, context)      # 원래 질문 q로 답변


def answer_conditional(q, route, flows):
    flow_id = route(q)               # 질문 하나 -> 경로 하나
    return flows[flow_id](q)


def answer_pre_branch(q, expand, retrieve, generate, merge):
    subqueries = expand(q)           # m개 하위 질문
    branch_answers = []
    for q_i in subqueries:
        docs_i = retrieve(q_i)       # 질문별 최대 k개 조각
        for d_ij in docs_i:
            branch_answers.append(generate(q_i, [d_ij]))
    return merge(branch_answers)     # 최대 m × k개 가지 결과


def answer_post_branch(q, retrieve, generate, merge):
    docs = retrieve(q)               # 검색 한 번, 최대 k개 조각
    answers = [generate(q, [d_i]) for d_i in docs]
    return merge(answers)            # 최대 k개 가지 결과
```

검색 전 분기의 Algorithm 3과 검색 후 분기의 Algorithm 4에는 결과 집합을 초기화한 이름과 이후 값을 추가하는 이름이 다른 부분이 있다. 위 의사코드는 각각 `branch_answers`, `answers`로 일관되게 적었다. 논문의 줄을 그대로 복사하면 초기화되지 않은 변수에 값을 넣는 구현이 될 수 있다.

**학습 루프와 온라인 답변 루프도 구별해야 한다.** 식 (10)의 검색기 학습은 질문·양성 문서·음성 문서로 후보 점수를 만들고 손실을 계산한다. 질문 배치가 $B$, 질문당 음성 후보가 $N$개라면 점수는 개념적으로 `(B, N+1)` 모양이다. 온라인 실행에서는 이미 구축한 색인에서 질문별 상위 $k$개를 찾아 답변에 사용한다. 식 (15)~(16)의 공동 조정은 양쪽 분포가 같은 후보 문서 순서와 축을 공유해야 계산할 수 있다. 후보가 같아도 순서가 다르면 KL 발산은 엉뚱한 문서 확률끼리 비교하게 된다.

루프는 위의 선형 함수에 단순히 `while`만 감싸서는 부족하다. 첫 회차에는 이전 답이 없고, 이후 회차에는 질문·검색 문서·잠정 답의 상태가 바뀐다. 최대 횟수 $T$나 최대 깊이 $K_{\max}$는 호출을 제한하지만 답이 충분한지 판단하는 규칙을 대신하지 않는다. 재귀 흐름에서는 현재 단계에서 새로 생긴 질문과 이전에 처리한 질문을 구별해야 한다. 적응형 흐름에서는 ‘검색 생략’이 곧 ‘답변 생략’을 뜻하는지 별도로 정의해야 한다.

구현 시 확인할 경계는 다음과 같다.

1. **검색 질문과 답변 질문:** 전처리한 $q'$로 검색하더라도 Algorithm 1의 생성 입력에는 원래 $q$가 들어간다.
2. **색인과 검색기의 계약:** 문서·질문 벡터는 비교 가능한 공간에 있어야 한다. 검색기 변경 후 기존 색인을 사용할 수 있는지 확인해야 한다.
3. **조각과 출처의 연결:** Small-to-Big과 계층 색인은 검색된 자식 조각에서 부모 문맥과 원래 자료로 돌아갈 수 있어야 한다.
4. **빈 결과:** 검색 또는 선택 뒤 근거가 없으면 생성·검증·재검색 중 다음 행동을 흐름에서 정해야 한다. 단순 연결만으로는 이 경우의 동작이 정해지지 않는다.
5. **라우팅 점수:** 키워드가 없을 때, 점수가 동률일 때, 해당 흐름이 없을 때의 처리를 구현 계약에 넣어야 한다.
6. **루프의 시작과 종료:** 초기 단계의 빈 이전 답, 최대 횟수, 충분성 판단, 중복 하위 질문을 각각 다뤄야 한다.
7. **융합의 입력 단위:** 식 (23)의 문서별 생성 확률 결합과 완성된 답을 언어 모델로 합치는 방식에는 서로 다른 인터페이스가 필요하다.

이 목록은 논문에 없는 새 실험 결과가 아니다. 모듈을 교체하고 흐름을 재구성할 때, 수식과 알고리즘 사이의 입력·출력 관계를 실제 프로그램에서 명시하기 위한 점검이다.

## 이 논문에서 확인할 수 있는 근거

이 논문은 새 시스템의 벤치마크 실험을 보고하는 형식이 아니다. Table I은 실험 결과가 아니라 기호 표다. 기존 방법을 공통 흐름으로 기술한 것과, 성능·비용의 개선 폭을 측정한 것은 구분해야 한다. 따라서 ‘Modular RAG가 기존 RAG보다 정확도를 얼마 높였다’거나 ‘특정 흐름이 항상 더 싸다’는 결론은 이 논문에서 낼 수 없다.

저자가 제시하는 근거는 기존 방법들을 공통 흐름으로 읽을 수 있다는 **사례 분석**이다. RRR은 질문 재작성·검색·생성이 이어지는 선형 흐름이다. REPLUG는 문서별 생성과 확률 융합을 보여준다. ITER-RETGEN, ToC, FLARE, Self-RAG는 각각 반복, 재귀, 적응형 검색에서 제어 결정이 어떻게 달라지는지 설명한다. 이 사례들은 패턴이 여러 방법을 기술할 수 있음을 보여주지만, 동일한 조건에서 성능을 비교한 실험은 아니다.

논문의 마지막 사례들은 확장 방식도 구별한다. DR-RAG는 기존 기능을 결합해 두 단계 검색과 분기·선택을 구성한다. PlanRAG는 새 연산자를 추가하기보다 계획, 검색, 판단, 재계획의 흐름을 설계한다. Multi-Head RAG는 여러 측면의 문서를 찾는 새 검색 연산자가 흐름 설계의 변화를 낳는 경우로 제시된다. 여기서 읽을 것은 개선 수치가 아니라 **기존 부품의 재조합, 새 흐름의 설계, 새 연산자의 도입**이라는 세 경로다.

## 비용과 트레이드오프

논문은 모듈화의 유연성과 유지보수성을 강조하지만 선택별 비용을 수치로 비교하지는 않는다. 식과 알고리즘에서 읽을 수 있는 비용의 방향은 다음과 같다.

| 선택 | 얻으려는 것 | 추가되는 비용 또는 위험 |
|---|---|---|
| 작은 조각과 겹침 증가 | 세밀한 검색, 경계 문맥 보존 | 색인 조각 수와 중복 증가 |
| Small-to-Big | 작은 단위로 찾고 큰 문맥으로 답변 | 생성 입력 길이 증가 |
| 밀집·혼합 검색 | 의미와 단어 신호의 보완 | 모델 추론, 벡터 저장 또는 복수 검색기 운영 |
| 재정렬·압축·검증 | 근거 선택과 답 점검 | 추가 처리와 지연, 압축 시 근거 손실 가능성 |
| 검색 전 분기 | 여러 질문 표현으로 회수 범위 확대 | 가지마다 검색·생성 수행 |
| 검색 후 분기 | 문서별 생성 결과의 결합 | 문서 수에 따른 생성 수행 |
| 반복·재귀 | 앞선 결과를 반영한 추가 탐색 | 반복 횟수·깊이에 따른 호출 증가 |
| 검색기·생성기 공동 튜닝 | 문서 선택과 답변 선호의 정렬 | 두 모델의 학습과 문서 분포 계산 |

이 표는 “어떤 방식이 우수한가”의 순위가 아니다. **어느 문제를 해결하기 위해 어느 자원을 더 쓰는가**를 읽는 표다. 예를 들어 검색 전 분기는 회수 범위를 넓힐 수 있지만, 논문의 Algorithm 3처럼 확장 질문 $m$개에서 각각 최대 $k$개 문서에 대해 생성하면 가지 답이 최대 $m\times k$개 생긴다. 검색 후 분기의 Algorithm 4는 검색을 한 번 수행하지만 최대 $k$개의 문서별 생성을 수행한다. 이는 알고리즘 구조에서 읽은 호출 수이며 논문이 측정한 지연 시간은 아니다.

경량화 관점에서 먼저 살펴볼 것은 생성 호출 수와 생성 입력 길이다. 압축과 선택은 입력을 줄이지만 필요한 근거가 빠질 수 있다. 분기는 서로 다른 근거를 더 살펴보는 대신 생성 호출을 늘린다. 루프에는 최대 횟수 $T$ 또는 최대 깊이 $K_{\max}$가 있어야 호출 상한을 정할 수 있다. 반대로 검색과 검증을 무조건 생략하면 앞에서 본 답의 근거 부족 문제로 돌아간다. **어떤 질문에서 추가 모듈의 비용이 정당화되는지** 판단하는 일이 오케스트레이션의 중요한 설계 과제로 보인다. 이는 논문에 나온 흐름과 비용 구조에서 도출한 판단이며, 측정으로 입증된 절감 효과는 아니다.

이 비용 문제는 뒤이은 설계 연구의 출발점이기도 하다. 같은 모듈 집합이라도 경로 선택, 검색 시점, 종료 조건에 따라 호출 수와 입력 길이가 달라진다. Modular RAG의 표현 틀은 그런 선택을 명시하고 비교할 위치를 제공한다. 다만 이 논문 자체는 어떤 정책이 특정 예산에서 가장 좋은지 실험하지 않는다.

## 한계와 생각해볼 점

저자는 기존 Naive·Advanced RAG가 복잡한 질문, 검색 잡음, 이질적인 데이터, 동적인 흐름과 유지보수 요구를 다루기 어렵다고 설명한다. 반면 **Modular RAG 자체의 한계를 별도 절로 정리하거나 실험으로 검증하지는 않는다**. 따라서 확인할 수 있는 것은 설계 분류와 사례를 통한 설명 가능성이지, 특정 모듈화 전략의 정확도·지연·비용 개선 폭이 아니다.

이 틀을 구현에 적용한다면 먼저 흐름을 그래프로 적고 각 노드의 입력, 출력, 출처, 종료 조건을 정해야 한다. 루프에는 답이 불충분할 때의 재검색 기준, 최대 호출 수, 중복 질문 제거를 함께 정의해야 한다. 분기는 결과를 합칠 때 단순 나열, 완성된 답의 요약, 토큰 확률의 가중 결합 중 어떤 인터페이스를 사용할지 분명히 해야 한다.

다른 자료 형태로의 일반화 가능성은 **구조 수준**에서 제시된다. 논문은 표·지식 그래프 같은 자료원, 표·이미지의 재정렬, 새 연산자 추가를 논의한다. 이를 구현에 적용하려면 자료 형태와 규모별로 라우팅이나 추가 검증의 이득이 비용을 넘는지 평가해야 한다. 이 논문의 실무적 가치는 특정 설정의 정답을 주는 데 있기보다, RAG를 **교체 가능한 기능과 명시적인 제어 흐름**으로 기술하고 점검하게 만드는 데 있다.
