## 세 줄 요약

이 논문은 대규모 언어 모델(LLM)의 지식 갱신, 긴 대화의 정보 보존, 반복적인 API 호출 비용 문제를 벡터 데이터베이스(VecDB)와 연결해 살핀 서베이다. 벡터 데이터베이스의 역할을 외부 지식 저장소를 이용한 검색 증강 생성(RAG), 시맨틱 캐시(semantic cache), 대화 메모리(memory)로 나누면 각 설계가 무엇을 저장하고 언제 검색하는지 분명해진다. 다만 검색 결과를 모델에 제공하는 것과 모델 자체의 지식을 수정하는 것은 다르며, 논문도 정확한 검색·비용·보안을 위한 과제를 남겨 둔다.

## 이 논문이 풀려는 문제

LLM은 사전학습(pre-training)을 통해 폭넓은 언어 능력을 얻는다. 논문은 언어 모델의 흐름을 순환 신경망(RNN)과 그 변형인 GRU·LSTM, 트랜스포머(Transformer), 대규모 사전학습으로 짚는다. 트랜스포머의 어텐션(attention)은 긴 거리의 문맥을 다루고 병렬 처리를 가능하게 했으며, 사전학습한 모델을 특정 작업에 맞게 조정하는 전이 학습(transfer learning)이 활용 범위를 넓혔다.

이 흐름만으로는 응용 서비스에 필요한 지식을 모두 다루기 어렵다. 논문이 제시하는 문제는 서로 구별할 필요가 있다.

- **모델 내부 지식의 범위와 시점:** 공개 데이터 중심의 학습만으로 특정 조직의 자료나 새로 바뀐 사실을 모두 알 수 없다. 매번 모델을 재학습하거나 미세 조정(fine-tuning)하는 방식은 데이터가 자주 바뀌는 환경에 부담이 된다.
- **환각과 편향:** 모델은 그럴듯하지만 틀린 답을 만들 수 있다. 데이터 편향도 답에 반영될 수 있다. 외부 자료를 검색하더라도 자료 자체가 부정확하거나 서로 충돌하면 이 문제가 자동으로 사라지지 않는다.
- **비용:** 모델의 학습·운영에는 상당한 계산 자원이 들고, 서비스에서는 반복적인 API 호출 비용도 쌓인다. 같은 질문이나 뜻이 비슷한 질문에 매번 새 답을 생성할 필요가 있는지가 별도의 설계 문제가 된다.
- **이전 대화의 활용:** 필요한 과거 대화가 현재 입력에 들어 있지 않으면 모델은 그 내용을 답에 활용하기 어렵다. 논문은 이를 메모리 문제와 연결한다.

모델 편집(model editing)은 내부 지식을 직접 바꾸는 또 다른 방향이다. 그러나 논문은 한 부분의 수정이 다른 성능이나 편향에 영향을 줄 수 있다는 어려움을 든다. 벡터 데이터베이스는 다른 위치에서 문제를 다룬다. 자료를 모델 바깥에 저장하고, 질문할 때 필요한 부분을 찾아 입력으로 건넨다. 내가 이 글에서 계속 구별할 지점은 **외부 자료를 참조해 답하는 능력**과 **모델 매개변수에 저장된 지식의 변화**다.

## 먼저 이해할 것: 벡터 데이터베이스가 검색하는 대상

텍스트·이미지·음성과 같은 자료는 임베딩 모델(embedding model)을 거쳐 고정 길이 벡터로 표현할 수 있다. 벡터 검색은 질의도 벡터로 만든 뒤 저장된 벡터 가운데 가까운 항목을 찾는다. 키워드가 정확히 일치하는 항목을 찾는 검색과 달리, 여기서는 벡터 공간의 거리나 유사도가 기준이다.

논문은 전체 $N$개 벡터를 직접 비교해 상위 $k$개를 찾는 비용을 다음과 같이 적는다. $d$는 벡터 차원이다.

$$
O(dN + N\log k)
$$

각 벡터와의 거리를 계산하는 데 $O(dN)$이 들고, 크기 $k$의 힙으로 후보를 유지하는 데 $O(N\log k)$이 든다는 설명이다. 이 식이 보여주는 병목은 자료가 늘수록 질의마다 비교할 벡터도 늘어난다는 점이다.

근사 최근접 이웃(ANN) 인덱스는 모든 벡터를 같은 방식으로 비교하는 작업을 줄이려는 선택이다. 논문은 트리, 해시, 곱 양자화(product quantization, PQ), 그래프 기반 방법을 소개하고, 그래프 기반 HNSW가 여러 벡터 데이터베이스에 쓰인다고 설명한다. 대신 근사 검색의 결과가 항상 전수 검색의 정확한 상위 $k$개와 같다고 가정해서는 안 된다. 검색 속도와 메모리뿐 아니라 재현율(recall)도 함께 봐야 하는 이유다.

논문의 Table 1은 벡터 검색을 지원하는 제품을 비교한다. 벡터 전용 제품과 관계형·전문 검색·NoSQL 기능을 갖춘 제품이 함께 있다. 표의 차원 값은 논문에 실린 해당 제품·버전의 값이며, 현재 제품 선택을 위한 성능 비교 수치는 아니다.

## 핵심 아이디어: 저장하고, 찾아서, 필요한 순간에 건넨다

논문은 LLM과 벡터 데이터베이스의 결합을 세 용도로 설명한다. 같은 검색 기술을 쓰더라도 저장하는 내용과 검색 결과의 쓰임이 다르다.

| 용도 | 저장하는 것 | 검색하는 시점 | 검색 결과의 역할 |
|---|---|---|---|
| RAG | 문서 조각과 그 임베딩 | 질문에 답하기 전 | 답의 근거로 제공할 문맥 |
| 시맨틱 캐시 | 이전 질문과 생성된 답 | LLM API를 호출하기 전 | 재사용할 수 있는 답의 후보 |
| 대화 메모리 | 과거 대화에서 보존할 내용 | 현재 대화에 과거 정보가 필요할 때 | 현재 입력에 다시 넣을 문맥 |

RAG는 바뀌는 자료를 매번 모델 매개변수에 새겨 넣지 않고 활용하는 방법이다. 시맨틱 캐시는 생성 호출 자체를 줄이는 방법이다. 대화 메모리는 이전 입력 가운데 지금 필요한 내용을 다시 찾는 방법이다. 세 경우 모두 벡터 데이터베이스가 **관련 항목을 찾는 장치**이고, 어떤 항목이 사실인지 또는 답을 재사용해도 되는지를 스스로 판정하는 장치는 아니다.

논문은 산업계 사례로 Azure AI Search의 Qdrant를 활용한 벡터 검색, Pinecone의 오픈소스 Canopy 프레임워크, Spotify와 Yahoo의 Vespa 채택을 든다. 이 사례들은 벡터 데이터베이스를 외부 지식 저장소로 연결해 조직별 자료를 검색하는 RAG의 활용 범위를 보여준다.

## RAG를 수식으로 따라가기

이 논문은 새로운 학습 목적함수나 RAG 수식 번호를 제안하지 않는다. 아래 표기는 본문에 설명된 저장·검색·생성 순서를 구현 관점에서 정리한 것이다.

### 1. 문서를 조각으로 나누고 벡터를 저장한다

전처리한 자료를 문서 조각 $D_1,\ldots,D_N$으로 나누고, 임베딩 모델 $E$로 각각을 변환한다고 쓰자.

$$
v_i = E(D_i), \qquad v_i \in \mathbb{R}^{d}
$$

논문은 자료 수집·정리·변환·정규화 뒤 청킹(chunking)과 임베딩을 수행하는 흐름을 설명한다. 조각으로 나누는 직접적인 이유는 LLM에 한 번에 넣을 수 있는 문맥이 제한되기 때문이다. 조각의 범위는 검색 결과가 답에 필요한 의미를 담을 수 있는지에도 영향을 준다. 논문은 명확한 의미를 갖는 정확한 조각이 검색에 중요하다고 지적하지만, 모든 자료에 적용할 수 있는 통일된 분할 방법을 제시하지는 않는다.

벡터만 보관해서는 검색 뒤 원문을 프롬프트에 넣을 수 없다. 본문의 “검색된 조각을 원래 형태로 가져온다”는 단계는 임베딩에서 원문을 역산한다는 뜻이 아니다. 구현할 때는 벡터와 해당 원문 조각을 연결해 두고, 검색 결과의 식별자로 원문을 가져와야 한다.

### 2. 질문을 같은 표현 공간에 놓고 상위 조각을 찾는다

질문 $Q$도 문서에 사용한 임베딩 모델로 변환한다.

$$
q = E(Q), \qquad q \in \mathbb{R}^{d}
$$

그다음 벡터 데이터베이스가 유사도에 따라 상위 $K$개 조각을 찾는다. 이를 개념적으로 쓰면 다음과 같다.

$$
I_K(Q)
=
\operatorname{TopK}_{i\in\{1,\ldots,N\}}
\operatorname{sim}(q,v_i)
$$

여기서 `sim`은 검색에 사용하는 유사도 점수를 뜻한다. 논문은 특정 거리 함수나 $K$의 최적값을 고정하지 않는다. ANN 인덱스를 쓴다면 실제 반환 목록은 위의 정확한 상위 $K$개에 대한 근사 결과일 수 있다. 이 차이는 “검색이 빨랐다”와 “답에 필요한 근거를 찾았다”를 따로 확인해야 함을 뜻한다.

### 3. 원문 조각과 질문을 모델 입력으로 만든다

검색 결과에 연결된 원문 조각을 $C(Q)$라고 두면 생성 단계는 다음과 같이 정리할 수 있다.

$$
A = G\bigl(T(Q,C(Q))\bigr)
$$

$T$는 질문과 검색 문맥을 결합하는 프롬프트 템플릿이고, $G$는 LLM이다. 템플릿이 필요한 까닭은 검색된 문서와 사용자의 질문을 모델이 사용할 수 있는 하나의 입력으로 묶어야 하기 때문이다. Figure 1은 문서를 저장하는 경로와 질문을 처리하는 경로가 생성 직전에 만나는 구조를 보여준다. 그림 속 영화 질문과 답은 동작을 설명하는 예시이지, RAG의 정확도를 측정한 실험이 아니다.

![문서 저장, 질문 검색, 답 생성으로 이어지는 RAG 흐름](/assets/img/posts/llms-meet-vector-databases/figure1.png){: w="800" }
_그림 1. 문서 조각의 임베딩은 미리 저장하고, 질문이 들어오면 관련 원문을 찾아 LLM 입력에 결합한다._

각 항의 역할도 분리된다. $E$가 문서와 질문을 검색 가능한 공간에 놓고, 벡터 인덱스가 후보를 찾고, $T$가 후보를 모델에 제시하며, $G$가 답을 만든다. 검색을 빼면 외부 자료를 참조할 경로가 사라진다. 원문 조각을 가져오는 단계를 빼면 벡터 검색 결과를 답의 근거 문장으로 제공할 수 없다. 생성 단계만으로도 답은 만들 수 있지만, 이 설계가 노리는 최신·도메인 자료의 활용은 보장되지 않는다.

## 구현 관점에서: 구축 단계와 질의 단계를 나누기

이 서베이에는 새 모델의 학습 루프나 샘플링 알고리즘이 없다. RAG에서 구별해야 할 두 루프는 **자료를 넣는 구축 단계**와 **질문마다 실행하는 온라인 단계**다. 앞 단계에서 임베딩과 인덱스를 준비해 두어야 뒤 단계에서 검색할 수 있다.

```python
# 개념적 의사코드. E, index, store, G는 논문이 설명한 역할이다.

# 구축 단계
documents = preprocess(raw_documents)
chunks = chunk(documents)                 # 길이가 서로 다른 원문 조각 N개
vectors = E(chunks)                       # (N, d)
ids = store.save(chunks)                  # 각 벡터에 연결할 원문 식별자 N개
index.add(ids, vectors)                   # 벡터와 원문 식별자를 함께 색인

# 질의 단계
questions = receive_questions()           # 배치 크기 B
query_vectors = E(questions)              # (B, d), 구축 단계와 같은 E
hits = index.search(query_vectors, K)     # 식별자·점수, 개념상 (B, K)
contexts = store.load(hits.ids)           # 질문별 원문 조각 목록, 길이는 가변
prompts = compose(questions, contexts)    # 질문과 검색 문맥을 결합
answers = G(prompts)                      # 질문별 생성 답
```

내가 구현 시 확인할 지점은 다음과 같다.

1. **임베딩 경로의 일치:** 논문의 RAG 설명은 저장 자료와 질문을 같은 임베딩 모델로 변환한다. 두 경로의 벡터 표현이 맞지 않으면 가까움이라는 검색 기준을 신뢰할 수 없다.
2. **원문과 벡터의 연결:** 검색 결과가 가리키는 원문 조각을 보존해야 한다. 조각을 갱신한다면 벡터와 원문이 서로 다른 내용을 가리키지 않도록 관리해야 한다.
3. **청킹과 입력 길이:** 조각이 지나치게 넓으면 무관한 문맥까지 가져올 수 있고, 필요한 근거가 여러 조각에 흩어지면 하나의 검색 결과만으로 답하기 어려울 수 있다. 이는 논문의 전처리 과제에서 이어지는 구현상 판단이며, 논문이 특정 청크 크기를 실험으로 정한 것은 아니다.
4. **검색 결과와 답의 구별:** 유사도가 높은 문서가 곧 정확한 답은 아니다. ANN의 검색 오차, 원문 자체의 오류, 여러 출처의 충돌, 생성 단계의 오류가 각각 남는다.
5. **변경되는 자료의 처리:** 외부 저장소는 자료를 새로 넣을 수 있지만, 현재 질의가 새 내용을 실제로 검색하고 답에 반영하는지는 별도 확인이 필요하다.

논문은 기업·개인 자료를 외부 지식 저장소로 활용할 수 있다고 설명한다. 따라서 운영 환경에서는 어떤 자료를 검색 후보에 넣을지와 사용자가 접근 가능한 자료가 무엇인지도 설계에 포함된다. 이 문제는 뒤의 다중 테넌트 격리 과제와 연결된다.

## 시맨틱 캐시: 생성 호출 전에 답을 재사용할 수 있는가

일반적인 정확 일치 캐시는 질문 문자열이 달라지면 같은 뜻이어도 다른 키로 취급한다. 논문이 설명하는 시맨틱 캐시는 이전 질문을 임베딩해 두고, 새 질문과 의미상 가까운 항목을 찾는다. 재사용 가능한 답이 있다면 LLM API 호출을 건너뛸 수 있다. Figure 2는 질문 임베딩, 벡터 검색, 캐시 적중 여부, 적중하지 않았을 때의 생성과 저장을 한 흐름으로 보여준다. 논문은 GPT-Cache(Bang, 2023)를 벡터 데이터베이스를 이용한 시맨틱 캐시 사례로 소개한다.

![질문 임베딩 검색과 캐시 적중 여부에 따라 생성 호출을 결정하는 흐름](/assets/img/posts/llms-meet-vector-databases/figure2.png){: w="500" }
_그림 2. 캐시는 답을 생성하기 전에 조회된다. 적중 판단이 틀리면 호출 비용뿐 아니라 답의 적합성도 달라진다._

이를 코드로 옮기면 핵심 분기는 짧다.

```python
# 개념적 의사코드. 질문 배치 B, 임베딩 차원 d.
queries = receive_questions()             # 질문 B개
query_vectors = E(queries)                # (B, d)
candidates = answer_index.search(query_vectors)  # 질문별 과거 Q&A 후보

for query, candidate in zip(queries, candidates):
    if reusable(query, candidate):        # 재사용 여부를 결정할 정책
        answer = candidate.saved_answer
    else:
        answer = G(query)
        save_qa_and_embedding(query, answer)
    return_answer(answer)
```

`reusable`은 논문이 수치나 판정 규칙을 정해 준 함수가 아니다. 실제 서비스에 필요한 판단 지점을 드러내기 위해 적었다. 의미가 가까운 두 질문이라도 시점, 사용자, 허용된 자료 범위가 다르면 같은 답을 돌려줄 수 없다. 논문이 내세우는 비용과 응답 시간 이득은 **올바른 적중이 충분히 일어날 때** 얻는다. 캐시를 조회·저장하는 비용도 생기므로, API 호출 감소량과 답의 적합성을 함께 평가해야 한다.

논문은 반복 질의가 API 비용을 키우고, 짧은 시간에 몰리는 호출이 대역폭 문제를 일으킬 수 있다고 설명한다. 캐시는 이때 재사용 가능한 답에 대한 호출을 줄이는 수단이다. 다만 캐시된 답이 최신 자료를 반영하는지, 다른 사용자에게 돌려줘도 되는지는 벡터 유사도만으로 결정되지 않는다.

## 대화 메모리: 과거 내용을 다시 입력으로 가져오기

대화 메모리도 외부 저장과 검색을 쓰지만, RAG의 일반 문서와 저장 대상이 다르다. 현재 답에 필요한 이전 대화 내용을 저장하고, 관련성이 있을 때 다시 검색해 입력에 넣는다. 논문은 이를 이전 대화를 잊는 문제와 연결하며, 새 정보가 벡터 데이터베이스에 들어오면 이후 답에 활용할 수 있다고 설명한다.

이 표현을 읽을 때는 두 수준을 구별해야 한다. 이전 대화가 현재 모델 입력에서 빠져서 활용되지 않는 문제는 **외부 메모리를 검색해 다시 제공하는 방식**으로 다룰 수 있다. 반면 연속 미세 조정 과정에서 이미 학습한 능력이 약해지는 파국적 망각(catastrophic forgetting)은 모델 매개변수의 문제다. 대화 내용을 외부 저장소에 보관하는 것만으로 모델 매개변수의 망각이 해결되었다고 해석할 근거는 이 논문에 없다. “실시간 학습”이라는 표현 역시 여기서는 새 자료를 검색해 활용하는 경로로 읽는 편이 정확하다.

메모리 검색의 입력은 현재 질문이고, 출력은 관련 과거 내용이다. 저장된 대화를 언제, 얼마나, 어떤 단위로 현재 입력에 넣을지는 RAG의 청킹·검색·문맥 길이 문제와 닮아 있다. 이 서베이는 그 선택의 정량적 기준이나 성능을 제시하지 않는다.

## 검색을 더 잘 쓰려는 흐름

논문은 RAG의 발전 방향을 **자료 형태**와 **검색 방식**으로 나누어 살핀다.

먼저 자료 형태가 텍스트를 넘어간다. 이미지·텍스트를 함께 다루는 사례로 DALL-E, BLIP-2, Flamingo, CM3, FROMAGe를 소개하고, 음성 관련 사례로 Wav2Seq와 LLaSM, 비디오 관련 사례로 Vid2Seq를 든다. 이 이름들은 이 서베이가 배경으로 소개하는 선행 연구다. 모두가 동일한 벡터 데이터베이스 기반 RAG 시스템이라는 뜻은 아니다. 중요한 연결점은 이미지·음성·비디오까지 검색 대상에 넣으려면 각 자료를 표현하고 서로 연결할 방법이 필요하다는 것이다.

검색 대상의 **단위와 구조**도 달라진다. 논문은 최근접 이웃 검색을 언어 모델에 결합한 kNN-LMs, 엔터티를 문장 임베딩의 신호로 쓰는 EASE, 입력에 근거 문서를 덧붙이는 in-context RALM을 소개한다. SURGE는 관련 지식 그래프의 부분 그래프를 대화 생성에 쓰고, RET-LLM은 읽기·쓰기 메모리의 방향을 다룬다. 넓은 조각을 가져오면 정보량은 늘 수 있지만 필요한 부분의 정밀도는 떨어질 수 있다. 반대로 잘 구조화된 세밀한 검색은 필요한 정보에 가까워질 수 있으나 처리 비용이 문제가 된다. 논문은 이 균형을 검색 단위와 데이터 구조의 과제로 본다.

**언제 검색할지**도 고정된 답이 없다. 논문에서 소개한 SKR은 모델이 외부 정보가 필요한 상황을 판단하는 방향이고, Selfmem은 모델 출력을 이후 단계의 메모리로 선택한다. FLARE는 앞으로 생성할 문장을 예상해 필요한 문서를 검색하는 방향이다. Atlas는 검색을 결합한 언어 모델의 사례로 언급된다. 이들은 “질문 한 번에 상위 $K$개를 검색한다”는 기본 RAG 흐름을 넘어, 검색 시점과 검색할 내용을 바꾸려는 선행 연구들이다. 이 서베이가 이 방법들을 동일한 조건에서 비교 실험한 것은 아니다.

## 실험 대신 이 논문에서 확인할 수 있는 것

이 글은 서베이이므로 새 모델, 데이터셋, 학습 설정을 제안하고 그 성능을 측정하는 실험 절이 없다. Table 1은 제품의 지원 기능과 벡터 차원을 모은 비교표이며, Figure 1과 Figure 2는 각각 RAG와 시맨틱 캐시의 구성도다. 따라서 이 자료에서 “어느 구성이 답의 정확도를 얼마나 높였다”거나 “API 비용을 얼마나 절약했다”는 수치를 끌어낼 수 없다. 구성의 **가능한 작동 방식**과 **측정된 효과**를 구별해야 한다.

논문의 주장을 실제 시스템에서 확인한다면 질문은 각 용도에 맞게 달라진다. RAG에는 필요한 근거를 검색했는지와 답이 그 근거를 반영했는지가 중요하다. 시맨틱 캐시에는 재사용 가능한 질의의 비율뿐 아니라 잘못 재사용한 답의 비율이 중요하다. 메모리에는 필요한 과거 내용이 검색되어 현재 답에 쓰였는지가 중요하다. 이 문단은 논문에 보고된 평가 결과가 아니라, 앞의 세 구조에서 내가 도출한 점검 항목이다.

## 비용과 경량화 관점

벡터 검색은 큰 LLM을 자료가 바뀔 때마다 다시 조정하지 않고 외부 정보를 제공할 수 있게 한다. 캐시는 일부 생성 호출을 줄일 수 있다. 그러나 두 설계 모두 임베딩 계산, 벡터 저장, 인덱스 유지, 검색을 새 비용으로 가져온다. RAG에서는 검색 결과를 프롬프트에 넣는 만큼 생성 모델에 전달하는 입력도 늘어난다. 어느 쪽이 전체 비용에 유리한지는 이 논문의 수치만으로 결정할 수 없다.

저장 공간은 특히 분명한 병목이다. 논문은 1,536차원 벡터 하나가 약 6킬로바이트이고, 이를 10억 개로 늘리면 약 6테라바이트라고 설명한다. 이는 벡터 표현 자체에 관한 규모 예시다. 실제 운영에서는 원문, 식별자, 인덱스 등도 관리해야 하므로 벡터 크기만으로 전체 저장 비용을 계산할 수 없다.

차원 축소나 PQ 같은 압축은 메모리·디스크 부담을 줄이는 방향이지만, 논문은 손실 압축이 검색 재현율을 떨어뜨릴 수 있다고 지적한다. 이것이 경량화의 핵심 교환 관계다. 벡터를 작게 만드는 데 성공해도 필요한 문서가 상위 검색 결과에서 빠진다면 생성 단계의 근거가 약해진다. 반대로 모든 벡터와 인덱스를 메모리에 올리는 방식은 대규모 데이터에서 비용이 높다. 논문은 디스크 기반 검색의 지연 시간이 실시간 응용의 요구와 충돌할 수 있다는 점도 남은 과제로 제시한다.

## 한계와 생각해 볼 점

논문의 토론 절은 벡터 데이터베이스와 LLM을 결합할 때 남는 과제를 여섯 갈래로 제시한다.

1. **벡터 검색만으로 처리할 수 없는 질의:** 정확한 거래 기록이나 특정 키워드를 찾는 질의에 의미상 비슷한 항목을 돌려주는 것은 적절하지 않을 수 있다. 논문은 사후 필터링, 전문 검색, 키워드 검색, 관계형 데이터 처리를 결합하는 하이브리드 검색의 필요성을 제기한다.
2. **멀티모달 저장·검색:** 여러 자료 형태를 함께 검색하려면 인코더뿐 아니라 저장 인덱스, 순위 가중치, 결과 융합을 설계해야 한다. 한 모달리티의 벡터 검색을 그대로 여러 모달리티에 확장하는 것으로 끝나지 않는다.
3. **전처리와 벡터 크기:** 텍스트를 의미 있는 단위로 나누는 방법은 검색 품질에 영향을 준다. 높은 벡터 차원은 저장 비용을 키우고, 차원 축소·손실 압축은 재현율과 교환 관계를 만든다.
4. **다중 테넌트 격리:** 여러 사용자의 자료를 함께 운영할 때는 테넌트 간 정보 누출을 막으면서 자원을 효율적으로 공유해야 한다. 검색 결과가 관련성이 높더라도 접근 권한을 넘어서는 자료라면 사용할 수 없다.
5. **대규모 저장 비용과 지연 시간:** 메모리 기반 인덱스의 비용과 디스크 기반 검색의 성능 사이에서, 큰 규모와 낮은 응답 지연을 동시에 만족시키는 방법이 필요하다.
6. **지식 충돌:** 서로 다른 저장소나 같은 저장소의 자료가 모순되거나 편향될 수 있다. 벡터 데이터베이스는 가까운 항목을 찾지만, 출처의 신뢰도와 문맥을 판정해 어느 사실이 옳은지 자연스럽게 해결하지는 못한다.

내가 이 서베이에서 얻는 설계 기준은 벡터 데이터베이스를 “LLM의 부족한 지식을 채우는 단일 해결책”으로 다루지 않는 것이다. 먼저 답에 필요한 작업이 **의미가 비슷한 자료 찾기**, **정확한 값 조회**, **과거 답 재사용**, **이전 대화 회수** 가운데 무엇인지 정해야 한다. 그다음 검색 결과가 답으로 넘어가는 경계에서 정확성, 접근 권한, 최신성, 비용을 각각 확인해야 한다. 논문은 그 경계를 넓게 지도화하지만, 어느 인덱스·압축률·청크 크기·캐시 판정 기준이 특정 서비스에 최적인지는 검증하지 않는다.
