## 서비스 아이디어를 검증 가능한 범위로 줄이기

교안은 첫날에 서비스 개요, 사용자별 기능, UI 흐름을 정의하도록 한다. 개인 설계 산출물 TraceFab은 가상의 반도체 설비 이상이 발생했을 때 로그·Lot·Recipe·정비 이력·작업 절차서가 흩어져 있다는 문제를 설정했다. 이 데이터는 교육용 가상 자료로, 실제 기업 설비 정보가 아니다.

설계 문서는 알람 등록에서 관련 자료 확인, 원인 후보 검토, 점검·복구, 완료까지의 업무 흐름을 정의한다. 설비 운영자·설비 엔지니어·공정 엔지니어가 같은 화면을 보더라도 승인 권한은 다르다. AI는 근거와 함께 후보를 제안하고, 최종 원인과 Lot 처리는 담당자가 결정하도록 범위를 정했다.

## 요구사항을 화면과 연결하기

‘원인 분석’이라는 한 문장만으로는 구현 범위를 알 수 없다. 분석 요청의 대기·완료·실패 상태, 후보별 근거, 채택·기각·보류, 문서 버전, 권한과 예외 흐름을 별도 요구사항으로 쪼개야 한다. UI 흐름은 사용자가 어떤 상태에서 다음 화면으로 이동하는지 보여준다.

첫날의 산출물은 구현 성과가 아니라 설계의 기준선이다. 이후 데이터 모델과 API가 각 요구사항을 실제로 표현할 수 있는지 확인한다.

## 기능 목록보다 먼저 정한 경계

TraceFab은 원인 후보를 최대 세 개 제시하도록 설계했지만 설비 자동 정지, 온라인 모델 학습, 부품 자동 발주 등은 범위에서 뺐다. 3일 설계 과제에서 업무 흐름을 보여주려면 범위를 좁히는 결정도 필요하다. 자동 제어를 제외했기 때문에 사용자 확인과 승인 단계를 화면 흐름에 명확히 넣었다.

같은 ‘이상 건’이라도 운영자가 점검값을 입력하는 권한과 공정 엔지니어가 Lot 처리를 승인하는 권한은 다르다. 버튼 숨김만으로는 부족하다. 이후 API 설계에서 서버가 역할별 권한을 확인하도록 연결했다.
