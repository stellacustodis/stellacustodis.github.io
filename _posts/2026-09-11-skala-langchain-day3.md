## 프로젝트와 게임 흐름

**명탐정 피카츄**는 SKALA 7반 2조가 Google Colab 노트북으로 만든 텍스트 입력 추리 게임이다. 사건은 축제 개막 전 박물관에서 기념 메달이 사라지는 것으로 시작한다. 플레이어는 나옹·이브이·파이리·꼬부기의 진술을 듣고, 두 장소에서 증거를 모아 범인과 이유를 설명한다. 입력과 출력은 `input()`과 `print()`가 맡고, 대화 상대를 바꿀 때는 PokéAPI 스프라이트만 이미지로 표시한다.

사건의 범인과 증거 위치는 게임을 시작할 때 정해진다. `ROLE_ASSIGNMENTS`에는 범인과 별개의 비밀을 숨기는 용의자를 바꾸는 **네 가지 고정 배치**가 있고, `build_case()`가 그중 하나로 사건을 만든다. 게임 도중 모델이 범인이나 증거를 새로 만드는 구조가 아니다. 이 글은 풀이를 보존하기 위해 개별 배치의 정답은 적지 않는다.

## 모델에 맡긴 일과 Python이 맡은 일

자유 입력을 모두 문자열 규칙으로 해석하기는 어렵다. 이 노트북은 Pydantic 구조화 출력으로 질문이 알리바이·목격·증거·기타 중 어디에 속하는지, 이전 질문의 후속 추궁인지, 어떤 보유 증거를 가리키는지 해석한다. 용의자 대사와 판결 설명의 의미 평가에도 모델을 쓴다.

반대로 **질문 횟수, 조사 가능한 단계, 증거 소유 여부, 공개 조건, 스트레스 변화, 최종 점수**는 Python 상태가 결정한다. 질문에 언급된 증거 ID가 수첩에 없으면 답변 단계로 넘어가지 않는다. 증거와 관련된 질문이더라도 스트레스만 높다는 이유로 자백을 열지 않는다. 해당 용의자의 사실을 공개할 조건을 코드가 먼저 확인한다.

이 구분이 필요한 이유는 모델이 자연스럽게 말하는 능력과 게임의 판정 권한이 다르기 때문이다. 모델이 ‘증거를 찾았다’고 대답해도 실제 수집 목록에 없으면 게임 상태를 바꾸지 않는다. 질문 해석이나 대사 생성이 재시도 후에도 실패하면 질문 횟수를 소모하지 않는다. 답변 검사 오류는 안전한 문장으로 교정하고 횟수를 소모한다.

## Agent, Tool, Middleware, 기억

노트북은 LangChain의 `create_agent`로 용의자 대화 Agent와 진행자 Agent를 나눈다. 진행자에게는 **도감 조회 `lookup_pokedex`**와 **공개 수첩 읽기 `read_notebook`** 두 Tool이 있다. Tool은 이미 확인된 값을 직접 표시한다. 용의자 Agent는 Tool 없이 답변을 만들며, 현재 용의자에게 허용된 사실과 제시된 증거만 `NpcContext`로 받는다.

`refresh_public_view()`는 수집 증거와 공개 진술만 따로 복사한다. 범인 ID와 아직 조사하지 않은 증거는 이 공개 뷰에 넣지 않는다. `after_agent` Middleware는 용의자 답변이 허용된 사실에 근거하는지, 증거를 제시했을 때 필요한 인정이 빠지지 않았는지 검사한다. 검사가 실패하면 대사를 안전한 대체 문장으로 바꾸고, **같은 메시지 ID로 대화 기억도 교정**한다. 답변을 가리는 화면 처리만으로 끝내지 않으려는 설계다.

기억은 `InMemorySaver` Checkpointer를 사용한다. 용의자별 `thread_id`를 `게임 ID:용의자 ID`로 나눠, 한 용의자에게 한 질문이 다른 용의자의 대화 이력으로 섞이지 않도록 했다. 이 기억은 게임 세션의 단기 상태이며, 별도 영구 저장 기능이라고 설명하지 않는다.

## 도감 수치와 사건 설정을 섞지 않기

도감 조회는 PokéAPI 응답의 ID·타입·키·몸무게를 사건 기준값과 대조하고 스프라이트 주소를 읽는다. 화면의 한국어 이름은 노트북의 고정값을 사용한다. API의 키 단위는 데시미터, 몸무게는 헥토그램이므로 화면에는 미터와 킬로그램으로 변환한다. 호출에 실패하면 노트북에 고정한 기준값을 쓰고 출처를 캐시로 표시한다. 응답값이 사건의 기준값과 다르면 게임을 시작하지 않도록 한다.

포켓몬의 신체 수치는 도감 자료지만 **알리바이와 동기는 팀이 작성한 사건 설정**이다. 타입이나 도난품의 성질만으로 범인을 정하지 않는다는 규칙도 코드에 고정돼 있다. 외부 API가 알려 주는 사실과 게임이 창작한 사실을 구분해야 증거 비교가 성립한다.

## 판결을 근거로 제한하기

최종 입력은 용의자 이름만 고르는 것으로 끝나지 않는다. 플레이어가 쓴 이유에서 원문 구절을 추출하고, 그 구절이 실제 입력에 있는지 확인한 다음, 수집한 두 증거와 공개 진술에 맞는지 검사한다. 증거 번호를 직접 적은 경우에는 Python이 수집 목록과 대조한다. 자연어로 증거를 가리킨 경우와 설명의 의미 평가는 모델이 맡지만, 존재하지 않는 증거를 점수에 넣지는 않는다.

판결은 두 경로를 허용한다. 하나는 **개방 기록의 몸무게 구간으로 후보 둘을 좁힌 뒤, 연속 알리바이로 한 명을 제외**하는 방법이다. 다른 하나는 **현장 기록과 휴대 기록이 같은 개방 사건인지 대조하고, 공개된 인정 진술을 연결**하는 방법이다. 두 경로 모두 실제 수집 증거와 사건의 시각·자료 종류를 확인한다.

```python
score = 40 + 40 * evidence + 20 * testimony
```

선택한 용의자가 맞으면 40점에서 시작한다. 증거 연결이 유효하면 40점, 처음 진술과 결론의 모순까지 설명하면 20점을 더한다. 100점일 때만 성공으로 처리한다. 다만 설명 구절의 **의미가 타당한지**는 모델 검사에 의존하므로, 이 점수식만으로 자유 입력 판정의 정확성이 보장되지는 않는다.

## 확인한 범위와 한계

노트북의 모델 없는 기본 검사를 다시 실행해 네 사건 배치, Pydantic 출력 형식, 초기 단계·횟수, 오프라인 도감 값이 통과하는 것을 확인했다. 노트북에 저장된 실행 출력에는 네 용의자의 도감 출처와 사건 도입, 초기 진술·입력 안내가 남아 있다. 저장된 출력만으로 **한 판 완주나 자유 질문에 대한 모델의 정답률**을 확인할 수는 없다.

노트북은 `gpt-4o-mini`를 기본 모델로 설정하고 API 키가 있는 Colab 환경에서 플레이하도록 작성됐다. 이 글에서 확인한 것은 코드 구조와 모델 없는 기본 검사다. 실제 모델의 질문 해석·대사·판결 판단은 별도 플레이 기록과 평가가 있어야 품질을 말할 수 있다.
